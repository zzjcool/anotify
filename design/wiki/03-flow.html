一条事件的旅程

一个 webhook 从进来到手机震动，中间到底发生了什么。这页把十跳摊开，标出哪一步会丢、哪一步会重、哪一步之后事实就不能再改。全程只有一次「路由决策」，就是查出口表。

主通路

webhookPOST /v1/in/{sourceId}
→
eventsappend-only
→
edges一次查表
→
tasks一个事务 N 行
→
nodeexecve(argv[])
→
手机human sink
六跳一条线。真正落库的只有两处：events 与 tasks，其余都是状态迁移。中间的 edges 不是一张运行时写进去的表，而是配置期就画好的出口图——跑起来只是读它。

十步时序

外部触发
GitHub webhook 打到 POST /v1/in/{sourceId}。服务端按 sourceId 取到签名密钥，先验签再收 payload。验签失败直接 401，事件不落库，也就不会在 trace 里留下任何东西。
事件入库
写一行 events，拿到 event_id；同一事务里分配 trace_id（新链路则新建）和 span_id（本跳）。到这一步事件只是「已发生的事实」，还没决定做任何事。 
-- 同一事务：事件 + trace 起点
INSERT INTO events (id, source, type, payload, trace_id, span_id, created_at)
VALUES (:event_id, 'github', 'pull_request.opened', :payload, :trace_id, :span_id, now());
查出口表
取事件的 (source, type) 作为起点，去 edges 查一次索引：从 (from_capability, from_port) 查到 N 行 to_capability，就是 N 个下游能力。触发器没有入边，所以它的 from_capability 由事件类型充当（source:github）。 
-- 中枢侧唯一的路由依据：一次索引查询
SELECT to_capability
  FROM edges
 WHERE from_capability = 'source:github'
   AND from_port       = 'pull_request.opened';

-- 返回 N 行 → N 个下游能力，全部建任务
没有条件求值、没有优先级、没有表达式。路由就是这一次查表：同样的 (source, type) 在任何机器、任何时间都得到同一批行，因为答案写死在图里。
查不到行 → 一个任务都不建，trace 上记 pruned，原因是 no_edge：表里没有这条边。
扇出
N 行结果在同一个事务里 INSERT N 行 tasks。这是扇出，不是互斥选择：一个 PR 可以既派 agent 审查、又推手机，两条都下发。事务保证了「要么都发出去，要么一条都没有」。 
BEGIN;
-- edges 第 1 行 → machine sink（capability = review）
INSERT INTO tasks (id, event_id, capability, sink, state) VALUES (:t1, :event_id, 'review', 'machine', 'pending');
-- edges 第 2 行 → human sink（capability = notify.phone）
INSERT INTO tasks (id, event_id, capability, sink, state) VALUES (:t2, :event_id, 'notify.phone', 'human', 'pending');
COMMIT;
派发
在申报了该能力的实例里按最少负载挑一个（比 inflight / concurrency），写 lease_until = now + 30s，状态 pending → assigned。 默认就是纯负载均衡——结果存在中枢，下游读结果不需要回原机器。 只有能力在 manifest 里声明了 sticky（共享工作目录、增量编译这类），才先查 node_pins。本期不做收集，所以绝大多数任务走纯均衡那条路。 
-- 默认：纯负载均衡，无状态
order_by inflight / concurrency asc
limit 1

-- 仅当 manifest.capabilities[].sticky 声明了才走：
sticky_key = sha256(trace_id ∥ capability ∥ selector)
-- node_pins 命中则直用；未命中按负载挑一个并写入
节点接单
节点收到 assign（或主动拉取），确认能力名在自己 manifest 里，回报 ack。ack 只是接单确认，不是完成。状态 assigned → acked，目标窗口 assign → ack 20s。
执行
节点在本地 execve(argv[]) 跑能力对应的命令，绝不经过 /bin/sh -c。执行期间每 10s 发一次心跳续租。状态 acked → running。中枢从头到尾不知道 argv 长什么样。
结果回流
节点回报 result：{status, out, summary, artifacts}，上限 8KB，超了截断并标记。状态从 running 落到 succeeded 或 failed，同时往 events 写一条派生事件。 这里最关键的是新增的 out：出口名，或 null。它同时回答了两件事——有没有下游、有哪个下游。 
{
  "status": "succeeded",   // succeeded | failed
  "out":    "fix",        // 我选了哪个出口；null = 到此为止
  "summary": "...",      // ≤8KB
  "artifacts": []
}
status 和 out 正交，失败也可能要走修复分支：
status out 含义
succeeded "fix" 干完了，往下走
succeeded null 干完了，到头了
failed "fix" 失败，但触发修复分支
failed null 失败且断在这里
接力
派生事件不会重新求值任何东西——它带着上游回报的 out 回来。拿 (上游能力, out) 去 edges 查，命中一行就建下一跳任务，hop 加一，trace_id 沿用。 
out = "fix"   →  edges(review, fix) = implement  →  建任务
out = null    →  不查表，这条分支停在这里
out = "xyz"   →  edges(review, xyz) 空  →  pruned / no_edge
环是允许的（review → fix → review 是真实场景），终止性靠 path 保证： path 是从根到本任务这条具体路径的能力名序列，不是整条 trace 的能力集合——同一个能力在另一条分支上照样能跑。 path 里已有该能力 → 静默剪枝，不报错、不暂停，但必须在 trace 上看得见（记 pruned 加原因）。
收敛
trace 内不再有 pending / assigned / acked / running 的任务，就记为 trace.settled，并向 human sink 发一条通知。
但“还有没有人会接着跑”不能靠看状态机猜。任务落到 succeeded 只是这一个 span 结束了， 它随时可能再派生出下一跳；而派生事件可能晚到，也可能永远不来。
所以出口由节点在结果里回报：result.out。 它必须在命令跑完之后才说得出来——成功要跑完才知道，失败也要跑完才知道。 中枢不预判、不反推，只看这一个字段有没有回报过。null 也算已回报（它明确表示「到头了」）。
另外，收敛不等于全成功：failed 和 abandoned 也算落定，只是通知里会点明是哪一种。 
-- 收敛判定：三个条件，缺一不可
1 无 pending / assigned / acked / running
2 无未到期任务（expires_at / not_before 全在过去）
3 每个终态任务都 out 已回报（null 或具体值都算）

-- 条件 2 是必须的：一个还在队列里排队的任务也满足条件 1，
-- 但它随时会被派发。少了它，trace 会在队列中途提前收敛。

-- out 来自节点回报的 result，不是 manifest 声明：
-- 命令跑完之前，谁也不知道它会走哪个出口。
-- 缺失 out → 按「未回报」计入（保守，不收敛），直到 max_duration 兜底。
这里有个容易漏掉的竞态。收敛判定的第一次扫描注定是「看着能收敛」—— 因为 trigger 事务是第二步才提交的，扫描可能跑在它前面。 所以不能在扫描成立时就立刻发通知，必须再查一次（写一个 pending_settle 标记 → 下一轮复核 → 仍成立才发）。 否则现象就是：链明明还有下一跳，手机已经先响了。

两个 sink 同时发生

扇出的典型样子：一个 PR 事件，一半去机器、一半去人。两条分支从同一行 events 长出来，之后互不相干。

pull_request.opened event · trace t_8f2a
machine sink · 至少一次
能力 review → node agent 审查 ack · 租约 · 重试 · 必须回报
human sink · 尽力而为
能力 notify.phone → 推手机 发了就忘 · 不回报 · 可丢
一条事件，两个产物。左支是一次 INSERT 出来的 task，右支也是一次 INSERT 出来的 task，两者只是 sink 字段不同——在 edges 表里就是两行不同的边。

两者互不等待。agent 卡住不影响手机已经响过；推送失败也不会让 agent 任务重试。两条分支各自收敛，各自在 trace 上留痕。

租约与心跳

租约回答一个问题：这个任务现在归谁。答案写死在 lease_until 里，节点用心跳把它往后推。

assign t = 0 · lease_until = t+30s
→
ack ≤ 20s · 只是接单
→
心跳 每 10s · 续租
→
心跳 每 10s · 续租
→
result ≤ 8KB
每次心跳把 lease_until 推到 now + 30s
→
TTL 30s / 心跳 10s = 允许连丢两次
心跳不是保活，是续租。连续两次心跳没到，租约到期，任务退回可派发状态——由中枢判，不由节点自报。

失败分支

两条失败路径，处理方式相反：一条重派，一条不重派。区别不在错误类型，而在「谁还活着」。

维度 租约过期 lease_expired 节点消失 abandoned
触发 30s 内没有心跳（含没等到 ack） 节点下线、被移除、长连接断到判死
状态 assigned | acked | running → lease_expired → pending assigned | acked | running → abandoned
重派 是，max_attempts 3 次 否
退避 10s → 60s → 300s —
通知 重派期间不通知；用尽 3 次转 failed 进 DLQ 时通知 默认发
算成功吗 重派成功就算成功 永远不算
assignedlease_until = +30s
→
30s 无心跳lease_expired
→
pending 重派attempt 2 / 3
assigned节点在线
→
节点消失无法确认副作用
→
abandoned不重试 · 默认通知
abandoned 不等于成功。它表示「不知道做没做成」，所以默认要吵醒人。唯一的例外是节点 manifest 标了 resumable: true——能力对应的命令本身可重入，才会重派到新节点。
