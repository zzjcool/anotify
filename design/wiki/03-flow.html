一条事件的旅程

一个 webhook 从进来到手机震动，中间到底发生了什么。这页把十跳摊开，标出哪一步会丢、哪一步会重、哪一步之后事实就不能再改。

主通路

webhookPOST /v1/in/{sourceId}
→
eventsappend-only
→
rulesmatch 求值
→
tasks一个事务 N 行
→
nodeexecve(argv[])
→
手机human sink
六跳一条线。真正落库的只有两处：events 与 tasks，其余都是状态迁移。任何一个环节挂掉，已经写下的行不会消失——这就是「能解释」的底座。

十步时序

外部触发
GitHub webhook 打到 POST /v1/in/{sourceId}。服务端按 sourceId 取到签名密钥，先验签再收 payload。验签失败直接 401，事件不落库，也就不会在 trace 里留下任何东西。
事件入库
写一行 events，拿到 event_id；同一事务里分配 trace_id（新链路则新建）和 span_id（本跳）。到这一步事件只是「已发生的事实」，还没决定做任何事。 
-- 同一事务：事件 + trace 起点
INSERT INTO events (id, source, type, payload, trace_id, span_id, created_at)
VALUES (:event_id, 'github', 'pull_request.opened', :payload, :trace_id, :span_id, now());
规则求值
取出该 source 下启用中的规则，逐条求 match。命中 N 条就是 N 条，不选最优的一条。命中 0 条则不派任务，但 trace 上要写 pruned 和具体原因——是哪个条件、实际值是什么。 
action == "opened"                     pass
labels contains "review-needed"         fail  actual: ["bug"]
扇出
N 条命中规则在同一个事务里 INSERT N 行 tasks。这是扇出，不是互斥选择：一个 PR 可以既派 agent 审查、又推手机，两条都下发。事务保证了「要么都发出去，要么一条都没有」。 
BEGIN;
-- 规则 A → machine sink
INSERT INTO tasks (id, event_id, rule_id, sink, state) VALUES (:t1, :event_id, :ra, 'machine', 'pending');
-- 规则 B → human sink
INSERT INTO tasks (id, event_id, rule_id, sink, state) VALUES (:t2, :event_id, :rb, 'human', 'pending');
COMMIT;
派发
按最少负载选执行器，再用粘性路由把同一 trace_id + rule_id 钉到同一个实例：首次按负载挑并写 node_pins，之后一律查表。写 lease_until = now + 30s，状态 pending → assigned。 
sticky_key = sha256(trace_id ∥ rule_id ∥ selector)
-- node_pins 命中则直用；未命中按 inflight 最少挑一个并写入
节点接单
节点收到 assign（或主动拉取），确认命令名在自己 manifest 里，回报 ack。ack 只是接单确认，不是完成。状态 assigned → acked，目标窗口 assign → ack 20s。
执行
节点在本地 execve(argv[]) 跑命令，绝不经过 /bin/sh -c。执行期间每 10s 发一次心跳续租。状态 acked → running。中枢从头到尾不知道 argv 长什么样。
结果回流
节点回报 result，上限 8KB，超了截断并标记。状态 running → succeeded，同时往 events 写一条派生事件。失败则是 running → failed，走重试或进 DLQ。
接力
派生事件再走一遍规则求值，命中就生出下一跳任务——这就是接力。防死循环靠 path：它是「从根到本任务这条具体路径」的 rule_id 序列，路径里已有的 rule_id 会被静默剪枝，不报错但必须在 trace 上看得见。没有可接的规则，链路就到此结束。
收敛
trace 内不再有 pending / assigned / acked / running 的任务，就记为 trace.settled，并向 human sink 发一条通知。注意收敛不等于全成功：failed 和 abandoned 也算落定，只是通知里会点明是哪一种。

两个 sink 同时发生

扇出的典型样子：一个 PR 事件，一半去机器、一半去人。两条分支从同一行 events 长出来，之后互不相干。

pull_request.opened event · trace t_8f2a
machine sink · 至少一次
规则 A → node agent 审查 ack · 租约 · 重试 · 必须回报
human sink · 尽力而为
规则 B → 推手机 发了就忘 · 不回报 · 可丢
一条事件，两个产物。左支是一次 INSERT 出来的 task，右支也是一次 INSERT 出来的 task，两者只是 sink 字段不同。
两者互不等待。agent 卡住不影响手机已经响过；推送失败也不会让 agent 任务重试。两条分支各自收敛，各自在 trace 上留痕。

租约与心跳

租约回答一个问题：这个任务现在归谁。答案写死在 lease_until 里，节点用心跳把它往后推。

assign t = 0 · lease_until = t+30s
→
ack ≤ 20s · 只是接单
→
心跳 每 10s · 续租
→
心跳 每 10s · 续租
→
result ≤ 8KB
每次心跳把 lease_until 推到 now + 30s
→
TTL 30s / 心跳 10s = 允许连丢两次
心跳不是保活，是续租。连续两次心跳没到，租约到期，任务退回可派发状态——由中枢判，不由节点自报。

失败分支

两条失败路径，处理方式相反：一条重派，一条不重派。区别不在错误类型，而在「谁还活着」。

维度 租约过期 lease_expired 节点消失 abandoned
触发 30s 内没有心跳（含没等到 ack） 节点下线、被移除、长连接断到判死
状态 assigned | acked | running → lease_expired → pending assigned | acked | running → abandoned
重派 是，max_attempts 3 次 否
退避 10s → 60s → 300s —
通知 重派期间不通知；用尽 3 次转 failed 进 DLQ 时通知 默认发
算成功吗 重派成功就算成功 永远不算

→
30s 无心跳lease_expired
→
pending 重派attempt 2 / 3
assigned节点在线
→

→

abandoned 不等于成功。它表示「不知道做没做成」，所以默认要吵醒人。唯一的例外是节点 manifest 标了 resumable: true——命令本身可重入，才会重派到新节点。
