一条事件的旅程

一个 webhook 从进来到手机震动，中间到底发生了什么。这页把十跳摊开，标出哪一步会丢、哪一步会重、哪一步之后事实就不能再改。全程只有一次「路由决策」，就是查出口表——查完之后还要拿目标接口的 schema 校一次参数。

主通路

webhookPOST /v1/in/{sourceId}
→
eventsappend-only
→
edges接口 → 接口 · 一次查表
→
tasks一个事务 N 行
→
nodeexecve(argv[])
→
手机end · 推手机
六跳一条线。真正落库的只有两处：events 与 tasks，其余都是状态迁移。中间的 edges 不是一张运行时写进去的表，而是配置期就画好的出口图——两端都是接口，不引用任何机器；跑起来只是读它。

十步时序

外部触发
GitHub webhook 打到 POST /v1/in/{sourceId}。服务端按 sourceId 取到签名密钥，先验签再收 payload。验签失败直接 401，事件不落库，也就不会在 trace 里留下任何东西。
事件入库
写一行 events，拿到 event_id；同一事务里分配 trace_id（新链路则新建）和 span_id（本跳）。到这一步事件只是「已发生的事实」，还没决定做任何事。 
-- 同一事务：事件 + trace 起点
INSERT INTO events (id, source, type, payload, trace_id, span_id, created_at)
VALUES (:event_id, 'github', 'pull_request.opened', :payload, :trace_id, :span_id, now());
查出口表，校验参数
取事件的 (source, type) 定位起点——起点也是接口：github@1（kind: origin）。 它的出口名不由事件类型自由充当，而是由接口给定，pull_request.opened 归一到 pr_opened。 然后去 edges 查一次索引：从 (from_interface, from_port) 查到 N 行 to_interface，就是 N 个下游接口。
查到边不等于派得出去。每个目标接口还要用它的 params_schema 校一次参数： 本次要带的 params 合不合目标接口的契约。不通过的出口记一条 pruned / reason=param_schema，任务不建——这一校验发生在建任务之前，执行器根本不会看到它。 
-- 派发四步：查表 → 校参数 → 找实现者 → 挑一台

-- ① 查表（出口名来自接口，两端都是 interface_id）
SELECT to_interface FROM edges
 WHERE from_interface = 'ifc_7c1a'      -- github@1
   AND from_port      = 'pr_opened';
-- N 行 → N 个下游接口；0 行 → 记 pruned / no_edge

-- ② 逐个用目标接口的 params_schema 校验本次参数（不通过就不建任务）
for each to_interface:
    schema = interface_versions[to_interface].params_schema
    if not validate(params, schema):
        trace.pruned(reason = 'param_schema')   -- 到此为止，不落 tasks
        continue

-- ③ 找实现了这个接口的执行器（不是按能力名找，是按 interface_id 找）
SELECT runner_id FROM capabilities WHERE interface_id = :to_interface;

-- ④ 在这些执行器里挑一台 → 建任务
没有条件求值、没有优先级、没有表达式。路由就是这一次查表：同样的 (from_interface, from_port) 在任何机器、任何时间都得到同一批行，因为答案写死在图里。
查不到行 → 一个任务都不建，trace 上记 pruned，原因是 no_edge：表里没有这条边。 查到了但参数不合 schema → 同样不建任务，原因换成 param_schema：这条边存在，只是这次的数据走不进去。
参数校验是查表之后唯一还能拦住的一步。它前移到建任务之前，所以执行器永远收不到一个 「参数不合自己接口契约」的任务。反过来说，一个任务只要能建出来，它的 params 就已经对得上目标接口的 params_schema——执行器不需要再校一次，也没有机会校错。
扇出
N 行结果在同一个事务里 INSERT N 行 tasks。这是扇出，不是互斥选择：一个 PR 可以既派 agent 审查、又推手机，两条都下发。事务保证了「要么都发出去，要么一条都没有」。 
BEGIN;
-- edges 第 1 行 → 接口 review@1（ifc_2e04）
INSERT INTO tasks (id, event_id, interface, state) VALUES (:t1, :event_id, 'ifc_2e04', 'pending');
-- edges 第 2 行 → 接口 notify.phone@1（ifc_51bd）
INSERT INTO tasks (id, event_id, interface, state) VALUES (:t2, :event_id, 'ifc_51bd', 'pending');
COMMIT;
写进 tasks 的是 interface_id，不是能力名。因为图里没有机器，只有接口； 「哪台机器去跑」是下一步才决定的事，建任务的时刻不需要知道它。这也意味着换一台机器重派同一个任务， interface 这一列一个字节都不用改。
派发
先查 capabilities WHERE interface_id = ?，得到实现了这个接口的所有执行器； 再在这些执行器里按最少负载挑一个（比 inflight / concurrency），写 lease_until = now + 30s，状态 pending → assigned。 顺序不能反：先有「谁能做这个接口」，才谈得上「在能做的里面挑哪一台」。
默认就是纯负载均衡——结果存在中枢，下游读结果不需要回原机器。 只有能力在执行器 manifest 里声明了 sticky（共享工作目录、增量编译这类），才先查 runner_pins。本期不做收集，所以绝大多数任务走纯均衡那条路。 
-- ① 先找实现者：按 interface_id，不按名字
SELECT runner_id
  FROM capabilities
 WHERE interface_id = :task.interface;
-- 0 行 → 任务保持 pending，按租约排队（这不是错误，也不是剪枝）

-- ② 在这些候选里按负载挑一台，默认纯均衡、无状态
order_by inflight / concurrency asc
limit 1

-- 仅当 manifest.capabilities[].sticky 声明了才走：
sticky_key = sha256(trace_id ∥ interface_id ∥ selector)
-- runner_pins 命中则直用；未命中按负载挑一个并写入
执行器接单
执行器收到 assign（或主动拉取），确认能力名在自己 manifest 里，回报 ack。ack 只是接单确认，不是完成。状态 assigned → acked，目标窗口 assign → ack 20s。
执行
执行器在本地 execve(argv[]) 跑能力对应的命令，绝不经过 /bin/sh -c。执行期间每 10s 发一次心跳续租。状态 acked → running。中枢从头到尾不知道 argv 长什么样。
结果回流
执行器回报 result：{status, out, summary, artifacts}，上限 8KB，超了截断并标记。状态从 running 落到 succeeded 或 failed，同时往 events 写一条派生事件。 这里最关键的是新增的 out：出口名，或 null。它同时回答了两件事——有没有下游、有哪个下游。 
{
  "status": "succeeded",   // succeeded | failed
  "out":    "fix",        // 我选了哪个出口；null = 到此为止
  "summary": "...",      // ≤8KB
  "artifacts": []
}
status 和 out 正交，失败也可能要走修复分支：
status out 含义
succeeded "fix" 干完了，往下走
succeeded null 干完了，到头了
failed "fix" 失败，但触发修复分支
failed null 失败且断在这里
接力
派生事件不会重新求值任何东西——它带着上游回报的 out 回来。拿 (该任务的 interface, out) 去 edges 查，命中一行就建下一跳任务，hop 加一，trace_id 沿用。 
out = "fix"   →  edges(ifc_2e04, fix) = ifc_9a13  →  建任务（再校一次参数）
out = null    →  不查表，这条分支停在这里
out = "xyz"   →  edges(ifc_2e04, xyz) 空  →  pruned / no_edge
环是允许的（review → fix → review 是真实场景），终止性靠 path 保证： path 是从根到本任务这条具体路径的接口序列，不是整条 trace 的接口集合——同一个接口在另一条分支上照样能跑。 path 里已有该接口 → 静默剪枝，不报错、不暂停，但必须在 trace 上看得见（记 pruned 加原因）。
到头
每个任务跑完都回报 out。拿（这个接口, 这个 out）再查一次表： 有边就建下一个任务，没边就在这里走到头。
中枢不判断「整条链是不是结束了」。它没有这个职责，也不该有—— 链有没有走完，是你查看事件流向时才关心的事，不是系统要实时维护的状态。
这里只保留一个事实：result.out 由执行器自己报。 它必须在跑完之后才说得出来——成功要跑完才知道，失败也要跑完才知道。 中枢不预判、不反推，只看这个字段有没有回报过。null 也算已回报（明确表示「到头了」）。 
-- 查表决定还有没有下一跳，这是唯一的路由动作
SELECT to_interface FROM edges
 WHERE from_interface = :ifc AND from_port = :out;

-- 0 行 = 到头。不建任务，没有「整条链结束」的判定，也不发通知。
-- 通知是图里的一条边（→ notify.phone@1），它在链上正常派发，
-- 不依赖任何「链走完了」的全局状态。

一个事件，两条分支

扇出的典型样子：一个 PR 事件，一半去机器、一半去人。两条分支从同一行 events 长出来，之后互不相干。

pull_request.opened event · trace t_8f2a
pipe · 至少一次
接口 review@1 → 执行器上 node agent 审查 ack · 租约 · 重试 · 必须回报
end · 尽力而为
接口 notify.phone@1 → 推手机 发了就忘 · 不回报 · 可丢
一条事件，两个产物。左支是一次 INSERT 出来的 task，右支也是一次 INSERT 出来的 task，两者只是 end 字段不同——在 edges 表里就是两行不同的边。

两者互不等待。agent 卡住不影响手机已经响过；推送失败也不会让 agent 任务重试。两条分支各自收敛，各自在 trace 上留痕。

租约与心跳

租约回答一个问题：这个任务现在归谁。答案写死在 lease_until 里，执行器用心跳把它往后推。

assign t = 0 · lease_until = t+30s
→
ack ≤ 20s · 只是接单
→
心跳 每 10s · 续租
→
心跳 每 10s · 续租
→
result ≤ 8KB
每次心跳把 lease_until 推到 now + 30s
→
TTL 30s / 心跳 10s = 允许连丢两次
心跳不是保活，是续租。连续两次心跳没到，租约到期，任务退回可派发状态——由中枢判，不由执行器自报。

失败分支

两条失败路径，处理方式相反：一条重派，一条不重派。区别不在错误类型，而在「谁还活着」。

维度 租约过期 lease_expired 执行器消失 abandoned
触发 30s 内没有心跳（含没等到 ack） 执行器下线、被移除、长连接断到判死
状态 assigned | acked | running → lease_expired → pending assigned | acked | running → abandoned
重派 是，max_attempts 3 次 否
退避 10s → 60s → 300s —
通知 重派期间不通知；用尽 3 次转 failed 进 DLQ 时通知 默认发
算成功吗 重派成功就算成功 永远不算
assignedlease_until = +30s
→
30s 无心跳lease_expired
→
pending 重派attempt 2 / 3
assigned执行器在线
→
执行器消失无法确认副作用
→
abandoned不重试 · 默认通知
abandoned 不等于成功。它表示「不知道做没做成」，所以默认要吵醒人。唯一的例外是能力清单标了 resumable: true——能力对应的命令本身可重入，才会重派到新机器。
