可观测与版本

事件系统上线后只有两个问题会被反复问：这件事到底走没走、为什么没走。前者靠 trace，后者靠查表和版本钉住。这一页讲这两样怎么变成默认能力，而不是出事以后再补日志。

对齐 OTel，不自己发明一套

trace 要表达的东西——一次根事件引起的全部工作、派生关系、以及「不是父子但仍然相关」的引用——OTel 已经定义过一遍了。我们借它的模型，五个词一一对应。

OTel Anotify 含义
Trace trace_id 一个根事件引起的全部工作。根事件落库时生成，之后所有派生任务继承同一个值。
Span task 一次实际执行：从任务建行到进入终态。
span_id task.id span 的唯一标识，就是任务 id 本身。
parent_span_id tasks.parent_task_id 谁派生出这个任务。根事件直接派生的任务，这一列为空。
Span Links tasks.inputs 不构成父子、但确实是输入来源的引用集合，可以有多个。

借的理由只有两条，但都硬：

语义已经被推演完整
父子、兄弟、并行、跨服务关联，以及「不是父子但相关」这几种情况，自己设计表结构一定会漏掉一两种；补的时候要改 schema，还要迁历史数据。OTel 把这些情况都想过了，照着摆就行。
字段名就是接口
命名对齐以后，要把 trace 吐给任何一个吃 OTel 的后端都不用重新建模；反过来，读过 OTel 的人不用再学一套私有词汇。

借的是模型和字段名，不是整套 SDK 与 collector 运行时。落到实现上就是几张表加几个字段——这也是「能解释」的前提：字段在库里才查得出来；只活在进程内存里的 trace，事后什么问题都回答不了。

一条 trace 长什么样

一个 pull_request.opened 事件进来，用 (source:github, pull_request.opened) 查一次 edges，拿到三条边，各派一个任务；任务回报的 out 再查表，接力往下走。每个条形是一个 span，长度就是它的时长。

横轴是时间，条的长度就是 span 的时长。左侧字母是分支：A 审查链、B lint 链、C 通知链，都由 t+0.00 的同一个根事件扇出，互不等待、互不汇聚。查表是一瞬间，画成细竖线；被 path 剪掉的那次没有时长，画成红虚框，位置就是它被拒的那一刻。最下面那行灰虚线是表里有、但这次没被走到的边。不足一个像素的短 span 保底 3px 才看得见。

能标出起止，是因为 span 就是任务

一个 span 从任务建行（pending）开始计时，到进入终态（succeeded / failed / canceled / abandoned）结束。lease_expired 是中间态，不算结束——它之后要么重试成新的一次尝试，要么落到上面某个终态。

森林，不是树

三条分支之间没有汇聚点：审查的结论不会和 lint 的结论合并成一个下游任务。中枢本期不做收集（join），所以 trace 在数据上是一片森林——每棵树是一条接力链，树与树之间靠 trace_id 归堆，链内靠 parent_task_id 连父子。

没有汇聚点，就不需要批次表、计数表，也不用定义「部分失败怎么算」。想「等一组都完成」，办法是把等待放进节点内部：A 在自己进程里并行、自己等、自己汇总，只回报一个 result，对中枢来说这仍是一个任务。代价要写清楚：A 内部那几路并行在 trace 上不可见，它是一条不可再分的横条。

「为什么没触发」

这是事件中心最常被问到的一句话。新模型下它变简单了：路由只是查表，所以「为什么没走这条边」只有三种可能，而且每一种都是图 + 回报的直接对照，不需要把任何求值过程重放一遍。

原因 判据（一眼可查） trace 上的样子
表里没有这条边 拿 (from_capability, from_port) 查 edges，返回 0 行。图是显式声明的，所以这一条不跑也能知道：把图投影出来就能看见缺口。 事件 span 上记 pruned / reason=no_edge，附上查表的两个键；没有 task span。
上游没回报这个出口 上游任务的 result.out 是 null 或别的出口名。既然没有从这个出口出去，就压根没查过表。 上游 span 上标着 out=null 或 out=<其它>，下游没有 span、也没有 pruned 记录。
被 path 剪枝 边查到了，但要去的那个能力已经在 path 里（从根到本任务这条路径的能力名序列）。静默剪枝：不报错、不暂停。 红虚框加 pruned / reason=path，指出重复的是哪个能力名。

三种原因长什么样

① 表里没有这条边
review --(fix)--> ?
edges(review, fix)
→ ∅ 0 行
记 pruned / no_edge
② 上游没回报这个出口
review result.out
→ null
不查表
到此为止，非剪枝
③ 被 path 剪枝
edges(implement, fix)
→ review 1 行
path 里已有 review

三者互斥，顺序也是固定的。先看上游有没有回报这个出口（②），再看表里有没有这一行（①），最后看 path 里是不是已经有它（③）。三种判断都是常量时间，都只读一行数据。

这就是新模型最大的收益：「为什么没触发」从一个推理问题变成了一个查表问题。以前的逐条件求值要跑过才知道答案，现在连线上的证据都不需要——图是静态的，path 和 out 是落库的字段，两条一对照，答案是确定的。

用户问 trace 上直接给的
这个 webhook 收到了吗 收到了。根 span 在 t+0.00 落库，原始 payload 挂在事件行上。
有几条边查到了 三条：(source:github, pull_request.opened) → review / lint / notify.phone，每条对应一个 task span。
为什么 review 没有往下走 done 那条边 review 回报的是 out=fix；edges(review, done) 确实在表里，但这次没被走到——图中灰虚线那一行。
为什么 implement 之后的 review 没跑 被 path 剪枝：path = [review, implement] 里已经有 review。红虚框加 pruned / path。
是不是被限额剪掉了 不是。G1 放行、G2 未到顶（hop 1 / 10）、G4 未超（3 / 100）、G6 未超，闸的当时的计数值都记着。
当时用的是哪张图 trace 上钉着 grf_20261024T090402Z_5e7c1b0f，点开就是当时的 edges + capabilities 快照。

三种原因在界面上共用一个视觉语言（红虚框），区别只在 reason 字段和随附的证据：no_edge 附查表的两个键，path 附重复的能力名，而「上游没回报这个出口」根本不算剪枝——它是一个正常结束的分支，只在 span 上标 out。剪枝是静默的，但一定留痕——静默指的是不打断业务，不是不记录。

版本钉住

复盘要能回答「当时那张图长什么样」。所以出口图、节点 manifest、中枢侧能力注册表都按内容存快照，每次变更追加一行。

表 存什么 什么时候多一行
graph_versions 整张出口图的快照：edges 的全部行，加上各节点申报的 capabilities[].outputs。图是一份整体，拆开钉就没法回答「当时有没有这条边」。 图被保存时（增删一条边、或某个能力的出口集变了）。
node_manifest_versions 节点上报的 manifest 内容快照：能力名、标签声明、outputs、sticky、idempotent / resumable。 节点上报的内容变了。
registry_versions 中枢侧能力注册表的快照。 注册表变了。

三张表都是 append-only，且 content_hash 上有 UNIQUE：同样的内容不会存第二遍；图改坏又改回来，命中旧行，也不会多出一条「看起来是新的」版本。

每行的标识是 <prefix>_<UTC时间>_<content_hash前8>：

reg_20261023T101500Z_a1b2c3d4   # registry_versions
grf_20261024T090402Z_5e7c1b0f   # graph_versions
man_20261022T183300Z_c93d24ae   # node_manifest_versions

钉 hash，不钉时间

trace 上记的是不可变的版本 id（那串 hash），不是「按时间反查当时生效的版本」这种结果。差别全在补录上。

假设有人在十月导入了一张八月的图版本。任何按「created_at 早于 span 时间且取最新一条」实现的解析，都会让八月的旧 trace 突然指向另一张图——旧结论当场变形，而没人动过那条 trace。钉死 hash 的话，补录只能新增一行，旧 trace 的指向一个字节都不会变。

时间不是版本，内容是版本。补录、回滚、跨时区导入都会打乱时间顺序，但动不了已经算好的 hash。这也是为什么标识里既有时间又有 hash：时间是给人看的坐标，hash 才是被钉住的锚。

节点不上报版本号

节点只上报 manifest 内容，不报自己算的版本号。版本号是节点自己起的名字，中枢无从校验，节点一改编号方式历史就对不上；内容是事实，hash 由中枢算，内容变一个字符 hash 就变。要认版本，就认 hash。

叠回去看

复盘时取 trace 上钉住的版本 id，读出当时的图快照，再把图里的每条边与 trace 上真实出现的 span 对齐：出现了的画亮实线，图里有但这次没走到的画灰虚线，被剪掉的画红虚框。

亮实线 · 走过
灰虚线 · 有边没走
红虚框 · 剪枝
三层叠加的读法。亮实线是这次真实执行的路径；灰虚线是当时的图里存在、这次却没走到的边，回答「本来还会发生什么」；红虚框是被剪枝挡住的那一步，回答「差一点就发生了」。

三种标记都来自同一份 trace 加同一份图快照，不用再查别的地方。这也是不做拖拽画布的原因之一：能解释的东西不靠画出来，靠记下来。
