为什么

这页说三件事：和现有几类工具差在哪、要解决哪三个问题、以及刻意不做什么。

和谁比

三类东西看起来都能「跑一段自动化」，但各自解决了不同的问题。

单机 agent dify / n8n 本设计
谁触发 你敲下命令 平台里配的触发器 事件（webhook / cron / 外部调用），和人工手动
能跑几步 一步到几步，跑完就结束 图里画多少步就跑多少步 图里查到几行就派几个，可以接力、可以成环
跑在哪 你的机器 平台侧，或你部署的集群 你的机器（节点出站连中枢），凭据永不出本机
能力从哪来 你本地有什么就用什么，没有契约 平台内置 + 插件市场 中枢先定义，节点只能声明已定义的那些
长任务断了 进程死了就没了 平台重试，但看不出断在哪一步 租约接管、换台机器重派，trace 上留痕
漏了怎么查 翻 shell 历史 翻执行日志，人肉还原 查一张表：(能力, 出口) 有没有这一行

差别不在功能多少，在「谁掌握图」。 单机 agent 没有图，跑一步算一步；dify / n8n 的图在平台里，节点是平台提供的积木； 这里的图也是显式的，但它由能力定义 + 出口表两层组成，节点只声明自己会哪些能力， 不掌握图长什么样——所以换机器不影响图，加机器也不用改图。

要解决的三件事

每一条都对应一个具体问题，也对应一条必须能验证的设计约束。

一、「为什么没触发」说不清

定时没跑、webhook 丢了、下游没接上，从外面看都是同一个现象：手机没响。这件事被压成了一次查表问答，答案只有四种：表里没有这一行、上游没回报这个出口、参数不符合目标能力的 schema，或者被 path 剪枝。四个都能直接从记录里展示出来，不需要推演。

答案一 · 图的问题

能力 review@1 回报走了出口 fix，但出口表里没有 (review@1, fix) 这一行 —— 所以到这里就是尽头。表里有没有这一行，一眼能查。

答案二 · 行为的问题

表里明明有 (review@1, fix) 这一行，但这次声明 review@1 的那个节点回报的 out 是 null —— 没人走这个出口。不是配置错，是这个节点这一次选择了到头。

答案三 · 参数的问题

边在、出口也对，但 params 过不了目标能力的 params_schema（比如少了必填的 pr）—— 任务压根没建，记 pruned / reason=param_schema。前两个答案要查记录，这一个在派发前就拦住了。

答案四 · 行程的问题

边在、参数也对，但这个能力已经在本次行程的 path 里走过（review → fix → review）—— 静默剪枝，不报错不停链，但 trace 上记 pruned / reason=path，并指出重复的是哪个能力。

四个答案都指向同一件事：不需要跑一遍才能知道原因。参数校验在派发前做，边的存在性在配置期就看得见， 出口回报是节点自己写的，行程是随任务落库的字段——四者都是躺在表里的记录，不是要从日志里推的因果。

二、长任务一断就没了

几十分钟的 agent 通常挂在 tmux 里，电脑一睡、进程一死，什么都没留下，只能从头再来，也没人知道它死在第几步。任务需要有租约和心跳：节点挂了，任务显式落到 failed 或 abandoned（不等于成功，默认通知），该重派的重派，结果按 TTL 留存。

三、凭据被迫放在中枢

要让中枢替你「启动东西」，最省事的做法是把 SSH key、云 token 和一行行命令塞进服务端——等于让一个对公网开放的盒子持有你全部权限。所以反过来：中枢只说做什么和参数，命令与凭据都留在你自己的机器上。

问题 现在的样子 接上事件中心之后
为什么没触发 没有通知，原因未知，只能翻日志 trace 上直接写清是「表里没有 (能力, 出口) 这一行」、「上游没回报出口」还是「参数不符合能力 schema」；因环剪枝另记 pruned
长任务中断 进程没了就没了，下次从头再跑 租约 + 心跳，显式 failed / abandoned，结果按 TTL 留存
凭据在哪 中枢持有密钥，并负责拼命令 argv 只在节点申报，中枢只发能力名 + 版本 + params

我们不是什么

「能做」的清单总会膨胀，所以先把不做的钉死。下面每一条都是主动放弃，不是还没排期。

拖拽画布
画布把一条出口边变成一张需要读懂位置的图，改一行边要点三次；我们让出口表是文本，能进 git、能 diff、能 review。
任意名字当能力
不是。能力定义是白名单：节点只能说「我声明了 review@1」，不能说「我有一个叫 xxx 的能力、带 yy 和 zz 两个出口」。 如果能力名和出口名都由节点自己编，两台机器都叫 review 却报出两套出口，edges 的 from_port 就不再是封闭集合，查表命中却派不出去——这正是「能力必须先定义」要堵的洞。 要新名字，先在中枢定义一个能力。
任意代码执行
一旦中枢能下发任意代码，它就成了执行平台，安全边界不复存在；节点只能声明已定义的能力，命令与 argv 永远留在本机配置里。
中枢存第三方密钥
中枢被攻破不该等于你所有服务的凭据泄漏，所以密钥和 argv 永不上传。
50 个集成
集成数量是维护债，不是价值；一个 webhook 入口加一个命令行出口已经覆盖绝大多数场景。
DAG 校验
我们的图不是运行期拼出来的：它就是一张显式声明的出口表，所以环在配置期就看得见 —— 画得出来，也查得出来，不需要运行期的 DAG 校验。而真实流程本来就该成环（审查 → 修复 → 复审），静态 DAG 会把它直接禁掉；我们允许成环，运行期靠 path 去重剪枝保证终止。

定位

执行能力是手段，不是卖点。卖点是：人能在不翻日志的前提下回答三个问题，而且答案来自记录，不是推断—— 事件为什么触发、走了哪条路、卡在哪一步。三者的答案都直接躺在表里，不必重跑一条链路。

B「可解释的自动化」——事件为什么触发、走了哪条路、卡在哪一步。
