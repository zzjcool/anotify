为什么

这页说三件事：现在的 agent 通知在哪三处断掉，事件中心针对性地补哪三个洞，以及我们刻意不做什么——免得被当成又一个 workflow 引擎。

现状：一条只走一次的单向链

最常见的用法是：本机跑一个 agent，结束时 curl 一下接口，手机收到一条「任务完成」。它能用，但整条链只走一遍，而且每一段都不留痕。

agent 在本机跑完exit 0，没有记录
→
推一条通知一句话：完成了
→
手机震一下人在开会，没看见
→
到此为止无事件、无结果、无下一步
断开点 1 · 干完了没人在场只留一个 exit code
断开点 2 · 长任务没有地方接进程一死，从头再来
断开点 3 · 通知发出去就断了背后没有可查的记录
人盯着屏幕时三处都不明显；任务一多、时长一长、人不在机器前，它们会同时断。本节之后的三小节，就是分别接这三处。

事件中心要解决的三件事

不是为了多接几个集成，而是把上面三处接上。每个洞对应一个具体问题，也对应一条必须能验证的设计约束。

一、「为什么没触发」说不清

定时没跑、webhook 丢了、出口表里没有这条边，从外面看都是同一个现象：手机没响。现在只能翻日志猜是哪一步。事件中心把事件本身和它的路由过程一起记下来。新模型下这个问题只有两个答案，都能直接展示： ① 出口表里没有这一行 —— 图是配置期画好的，所以「没接这条边」在跑之前就能看出来； ② 上游没回报这个出口 —— 上游选了别的出口，或者报了 null。 两种判断都只读一行数据，不需要重新推理。

二、长任务一断就没了

几十分钟的 agent 通常挂在 tmux 里，电脑一睡、进程一死，什么都没留下，只能从头再来，也没人知道它死在第几步。任务需要有租约和心跳：节点挂了，任务显式落到 failed 或 abandoned（不等于成功，默认通知），该重派的重派，结果按 TTL 留存。

三、凭据被迫放在中枢

要让中枢替你「启动东西」，最省事的做法是把 SSH key、云 token 和一行行命令塞进服务端——等于让一个对公网开放的盒子持有你全部权限。所以反过来：中枢只说做什么和参数，命令与凭据都留在你自己的机器上。

问题 现在的样子 接上事件中心之后
为什么没触发 没有通知，原因未知，只能翻日志 直接给两个答案：表里没这行 / 上游没回报这个出口
长任务中断 进程没了就没了，下次从头再跑 租约 + 心跳，显式 failed / abandoned，结果按 TTL 留存
凭据在哪 中枢持有密钥，并负责拼命令 命令只在节点注册，中枢只发命令名 + params

我们不是什么

「能做」的清单总会膨胀，所以先把不做的钉死。下面每一条都是主动放弃，不是还没排期。

拖拽画布
画布把一条边变成一张需要读懂位置的图，改一条边要点三次；我们让路由是一张表，能进 git、能 diff、能 review。
任意代码节点
一旦中枢能下发任意代码，它就成了执行平台，安全边界不复存在；我们只认节点上注册过的能力名。
中枢存第三方密钥
中枢被攻破不该等于你所有服务的凭据泄漏，所以密钥和 argv 永不上传。
50 个集成
集成数量是维护债，不是价值；一个 webhook 入口加一个命令行出口已经覆盖绝大多数场景。
DAG 校验
图是显式声明的出口表，所以环在配置期就看得见，不需要运行期的 DAG 校验器。 而我们允许成环（审查 → 修复 → 复审），终止由 path 能力名去重保证。

所以定位是什么

执行能力是第二层。第一层是：人能在不翻日志的前提下回答三个问题，且答案来自记录而不是推断。

B「可解释的自动化」——事件为什么触发、走了哪条路、卡在哪一步。
