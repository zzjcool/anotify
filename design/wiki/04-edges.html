能力与出口

这一页讲路由。旧模型用「规则 + 条件匹配」，新模型把这一层整个去掉了： 接口先定义，执行器只能实现已定义的接口，出口名由接口给定。 派发就是查一张表——没有条件求值，没有优先级，没有表达式引擎。

四个要素

先把词定住。关键是接口在最上面一层——它规定了「这个能力接受什么参数、可能怎么结束」， 下面三层都受它约束。

接口 interface
一份契约：name@version、角色 kind、参数结构 params_schema、 出口名集合 outputs。出口名只能来自这里，执行器没有命名权。
能力 capability
一台执行器对某个接口的实现。能力 = (runner_id, interface_id)。 它不再自带出口——出口是它实现的那个接口给的。
出口 output
接口定义里的一个命名点。跑完之后执行器选一个。它是字符串，不是条件。
边 edge
(from_interface, from_port) → to_interface。 注意两端都是接口，不是机器——换机器不影响图。
为什么必须有接口这一层。如果出口名由执行器自己编，两台机器实现同一个 review 却报出 [fix, clean] 和 [ok, bad]，edges 里就会出现 (review, fix) 和 (review, ok) 两套起点——查表时不知道该用哪个。 接口把命名权收归中枢，from_port 才是封闭集合。

三种角色，按端口形状分

分类只有一条依据：有没有入口、有没有出口。不看它跑在哪、用什么语言、由谁维护、是不是人。

source · 源入 ✗ · 出 ✓ →
pipe · 管道入 ✓ · 出 ✓ →
end · 终点入 ✓ · 出 ✗
触发器就是「只有出口、没有入边」的角色。它不接任务，只把外部世界的变化转成一次出口选择。
种类 入 出 例子 kind
源 / 触发器 ✗ ✓ GitHub webhook、cron、文件 watch、外部 API origin
管道 ✓ ✓ 机器上的 review / implement / test pipe
终点 ✓ ✗ 推手机、写日志（都是 end） end

没有第四种。任何东西都能落进这三类之一——包括你没想过的那些： 一个审批人点「通过」是 pipe（有进有出）；一个只负责收尾的 webhook 回调是 end。

出口表：路由的唯一依据

中枢不存条件、不跑匹配。它只存一张边表——两端都是接口，不引用任何机器。 

CREATE TABLE edges (
  from_interface TEXT NOT NULL,   -- ifc_...
  from_port      TEXT NOT NULL,   -- 必须是该接口 outputs 里的一个
  to_interface   TEXT NOT NULL,   -- ifc_...
  PRIMARY KEY (from_interface, from_port, to_interface)
);

派发是四步，比之前多一步参数校验： 

-- ① 查表
SELECT to_interface FROM edges
 WHERE from_interface = :ifc AND from_port = :out;
-- 返回 N 行 → N 个下游；0 行 → 到头，记 pruned

-- ② 用目标接口的 schema 校验参数（不通过就不建任务）
-- ③ 找实现了这个接口的执行器
SELECT runner_id FROM capabilities
 WHERE interface_id = :to_interface;

-- ④ 按负载挑一台（或按 sticky 查 runner_pins）
这就是全部的路由逻辑。没有 match 表达式、没有条件树、没有优先级排序、 没有 DSL 解析器。它之所以能这样，是因为图是显式声明的—— 「PR 打开之后要做什么」不再是一条需要求值的规则，而是表里的两三行。

四方怎么声明

顺序很重要：接口先定义，执行器再实现，最后才画边。 执行器从头到尾不知道全图长什么样，也不需要知道。

① 接口：中枢侧定义

接口进 git、走 review，和代码一样可 diff。项目自带一批内置接口，用户可以在自己的配置目录里追加。 

# interfaces/ · 进 git
- name: review
  version: 1
  kind: pipe
  params_schema:                 # 派发前用它校验参数
    type: object
    required: [pr]
    properties:
      pr: { type: integer }
  outputs: [fix, clean]          # ★ 出口名在这里定死

- name: notify.phone
  version: 1
  kind: end
  outputs: []                    # 终点，没有出口

- name: github
  version: 1
  kind: origin                  # 触发器也走接口
  outputs: [pr_opened, pr_merged]

② 执行器：只写「实现了哪个接口」

# ~/.anotifyd/config.yaml · 执行器本地
runner: mbp-16
kind: pipe
capabilities:
  - implements: review@1        # ★ 不再自己写 outputs
    argv: ["git", "diff", "--name-only"]
  - implements: implement@1
    argv: ["./agent.sh"]
执行器没有出口命名权。它只能声明「我实现了 review@1」， 出口集合 {fix, clean} 是接口给的。 而且不允许只实现一部分——实现 review@1 就必须两个出口都能走， 否则 edges 里会出现「查到了边但这台机器没有这个出口」的分叉。

③ 边：中枢侧配置

# 边在接口之间，不引用机器
edges:
  - from: origin:github
    port: pr_opened
    to: [review@1, notify.phone@1]   # 一个出口两条边 → 扇出
  - from: review@1
    port: fix
    to: [implement@1]

④ 执行器实际收到什么

只有接口名、版本和参数——没有 argv，没有图，也没有「下一步是谁」。 

{
  "task": "tsk_8f21a3c0",
  "implements": "review",
  "version": 1,
  "params": { "pr": 431 }
}

版本：两个版本就是两个接口

review@1 和 review@2 是两个不同的接口，可以同时存在。 旧机器继续实现 @1，新机器实现 @2，edges 里各有一条边。

版本并存（选这个） 强制全量升级
升级期 旧接口继续跑，不中断 全网停机到全部升级完
代价 图里同名接口出现两个版本，控制台必须显式显示版本号 无
清理 旧版本没人实现后，删掉它的边即可 —

所以展示时不能只写 review——必须写 review@1 或 review@2， 否则看不出走的是哪条边。

运行时：执行器跑完才选出口

出口不能提前定，因为命令还没跑，谁也不知道会走到哪。 成功要跑完才知道，失败也要跑完才知道。所以它出现在 result 里。 

// 执行器回报的 result（≤8KB）
{
  "status": "succeeded",
  "out": "fix",              // ★ 我选了 fix 这个出口
  "summary": "发现 2 处类型错误",
  "artifacts": ["diff.patch"]
}

{
  "status": "failed",
  "out": null,               // ★ 失败，且这条线到我为止
  "error": "build exited 1"
}

out 一个字段同时表达两件事：有没有下游（null = 没有）、 有哪个下游（"fix" = 走这条边）。它和 status 正交：

status out 含义
succeeded "fix" 干完了，往下走
succeeded null 干完了，到头了
failed "fix" 失败，但触发了修复分支
failed null 失败且断在这里

第二行和第四行是「这条线结束」；第一行和第三行会继续。 注意失败也能继续——失败本身可能就是下一跳的起点，中枢不判断该不该。

可解释性：比之前更强

旧模型要回答「为什么没触发」，得逐条件求值、记录每个条件的 passed/failed。 新模型只需要看两个地方。

问题 答案 怎么展示
为什么没有下一个任务？ edges 里没有 (能力, 出口) 这一行 直接高亮「表里无此行」，不需要推理
为什么走了这条边？ 上游回报了 out = 这个出口 把上游的 result.out 和边放在一起
为什么另一条边没走？ 上游回报的 out 不是它 标出上游实际选的出口

这三种都能在跑之前静态展示。旧模型要解释「某个条件为什么是 false」， 往往得重跑一次；新模型只是「表里有没有这一行」。

环：配置期就看得见

图是显式声明出来的，所以环不需要等到运行时才发现——它在 edges 表里就是几条首尾相接的行。 而且环是允许的：审查 → 修复 → 复审 是真实场景。

reviewout: fix →
implementout: verify →
reviewpath 已含 → 剪枝
第二次回到 review 时剪枝——不报错、不暂停 trace，但这笔要留在 trace 上看得见。
行程 path
从根到本任务这条具体路径的能力名序列，不是整个 trace 见过的集合。两条分支的 path 互不影响。
剪枝 pruned
path 里已有该能力 → 不建任务。静默但不隐形成：trace 上记 pruned + 原因。
为什么必然终止
path 去重保证路径最长 = 图里的能力数。max_hops 只是这个上界的外显配置，不是唯一防线。
