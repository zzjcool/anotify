能力与出口

这一页讲路由。旧模型用「规则 + 条件匹配」，新模型把这一层整个去掉了： 一切参与流转的东西都是节点，节点申报能力，能力带出口， 派发就是查一张表。没有条件求值，没有优先级，没有表达式引擎。

三个要素

先把词定住。后面所有页面都只用这三个词描述结构。

节点 node
参与流转的一个实体。可以是一台机器、一个 webhook、一个收通知的手机。
能力 capability
节点申报的「我能做什么」。路由的单位是能力，不是机器——同一台机器可以申报很多个能力。
出口 output
能力的命名出口。跑完之后节点选择走哪个出口。出口是字符串，不是条件。

三种节点，按端口形状分

分类只有一条依据：有没有入口、有没有出口。不看它跑在哪、用什么语言、由谁维护、是不是人。

source · 源入 ✗ · 出 ✓ →
worker · 工作节点入 ✓ · 出 ✓ →
sink · 终端入 ✓ · 出 ✗
触发器就是「只有出口、没有能力」的节点。它不接任务，只把外部世界的变化转成一次出口选择。
种类 入 出 例子 kind
源 / 触发器 ✗ ✓ GitHub webhook、cron、文件 watch、外部 API source
工作节点 ✓ ✓ 机器上的 review / implement / test worker
终端 / 叶子 ✓ ✗ 推手机（human sink）、写日志 sink

没有第四种。任何东西都能落进这三类之一——包括你没想过的那些： 一个审批人点「通过」是 worker（有入有出）；一个只负责收尾的 webhook 回调是 sink。

出口表：路由的唯一依据

中枢不存条件、不跑匹配。它只存一张边表。 

CREATE TABLE edges (
  from_capability TEXT NOT NULL,   -- 谁产的
  from_port       TEXT NOT NULL,   -- 走了哪个出口
  to_capability   TEXT NOT NULL,   -- 下一个能力
  PRIMARY KEY (from_capability, from_port, to_capability)
);

派发就是一次索引查询。返回几行，就派几个任务： 

SELECT to_capability FROM edges
 WHERE from_capability = :cap
   AND from_port = :port;

-- 返回 N 行 → 派 N 个任务（全部下发，不是择一）
-- 返回 0 行 → 这条线到此为止，记 pruned + 原因
这就是全部的路由逻辑。没有 match 表达式、没有条件树、没有优先级排序、 没有 DSL 解析器。它之所以能这样，是因为图是显式声明的—— 「PR 打开之后要做什么」不再是一条需要求值的规则，而是表里的两三行。

三方怎么声明

节点在本地配置文件里申报自己的能力与出口，这些事实被上报到中枢， 中枢把它们拼成 edges 表。节点看不到全图，也不需要看。

source：只有出口

# ~/.anotifyd/config.yaml · 触发器节点
node: gh-webhook
kind: source
emits:
  pr_opened:
    to: [review, notify.phone]   # 一个出口通向两个能力 → 扇出
  pr_merged:
    to: [notify.phone]

中枢只收到「source:github 的 pr_opened 通向 review 和 notify.phone」 这个事实，收不到任何 webhook 解析逻辑。

worker：有进有出

# 工作节点
node: mbp-16
kind: worker
capabilities:
  - name: review
    argv: ["git", "diff", "--name-only"]
    outputs: [fix, clean]        # 我可能往哪走
  - name: implement
    argv: ["./agent.sh"]
    outputs: [verify]
outputs 是「我会用到的出口名」，不是「我会去哪」。 这一点很容易读错。review 知道自己在两种情况下会走 fix 或 clean， 但它不知道 fix 后面接谁——那是中枢 edges 表的事。 节点不该知道图长什么样。这就是「中枢不下发命令」的同一条原则。

sink：只有入口

# 终端节点
node: my-phone
kind: sink
capabilities:
  - name: notify.phone
    outputs: []                  # 没有出口

运行时：节点跑完才选出口

出口不能提前定，因为命令还没跑，谁也不知道会走到哪。 成功要跑完才知道，失败也要跑完才知道。所以它出现在 result 里。 

// 节点回报的 result（≤8KB）
{
  "status": "succeeded",
  "out": "fix",              // ★ 我选了 fix 这个出口
  "summary": "发现 2 处类型错误",
  "artifacts": ["diff.patch"]
}

{
  "status": "failed",
  "out": null,               // ★ 失败，且这条线到我为止
  "error": "build exited 1"
}

out 一个字段同时表达两件事：有没有下游（null = 没有）、 有哪个下游（"fix" = 走这条边）。它和 status 正交：

status out 含义
succeeded "fix" 干完了，往下走
succeeded null 干完了，到头了
failed "fix" 失败，但触发了修复分支
failed null 失败且断在这里

第二行和第四行是「这条线结束」；第一行和第三行会继续。 注意失败也能继续——失败本身可能就是下一跳的起点，中枢不判断该不该。

可解释性：比之前更强

旧模型要回答「为什么没触发」，得逐条件求值、记录每个条件的 passed/failed。 新模型只需要看两个地方。

问题 答案 怎么展示
为什么没有下一个任务？ edges 里没有 (能力, 出口) 这一行 直接高亮「表里无此行」，不需要推理
为什么走了这条边？ 上游回报了 out = 这个出口 把上游的 result.out 和边放在一起
为什么另一条边没走？ 上游回报的 out 不是它 标出上游实际选的出口

这三种都能在跑之前静态展示。旧模型要解释「某个条件为什么是 false」， 往往得重跑一次；新模型只是「表里有没有这一行」。

环：配置期就看得见

图是显式声明出来的，所以环不需要等到运行时才发现——它在 edges 表里就是几条首尾相接的行。 而且环是允许的：审查 → 修复 → 复审 是真实场景。

reviewout: fix →
implementout: verify →
reviewpath 已含 → 剪枝
第二次回到 review 时剪枝——不报错、不暂停 trace，但这笔要留在 trace 上看得见。
行程 path
从根到本任务这条具体路径的能力名序列，不是整个 trace 见过的集合。两条分支的 path 互不影响。
剪枝 pruned
path 里已有该能力 → 不建任务。静默但不隐形成：trace 上记 pruned + 原因。
为什么必然终止
path 去重保证路径最长 = 图里的能力数。max_hops 只是这个上界的外显配置，不是唯一防线。
