能力与出口

这一页讲路由。旧模型用「规则 + 条件匹配」，新模型把这一层整个去掉了： 能力必须先定义，节点只能声明自己有哪些已定义的能力。 派发就是查一张表——没有条件求值，没有优先级，没有表达式引擎。

三个要素

先把词定住。能力是最小单位——一个动作、一条命令、一组可能的出口。 下面所有结构都建立在它之上。

能力定义 capability
中枢提前写好的一份定义：name@version、参数结构 params_schema、 出口名集合 outputs。出口名只能来自这里，节点没有命名权。
它就是最小的原子：一个能力定义一条命令，不能再分。
节点 node
一台声明了能力的机器。它只说「我有 review@1」， 不能自己发明能力名，也不能自己加出口。
出口 output
能力定义里允许报出的几个名字之一，跑完之后节点选一个报出来。 它是字符串，不是条件。
出口名就是一个能力名——报出 fix，就是要求中枢去派 fix 这个能力。所以 fix / clean 各自是独立的能力定义，各带自己的版本，各自被不同节点声明。

为什么能力必须先定义。如果能力名和出口名都由节点自己编，两台机器都叫 review 却报出 [fix, clean] 和 [ok, bad]，edges 里就会出现 (review, fix) 和 (review, ok) 两套起点——查表时不知道该用哪个。 定义权归中枢，from_port 才是封闭集合。

出口名就是下一个能力的名字

这是整个模型里最容易被想歪的一点。fix 不是一个「子结果」，它就是 fix 这个能力的名字。 

# 三个独立的能力，各有各的版本，互不包含
- name: review      # 跑完报出「我接下来要 fix」或「我接下来要 clean」
  version: 1
  outputs: [fix, clean]

- name: fix         # ★ 它自己就是一个能力，有人认领它
  version: 1
  params_schema:
    type: object
    required: [diff]
  outputs: [verify]

- name: clean       # ★ 另一个能力，另一个版本
  version: 1
  outputs: []

所以路由查的是：review@1 报出 fix → 派 fix@1 这个能力 → 找声明了 fix@1 的节点。 不存在「先找 review 这台机器」这回事——review 只负责报出口，之后它的事就完了。

错误理解 正确理解
outputs: [fix, clean] review 包含 fix 和 clean 两个子功能
→ 所以声明 review 就得全实现		 review 跑完可以报出 fix 或 clean
→ fix / clean 是别人的能力，跟 review 的实现无关
版本属于谁 版本属于 review，fix 跟着 review 的版本走 每个能力各有版本：review@1、fix@2、clean@1 互不相干
派发时找谁 找声明了 review 的节点 review 已经跑完了；找声明了 fix@1 的节点
能不能只做一半 不可以，必须 fix 和 clean 都能走 可以——review 只报名字，它不需要「实现」fix。谁实现 fix 是 fix 自己的事

三种节点，按端口形状分

分类只有一条依据：有没有入口、有没有出口。不看它跑在哪、用什么语言、由谁维护、是不是人。

origin · 源头入 ✗ · 出 ✓ →
pipe · 管道入 ✓ · 出 ✓ →
end · 终点入 ✓ · 出 ✗
触发器就是「只有出口、没有入边」的位置。它不接任务，只把外部世界的变化转成一次出口选择。
种类 入 出 例子 kind
源 / 触发器 ✗ ✓ GitHub webhook、cron、文件 watch、外部 API origin
管道 ✓ ✓ 机器上的 review / implement / test pipe
终点 ✓ ✗ 推手机 notify.phone@1、写日志 log@1、webhook 回调 notify.webhook@1 end

没有第四种。任何东西都能落进这三类之一——包括你没想过的那些： 一个审批人点「通过」是 pipe（有进有出）；一个只负责收尾的 webhook 回调是 end。

kind 是算出来的，不是写上去的

kind 从来不写进配置。它由节点声明的能力自动推导—— 「有没有入」看它有没有被别的节点指向；「有没有出」看它声明的能力有没有非空 outputs。 

// 由节点的能力声明推导，不手写
kind(node) =
  all outputs 为空        → end      // 只有入：推手机 / 写日志 / 回调 / 归档
  some outputs 非空       → pipe     // 有进有出：review / implement
  没有任何节点声明它        → origin   // 只有出：触发器，事件本身充当起点
节点声明的能力 推导出的 kind 为什么
[notify.phone]，outputs 全为空 end 能接任务，但跑完没有下一跳
[review]，outputs: [fix, clean] pipe 能接任务，跑完还能往下走
[review, notify.phone] 混挂 pipe 只要有一个能力带出口，这个节点就还能往下走
没有节点声明（如 github） origin 没人实现它，事件本身是链的起点

推导的好处：不可能出现自相矛盾的配置。 如果 kind 要手写，就会有人标了 end 却挂上一个带出口的能力， 然后指望校验期拦住他。让它是算出来的，这种配置根本表达不出来。

出口表：路由的唯一依据

中枢不存条件、不跑匹配。它只存一张边表——两端都是能力定义，不引用任何机器。 

CREATE TABLE edges (
  from_capability TEXT NOT NULL,   -- cap_...
  from_port       TEXT NOT NULL,   -- 必须是该能力 outputs 里的一个
  to_capability   TEXT NOT NULL,   -- cap_...
  PRIMARY KEY (from_capability, from_port, to_capability)
);

派发是四步，比之前多一步参数校验： 

-- ① 查表
SELECT to_capability FROM edges
 WHERE from_capability = :cap AND from_port = :out;
-- 返回 N 行 → N 个下游；0 行 → 到头，记 pruned

-- ② 用目标能力的 schema 校验参数（不通过就不建任务）
-- ③ 找声明了这个能力的节点
SELECT node_id FROM node_capabilities
 WHERE capability_id = :to_capability;

-- ④ 按负载挑一台（或按 sticky 查 node_pins）
这就是全部的路由逻辑。没有 match 表达式、没有条件树、没有优先级排序、 没有 DSL 解析器。它之所以能这样，是因为图是显式声明的—— 「PR 打开之后要做什么」不再是一条需要求值的规则，而是表里的两三行。

三方怎么声明

顺序很重要：能力先定义，节点再声明自己有哪些，最后才画边。 节点从头到尾不知道全图长什么样，也不需要知道。

① 能力：中枢侧提前定义

能力定义进 git、走 review，和代码一样可 diff。项目自带一批内置能力，用户可以追加自己的。 注意这里没有 kind——它不属于能力。 

# capabilities/ · 进 git · 一份定义 = 一个原子能力
- name: review
  version: 1
  params_schema:                 # 派发前用它校验参数
    type: object
    required: [pr]
    properties:
      pr: { type: integer }
  outputs: [fix, clean]          # ★ 跑完可能走这两个结局之一

- name: notify.phone
  version: 1
  outputs: []                    # 没有出口 = 到头

- name: github
  version: 1
  outputs: [pr_opened, pr_merged]  # 触发器也是一种能力定义

② 节点：只声明「我有哪些能力」

# ~/.anotifyd/config.yaml · 节点本地
node: mbp-16
# 没有 kind —— 它由下面这份声明推导
capabilities:
  - review@1                      # ★ 只能从已定义的清单里挑
    argv: ["git", "diff", "--name-only"]
  - implement@1
    argv: ["./agent.sh"]
节点没有定义权。它不能发明能力名，也不能加出口——两者都来自中枢的定义。
但它也不需要「实现」自己报出的那些出口：review 声明 outputs: [fix, clean]， 意思只是「跑完我会报这两个名字之一」，不是「我得把 fix 和 clean 都做出来」。 fix 由谁做，是 fix 这个能力自己的事，由别的节点声明。

③ 边：中枢侧配置

# 边在能力之间，不引用任何机器
edges:
  - from: origin:github
    port: pr_opened
    to: [review@1, notify.phone@1]   # 一个出口两条边 → 扇出
  - from: review@1
    port: fix                          # 出口名 = 要把活派给谁
    to: [fix@1]

节点实际收到什么

只有能力名、版本和参数——没有 argv，没有图，也没有「下一步是谁」。 

{
  "task": "tsk_8f21a3c0",
  "capability": "review",
  "version": 1,
  "params": { "pr": 431 }
}

版本：两个版本就是两个能力

review@1 和 review@2 是两个不同的能力定义，可以同时存在。 旧节点继续声明 @1，新节点声明 @2，edges 里各有一条边。

版本并存（选这个） 强制全量升级
升级期 旧版本继续跑，不中断 全网停机到全部升级完
代价 图里同名能力出现两个版本，控制台必须显式显示版本号 无
清理 旧版本没有节点声明后，删掉它的边即可 —

所以展示时不能只写 review——必须写 review@1 或 review@2， 否则看不出走的是哪条边。

运行时：节点跑完才选出口

出口不能提前定，因为命令还没跑，谁也不知道会走到哪。 成功要跑完才知道，失败也要跑完才知道。所以它出现在 result 里。 

// 节点回报的 result（≤8KB）
{
  "status": "succeeded",
  "out": "fix",              // ★ 我选了 fix 这个出口
  "summary": "发现 2 处类型错误",
  "artifacts": ["diff.patch"]
}

{
  "status": "failed",
  "out": null,               // ★ 失败，且这条线到我为止
  "error": "build exited 1"
}

out 一个字段同时表达两件事：有没有下游（null = 没有）、 有哪个下游（"fix" = 走这条边）。它和 status 正交：

status out 含义
succeeded "fix" 干完了，往下走
succeeded null 干完了，到头了
failed "fix" 失败，但触发了修复分支
failed null 失败且断在这里

第二行和第四行是「这条线结束」；第一行和第三行会继续。 注意失败也能继续——失败本身可能就是下一跳的起点，中枢不判断该不该。

可解释性：比之前更强

旧模型要回答「为什么没触发」，得逐条件求值、记录每个条件的 passed/failed。 新模型只需要看两个地方。

问题 答案 怎么展示
为什么没有下一个任务？ edges 里没有 (能力, 出口) 这一行 直接高亮「表里无此行」，不需要推理
为什么走了这条边？ 上游回报了 out = 这个出口 把上游的 result.out 和边放在一起
为什么另一条边没走？ 上游回报的 out 不是它 标出上游实际选的出口

这三种都能在跑之前静态展示。旧模型要解释「某个条件为什么是 false」， 往往得重跑一次；新模型只是「表里有没有这一行」。

环：配置期就看得见

图是显式声明出来的，所以环不需要等到运行时才发现——它在 edges 表里就是几条首尾相接的行。 而且环是允许的：审查 → 修复 → 复审 是真实场景。

reviewout: fix →
implementout: verify →
reviewpath 已含 → 剪枝
第二次回到 review 时剪枝——不报错、不暂停 trace，但这笔要留在 trace 上看得见。
行程 path
从根到本任务这条具体路径的能力名序列，不是整个 trace 见过的集合。两条分支的 path 互不影响。
剪枝 pruned
path 里已有该能力 → 不建任务。静默但不隐形成：trace 上记 pruned + 原因。
为什么必然终止
path 去重保证路径最长 = 图里的能力数。max_hops 只是这个上界的外显配置，不是唯一防线。
