核心概念

整份文档只用五个名词：Node、Capability、Output、Task、Trace。这页把每个名词钉死——它是什么、长什么样、举一个具体例子——然后画一张图说明它们怎么串起来。没有条件求值，也没有优先级：派发只是查一张表。

五个名词

五个词各自回答一个问题：谁在场（Node）、谁会干什么（Capability）、干完往哪走（Output）、这一趟待办本身（Task）、这整趟是怎么走的（Trace，行程）。括号里是代码原名。

Node node
参与流转的一个实体，带一个 kind：origin / pipe / end。它在自己机器上的 config.yaml 里申报自己是谁、会什么。
例：runner: mbp-16、kind: pipe，下挂 review 与 implement 两个能力；另一台 runner: my-phone、kind: end。
Capability capability
能力是执行器申报的「我能做什么」。路由的单位是能力，不是机器：派出去的是 review，至于落到哪台机器，由执行器池按负载挑。
例：name: review，带一段本机的 argv；中枢只认这个名字，不知道命令内容。
Output output / port
能力的命名出口，一个可以指认的点，跑完之后才由执行器选一个。能力声明里的 outputs 是「我会用到的出口名」，不是「我会去哪」——去哪由中枢的出口表决定，执行器不该知道图长什么样。
例：review 声明 outputs: [fix, done]；这次跑完它回报 out: "fix"，就意味着它选了那个叫 fix 的出口。
Task task
查表查到一条边之后落地的一行待办，带租约和状态机；它是「谁去做、做到哪一步」的唯一载体。
例：task_id=8f21，能力 review，参数 {pr: 431}，状态依次 pending → assigned → acked → running。
Trace trace_id · 行程
一趟行程：从最初那个事件到最后一条任务的完整因果链，事件、每次查表、每个任务的回报都挂在同一个 trace_id 下。这次行程具体走过哪些能力，记在 path 上——从根到本任务这条具体路径的能力名序列，用来做去重剪枝。
例：trace=tr_7c1a，跑到 review → implement，那么 implement 这个任务走的行程是 path = [review, implement]。

五个词的关系是一句套娃：执行器申报能力，能力带出口，出口经一条边指向下一个能力，一次派发落成一个任务，整趟行程是一条 trace。所以系统里唯一需要被推理的东西只剩「查表」，其余都是记录。

角色有三种，按端口形状分

分类的依据不是「这东西有多重要」，而是它的端口形状：有没有入口、有没有出口。origin 只有出，pipe 有进有出，end 只有入。

源 · source有出 · 无入
→
pipe · 管道有进 · 有出
→
end · 终点有进 · 无出
入在左，出在右。一个角色最多两类端口，所以它必定落进上面三种形状之一。链的最左边只能是 origin，最右边只能是 end——中间想再插什么，都得是 pipe。
种类 入 出 能力 例子 kind
源 · 触发器 ✗ ✓ 不申报能力，边的起点用事件类型充当 GitHub webhook、cron、watch、外部 API 轮询 origin
管道 ✓ ✓ 申报 capabilities，每个带自己的 outputs 机器上的 review / implement / test pipe
终端 · 叶子 ✓ ✗ 申报 capabilities，outputs 为空 推手机 notify.phone、写归档日志 end
没有第四种。任何参与流转的东西都能被这三类装下：定时器是源，CI 里的一个步骤是管道，企业微信机器人是终端。所以中枢不必为「新类型实体」写新代码，只读它的 kind 和它申报的能力。
触发器就是「只有出口、没有入边的角色」。它不申报能力，所以边的起点由事件类型充当：origin:github --(pr_opened)--> review。

一条链是怎么连起来的

整条链只有一个形状：源出一件事件，用事件类型当出口查一次表，落到一个能力上；能力跑完选一个出口，再查一次表。中间可以插任意多个 pipe，两头分别是 origin 和 end。连起来的整条因果链，就是一条 Trace。

   (implement,          done)       →  notify.phone
edges 表是中枢侧唯一的路由依据。中间那几个虚线框是出口，也是表里的 from_port。中枢不看执行器上的代码、不解释出口的业务含义，只把（能力, 出口）这一对填进表里查一次——图是画给人看的，跑的永远是这张表。

一个出口可以有多条边

表里同一个（能力, 出口）可以有多行，那就是扇出。返回 N 行就派 N 个任务，全部下发，不是择一；返回 0 行就是到头，理由是「表里没有这一行」。

review这次走了出口 fix
implement(review, fix) 的第 1 行
notify.phone(review, fix) 的第 2 行
扇出，不收集。两条边都成立，所以建两个任务、trace 在这里分叉——没有优先级，也不需要挑一个，一次查表返回多行就往多下走。反过来「等这组任务都回来再继续」本期不做——那件事放在执行器内部自己并行、自己汇总。任务回报的出口本身可以再查表，那就是接力。

一次旅程（文字版）

把上面的名词按时间排一遍，就是一次完整的调用。完整的时序图在下一页，这里先记住四步。

事件入库
触发源发来一次调用（或者 cron 到点），中枢把它存成一行 event：source、type、payload、trace_id、span_id。入库即完成，之后的一切都基于这条记录，不基于原始请求。
查出口表
拿（源标识, 事件类型）这一对去 edges 表查一次：from_capability 用事件源充当、from_port 用事件类型充当。查表只有一次索引查询——没有条件求值、没有优先级、也不是择一。返回 N 行，就是 N 个下游能力，全部都要派；返回 0 行就到此为止，理由写清楚是「表里没有这一行」。
任务派发
每个下游能力建一个 task，按能力名挑一台声明过它的执行器，带租约下发。中枢只发能力名和参数，执行器用自己注册的 argv 执行。执行器 acked 表示接单，随后 running，心跳持续续租。
结果回流
执行器回报 status 与 out。中枢拿（这个能力, 这个 out）再查一次表：有边就建下一个任务，没边就在这里走到头。同一条 trace 不换 trace_id。每个任务各自到头，通知走图里那条边，不需要等整条链结束。
