核心概念

整份文档只用六个名词：Capability、Output、Node、Task、Trace、Edge。这页把每个名词钉死——它是什么、长什么样、举一个具体例子——然后画一张图说明它们怎么串起来。没有条件求值，也没有优先级：派发只是查一张表。

六个名词

六个词各自回答一个问题：中枢提前定义了什么动作（Capability）、干完能不能往下走、往哪走（Output）、谁来做（Node）、这一趟待办本身（Task）、这整趟是怎么走的（Trace）、下一跳是谁（Edge）。括号里是代码原名。 能力排第一，因为它是最小单位——其余五个词都绕着它转。

Capability capability · 能力
中枢提前定义的一个动作：name@version、参数结构 params_schema、出口名集合 outputs。定义进 git、走 review、版本化，和代码一样可 diff。
它是这个系统的最小单位，不包含其它能力。review 是一个能力；fix / clean 是它跑完后可能的两个结局，不是两个能力。
来源两种：内置能力（随项目发布，项目维护）与自定义能力（中枢配置目录里用户自己加），同一套格式、同一套版本化，加载后没有区别。
例：review@1，params_schema 要求一个整数 pr，outputs: [fix, clean]。
Output output · 出口
能力定义里的一个命名点，一个可以指认的字符串，不是条件；跑完之后才由节点选一个。
出口名只能来自能力定义，节点没有命名权——两台节点声明同一个 review@1，出口集合必然一样。路由的原子坐标是 (能力, 出口)。
例：review@1 的出口是 {fix, clean}；这次跑完节点回报 out: "fix"，就意味着它选了那个叫 fix 的出口。
Node node · 节点
一台声明了能力的机器。它只说「我有 review@1」，不能自己发明能力名，也不能自己加出口；声明里只有能力名和一段本机的 argv。
它没有 kind 字段——kind 由它声明的能力推导出来（origin / pipe / end），见下一节。
例：node: mbp-16 声明 review@1 和 implement@1，各带一段本机 argv；中枢只记「这台机器有这两个能力」，不知道命令内容。
Task task
查表查到一条边之后落地的一行待办，带租约和状态机；它是「谁去做、做到哪一步」的唯一载体，载荷里只有能力名、版本和参数。
例：tsk_8f21a3c0，能力 review@1，参数 {pr: 431}，状态依次 pending → assigned → acked → running。
Trace trace_id · 行程
一趟行程：从最初那个事件到最后一条任务的完整因果链，事件、每次查表、每个任务的回报都挂在同一个 trace_id 下。这次行程具体走过哪些能力，记在 path 上——从根到本任务这条具体路径的能力名序列，用来做去重剪枝。
例：trace=tr_7c1a，跑到 review@1 → implement@1，那么 implement 这个任务走的行程是 path = [review@1, implement@1]。
Edge edges · 边
能力到能力的一条边：from_capability + from_port → to_capability。两端都是能力定义，不引用任何机器——换一台节点声明同一个能力，表一个字都不用改。
它是唯一的路由依据：没有条件、没有优先级、没有表达式。查表返回 N 行，就派 N 个任务。
例：(review@1, fix) → implement@1 是表里的一行。

六个词的关系是一句套娃：中枢先定义能力，节点再声明自己有哪些已定义的能力，能力里那个出口经一条边指向下一个能力，一次派发落成一个任务，整趟行程是一条 trace。出口名、参数结构、谁能声明，全在能力定义里定死了，所以系统里唯一需要被推理的东西只剩「查表」，其余都是记录。

箭头就是动词。中枢先定义能力，节点再声明自己有哪些已定义的能力，边只在能力之间连。图只认能力，不认机器——换一台机器声明同一个能力，图一个字都不用改。只有这三层，中间没有别的层：kind 不属于任何一层，它是从节点的能力声明里算出来的。

三种节点

按端口形状分，只有三种。kind 不写，由节点的能力声明推导： 有非空出口 → pipe，出口全空 → end，没有任何节点声明它 → origin。 04 能力与出口 有完整的推导规则。

种类 入 出 例子 kind
源 · 触发器 ✗ ✓ GitHub webhook、cron、文件 watch、外部 API origin
管道 ✓ ✓ 节点上的 review@1 / implement@1 / test@1 pipe
终点 ✓ ✗ notify.phone@1、log@1、notify.webhook@1 end

没有第四种。链的最左边只能是 origin，最右边只能是 end，中间插什么都是 pipe。

一条链是怎么连起来的

整条链只有一个形状：触发器出一件事件，用事件类型当出口查一次表，落到一个能力上；某个声明了这个能力的节点接单，跑完选一个出口，再查一次表。中间可以插任意多个 pipe 位置，两头分别是 origin 和 end。连起来的整条因果链，就是一条 Trace。

这些名字全是能力，不是机器。图里没有一个节点——机器在后面：能力要由某个节点声明才跑得起来，换一台节点声明同一个能力，图也不用改。edges 表是中枢侧唯一的路由依据：它不看节点上的代码、不解释出口的业务含义，只把（能力, 出口）这一对填进表里查一次——图是画给人看的，跑的永远是这张表。

出口名为什么必须由能力定义给定

如果出口名让节点自己编，两台机器都声明 review 却报出 [fix, clean] 和 [ok, bad]，edges 里于是出现 (review, fix) 和 (review, ok) 两套起点——查表时不知道该用哪个，边的唯一性没了。所以定义权归中枢，from_port 才是封闭集合；节点只负责说「我有 review@1」，以及跑完从定义给定的那几个出口里选一个。

一个版本就是一个能力

review@1 和 review@2 是两个不同的能力定义，可以并存：旧节点继续声明 @1，新节点声明 @2，edges 里各有一条边，升级期不必全网停机。代价是图里同名能力会出现两个版本，所以展示时不能只写 review，必须带版本号，否则看不出走的是哪条边。

而且它不需要「实现」自己报出的出口。outputs: [fix, clean] 只是说「跑完会报这两个名字之一」——fix 和 clean 各自是独立的能力定义，各带自己的版本，由别的节点声明。review 报出 fix，中枢就去派 fix@1 这个能力，不会回头找 review。

一个出口可以有多条边

表里同一个（能力, 出口）可以有多行，那就是扇出。返回 N 行就派 N 个任务，全部下发，不是择一；返回 0 行就是到头，理由是「表里没有这一行」。

review@1这次走了出口 fix
fix@1(review@1, fix) 的第 1 行 → 派 fix 能力
notify.phone@1(review@1, fix) 的第 2 行
扇出，不收集。两条边都成立，所以建两个任务、trace 在这里分叉——没有优先级，也不需要挑一个，一次查表返回多行就往多下走。反过来「等这组任务都回来再继续」本期不做——那件事放在节点内部自己并行、自己汇总。任务回报的出口本身可以再查表，那就是接力。

一次旅程（文字版）

把上面的名词按时间排一遍，就是一次完整的调用。完整的时序图在下一页，这里先记住四步。

事件入库
触发源发来一次调用（或者 cron 到点），中枢把它存成一行 event：source、type、payload、trace_id、span_id。入库即完成，之后的一切都基于这条记录，不基于原始请求。
查表 → 校验参数 → 找节点 → 挑一台
拿（触发器那个能力, 出口）这一对去 edges 表查一次：from_capability 是触发器那个能力、from_port 是事件类型。查表只有一次索引查询——没有条件求值、没有优先级、也不是择一。返回 N 行，就是 N 个下游能力，全部都要派；返回 0 行就到此为止，理由写清楚是「表里没有这一行」。
拿到的每个下游能力再走四步（派发全貌在 第 04 页）： ① 查表得 to_capability → ② 用这个能力的 params_schema 校验参数（不通过就记 pruned、reason=param_schema，不建任务）→ ③ 找声明了这个能力的节点（查 node_capabilities 里 capability_id 等于它的行；一台都没声明就保持 pending 排队，不算错）→ ④ 按负载挑一台（或按 sticky 查 node_pins）建任务。
任务派发
每个下游能力建一个 task，带租约下发给选中的那台节点。中枢只发能力名、版本和参数——不发 argv、不发图、不说下一步是谁；节点用自己本地的 argv 执行。节点 acked 表示接单，随后 running，心跳持续续租。
结果回流
节点回报 status 与 out。中枢拿（这个能力, 这个 out）再查一次表：有边就建下一个任务，没边就在这里走到头。同一条 trace 不换 trace_id。每个任务各自到头，通知走图里那条边，不需要等整条链结束。
