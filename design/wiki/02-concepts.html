核心概念

整份文档只用六个名词：Interface、Capability、Output、Task、Trace、Node。这页把每个名词钉死——它是什么、长什么样、举一个具体例子——然后画一张图说明它们怎么串起来。没有条件求值，也没有优先级：派发只是查一张表。

六个名词

六个词各自回答一个问题：契约是什么（Interface）、哪台机器实现了它（Capability）、干完往哪走（Output）、这一趟待办本身（Task）、这整趟是怎么走的（Trace，行程）、它站在链的哪一端（Node）。括号里是代码原名。

Interface interface · 接口
一份契约：中枢侧定义、进 git、走 review、版本化。里面钉死四样东西——name@version（如 review@1）、节点类型 kind（origin / pipe / end）、参数结构 params_schema（JSON Schema，派发前校验）、出口名集合 outputs。出口名只能来自这里，执行器没有命名权。
来源两种：内置接口 builtin（interfaces/builtin/，随项目发布，项目维护）与自定义接口 custom（中枢配置目录里用户自己加），同一套格式、同一套版本化，加载后没有区别。
例：review@1，kind: pipe，params_schema 要求一个整数 pr，outputs: [fix, clean]。
Capability capability · 能力
不是「我能做什么」，而是某台机器对某个接口的实现：能力 = (runner_id, interface_id)。它不自带出口——出口是它实现的那个接口给的。
路由的单位是接口，不是能力：中枢派出去的是「谁来实现 review@1」，落到哪台机器由执行器池按负载挑。而且必须整份实现——实现 review@1 就得 fix 和 clean 两个出口都能走。
例：runner: mbp-16 声明 implements: review@1，带一段本机的 argv；中枢只记 (mbp-16, review@1)，不知道命令内容。
Output output · 出口
接口定义里的一个命名点，一个可以指认的字符串，不是条件；跑完之后才由执行器选一个。
它是接口给的，不是执行器编的——两台机器实现同一个 review@1，出口集合必然一样。去哪仍由中枢的边表决定，执行器不该知道图长什么样。
例：review@1 的出口是 {fix, clean}；这次跑完它回报 out: "fix"，就意味着它选了那个叫 fix 的出口。
Task task
查表查到一条边之后落地的一行待办，带租约和状态机；它是「谁去做、做到哪一步」的唯一载体。
例：task_id=8f21，实现 review@1，参数 {pr: 431}，状态依次 pending → assigned → acked → running。
Trace trace_id · 行程
一趟行程：从最初那个事件到最后一条任务的完整因果链，事件、每次查表、每个任务的回报都挂在同一个 trace_id 下。这次行程具体走过哪些接口，记在 path 上——从根到本任务这条具体路径的接口名序列，用来做去重剪枝。
例：trace=tr_7c1a，跑到 review@1 → implement@1，那么 implement 这个任务走的行程是 path = [review@1, implement@1]。
Node node · 链路节点
链上的一个位置，只有三种：origin（只有出）、pipe（有进有出）、end（只有入）。注意它不是机器——机器叫执行器 runner。
接口自己带 kind，执行器也带 kind，实现时两者必须一致，否则注册就被拒（kind_mismatch）——end 接口只能被 end 执行器实现。
例：notify.phone@1 是 end，只能由 kind: end 的手机端承接；review@1 是 pipe。

六个词的关系是一句套娃：中枢先定义接口，执行器实现接口形成能力，能力里那个接口的出口经一条边指向下一个接口，一次派发落成一个任务，整趟行程是一条 trace。出口名、参数结构、谁能实现，全在接口里定死了，所以系统里唯一需要被推理的东西只剩「查表」，其余都是记录。

箭头就是动词。执行器 implements 接口，这个实现就是能力；能力里的接口按 edges 连成图。图只认接口，不认机器——换一台机器实现同一个接口，图一个字都不用改。

节点有三种，按端口形状分

分类的依据不是「这东西有多重要」，而是它的端口形状：有没有入口、有没有出口。origin 只有出，pipe 有进有出，end 只有入。

源 · source有出 · 无入
→
pipe · 管道有进 · 有出
→
end · 终点有进 · 无出
入在左，出在右。一个节点最多两类端口，所以它必定落进上面三种形状之一。链的最左边只能是 origin，最右边只能是 end——中间想再插什么，都得是 pipe。
种类 入 出 接口与能力 例子 kind
源 · 触发器 ✗ ✓ 有 kind: origin 的接口（github@1 等），出口由接口给定；执行器不实现它，事件本身充当起点 GitHub webhook、cron、watch、外部 API 轮询 origin
管道 ✓ ✓ 执行器 implements 某个 kind: pipe 的接口，形成能力；出口来自接口 机器上的 review@1 / implement@1 / test@1 pipe
终端 · 叶子 ✓ ✗ 执行器 implements 某个 kind: end 的接口，该接口 outputs 为空 推手机 notify.phone@1、写归档日志 log@1 end
没有第四种。任何参与流转的东西都能被这三类装下：定时器是源，CI 里的一个步骤是管道，企业微信机器人是终端。所以中枢不必为「新类型实体」写新代码，只读它的 kind 和它实现了哪些接口。
触发器就是「只有出口、没有入边的节点」。它也是一个接口（github@1，kind: origin），只是没有执行器去实现它：外部事件打进来，中枢直接拿这个接口的出口（事件类型）查表——github@1 --(pr_opened)--> review@1。

这些名字全是接口，不是机器。图里没有一个执行器——机器在后面：review@1 这个接口由某台机器 implements，换一台机器实现图也不用改。中间那几个虚线框是接口给的出口，也就是表里的 from_port。edges 表是中枢侧唯一的路由依据：它不看执行器上的代码、不解释出口的业务含义，只把（接口, 出口）这一对填进表里查一次——图是画给人看的，跑的永远是这张表。

出口名为什么必须由接口给定

旧模型让执行器自己编出口名，结果是两台机器实现同一个 review 却报出 [fix, clean] 和 [ok, bad]，edges 里于是出现 (review, fix) 和 (review, ok) 两套起点——查表时不知道该用哪个，边的唯一性没了。接口把命名权收归中枢，from_port 才是封闭集合；执行器只负责说「我实现了 review@1」，以及跑完从接口给定的那几个出口里选一个。

一个版本就是一个接口

review@1 和 review@2 是两个不同的接口，可以并存：旧机器继续实现 @1，新机器实现 @2，edges 里各有一条边，升级期不必全网停机。代价是图里同名接口会出现两个版本，所以展示时不能只写 review，必须带版本号，否则看不出走的是哪条边。

而且不允许实现子集。实现 review@1 就必须 fix 和 clean 两个出口都能走。若能只实现一半，edges 里就会出现「这台机器没这个出口」的分叉：查表命中却派不出去。要单独能力就定义一个新接口，别在旧接口上开洞。

一个出口可以有多条边

表里同一个（接口, 出口）可以有多行，那就是扇出。返回 N 行就派 N 个任务，全部下发，不是择一；返回 0 行就是到头，理由是「表里没有这一行」。

review@1这次走了出口 fix
implement@1(review@1, fix) 的第 1 行
notify.phone@1(review@1, fix) 的第 2 行
扇出，不收集。两条边都成立，所以建两个任务、trace 在这里分叉——没有优先级，也不需要挑一个，一次查表返回多行就往多下走。反过来「等这组任务都回来再继续」本期不做——那件事放在执行器内部自己并行、自己汇总。任务回报的出口本身可以再查表，那就是接力。

一次旅程（文字版）

把上面的名词按时间排一遍，就是一次完整的调用。完整的时序图在下一页，这里先记住四步。

事件入库
触发源发来一次调用（或者 cron 到点），中枢把它存成一行 event：source、type、payload、trace_id、span_id。入库即完成，之后的一切都基于这条记录，不基于原始请求。
查表 → 校验参数 → 选执行器
拿（源接口, 出口）这一对去 edges 表查一次：from_interface 是触发源那个接口、from_port 是事件类型。查表只有一次索引查询——没有条件求值、没有优先级、也不是择一。返回 N 行，就是 N 个下游接口，全部都要派；返回 0 行就到此为止，理由写清楚是「表里没有这一行」。
拿到的每个下游接口再走四步（派发全貌在 第 04 页）： ① 查表得 to_interface → ② 用这个接口的 params_schema 校验参数（不通过就记 pruned、reason=param_schema，不建任务）→ ③ 找实现了这个接口的执行器（查 capabilities 表里 interface_id 等于它的行；一台都没实现就保持 pending 排队，不算错）→ ④ 按负载挑一台（或按 sticky 查 runner_pins）建任务。
任务派发
每个下游接口建一个 task，带租约下发给选中的那台执行器。中枢只发接口名、版本和参数——不发 argv、不发图、不说下一步是谁；执行器用自己本地的 argv 执行。执行器 acked 表示接单，随后 running，心跳持续续租。
结果回流
执行器回报 status 与 out。中枢拿（这个接口, 这个 out）再查一次表：有边就建下一个任务，没边就在这里走到头。同一条 trace 不换 trace_id。每个任务各自到头，通知走图里那条边，不需要等整条链结束。
