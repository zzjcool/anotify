安全边界

中枢手上没有任何一条命令。这页讲这条边界怎么落到 DB 字段、协议载荷和 execve 上，为了保住它设了哪六道闸，为什么删掉规则引擎本身也是一道安全收益，以及我们因此接受了什么代价。

根本原则：中枢永不下发命令

中枢只做三件事：记事件、查出口表、派任务。它不知道目标机器上装着什么程序，也不知道某个名字背后对应哪条 argv。任务载荷里只有 {kind, name, params} —— 一个能力名，加上给这个能力的参数。

中枢 · 不掌握执行

DB 里只有事实与引用：events / edges / tasks / runner_pins。没有 argv，没有 shell 字符串，没有脚本文本。

argv不存在
shell / cmd不存在
script不存在
↓
任务载荷 {kind, name, params}中枢所能表达的全部
↓
执行器 · 本地决定能执行什么

本地 config.yaml 把 capabilities[].name 映射到 argv[]，命中就 execve(argv[0], argv, envp) 起进程。这个名字存在过，中枢才知道它存在。

review-pr
deploy-preview
未申报 → unknown_capability
边界画在「名字」上。中枢能说的最多是「review-pr 这个能力，参数是这些」；这串东西能不能变成进程，由执行器本地的 config.yaml 和进程的 OS 权限决定。

执行器侧的真东西长这样，留在本地，永不上传：

# ~/.anotifyd/config.yaml —— 只在本机，中枢读不到
capabilities:
  - name: review-pr
    argv: ["/usr/local/bin/review", "--pr", "{pr}", "--json"]
    outputs: [fix, done]        # 我会用到这两个出口名，不是目的地
    idempotent: true
    retries: 1
  - name: deploy-preview
    argv: ["/opt/deploy/bin/deploy", "--sha", "{sha}"]
    outputs: []                 # 没有出口，干完就结束
    idempotent: false

执行器收到任务后自己查表：name 命中本地申报的能力表就取 argv[]，把 params 逐个填进占位符，然后 execve 直接起进程。不经过 shell —— 没有引号拼接、没有变量展开、没有通配符、没有管道。

  • 未申报的 name → unknown_capability。不回退到默认能力，不做模糊匹配。
  • params 的值只做占位替换，替换结果作为一个完整的 argv 元素传入，不再做二次字符串拼接。
  • env 由执行器本地决定，中枢不提供环境变量。
为什么 /bin/sh -c 是禁区。一旦 argv 被拼成一个字符串交给 shell，params 里的一个分号、一个反引号就能改写整条命令。参数注入的上限会从「某个程序收到一个奇怪的字符串」变成「攻击者在你的机器上执行任意命令」。这条线不放松，一次都不放松。

别人怎么做，我们怎么不一样

多数自动化工具把「要做什么」当成数据存在中枢里：流程节点定义、脚本体、命令行模板。我们反过来，中枢只存名字的引用，能不能执行由执行器自己说了算。差别不在实现细节，在被攻破之后的半径。

问题 其他方案 本设计
中枢存不存「要跑什么」 存。流程节点的命令、脚本、镜像都在中枢 DB 里 不存。只有执行器申报过的能力名 name
能力从哪来 中枢随任务下发，执行器照着执行 节点本地 config.yaml 申报，中枢永远读不到 argv
怎么起进程 解释执行脚本，或拼字符串后交给 sh -c execve(argv[])，参数不经过 shell
中枢被打穿之后 攻击者拿到全部执行能力，可下发任意命令 攻击者只能重复点名已申报的能力

六道闸

扇出、接力、成环都是真实需求，所以不能靠「不允许多发」来防死循环。改成一组数值闸：默认收紧，配置作者可以在硬顶以内放松，越界在配置校验期直接拒绝，而不是运行时静默截断。最后一列分两段写：第一段是它一直防的东西，第二段是它在新模型下防的东西。

闸 内容 默认 / 硬顶 防什么 在新模型下防什么
G1 allow_chain 不显式开启就不允许接力派生 关 / 不可配 防「顺手」接力：一次事件不会靠自己长出第二条链 表里查得到一行，不等于允许走。G1 独立于 edges：它管「允不允许派生」，跟图宽不宽无关。
G2 max_hops 一条链上允许的最大跳数 10 / 32 防链路无限拉长 扇出由表决定，一跳可以同时走多条边；max_hops 管的是深度，不管宽度。
G3 环检测 path 里能力名去重，重复即静默剪枝 隐含 / 不可配 防 A→B→A 转圈；剪枝必须在 trace 上可见 环在配置期就看得见：edges 是显式声明的，画得出也查得出。运行期仍靠 path 去重剪枝 —— 看得见不等于不会走到。
G4 max_tasks 单个事件最多扇出多少个任务 100 / 1000 防一条 webhook 把执行器池一次打满 一次查表返回 N 行就建 N 个任务，表写多宽直接决定分发面，所以这里必须封顶。
G6 max_duration 一条链从根任务算起的总时长 24h / 7d 防慢速循环长期占着租约和预算 环虽然配置期可见，心跳、等待与重试照样能拖很久；总时长兜住慢速循环。
G5 已废弃 付费任务数 — / — 计费口径没定，先留一个空位比留一个错的闸好 无。不参与路由，也不参与收敛判定。

注意分工：G3 保证终止，G2 只是兜住异常。path 去重之后，一条链最长不可能超过图里的能力数，max_hops 管的是「作者期望的深度」而不是「系统的安全上限」。两者都留着，因为前者防转圈，后者防人类配置失误。

三层可配，硬顶只能改代码

同一个限额有三个来源，优先级从下往上：全局 env 给默认值，单版本（图配置）可以覆盖，代码里的常量是天花板。配置里写超过硬顶的数字，校验期直接报错，不悄悄收窄 —— 作者必须知道他写的东西没有生效。

1 全局 env ANOTIFY_MAX_HOPS=10 部署时定，所有版本的默认值
↓ 单版本可覆盖
2 单版本 limits.max_hops: 24 图配置作者填，越界即拒
↓ 但不可越过
3 代码硬顶 hardMaxHops = 32 常量。只能改代码并重新部署，没有配置项、没有 env
为什么硬顶不开放配置。如果硬顶也能改，那它就不是硬顶，只是一层更深的默认值。真正需要放松时走代码变更，让它被 review、被记进版本、被所有部署继承。

为什么删掉规则引擎是一道安全收益

旧模型里，「下一步派给谁」由规则里的 match 表达式决定。要让它能跑，中枢里就必须有一个表达式求值器：一个真正的解释器，要支持字段路径、比较、布尔组合、函数调用，还得维护一套自己的 DSL 语法和文档。这个求值器会成为整个中枢最危险的代码。

旧模型 · 规则引擎

收到事件 → 解 payload → 求值表达式（大量运算）→ 排序优先级 → 选一个 action。求值器要处理任意嵌套的输入结构，输入又来自外部 webhook。

新模型 · 出口表

收到回报 {capability, out} → 一次索引查询 edges → 拿到 N 行 → 全部下发。没有求值，没有表达式，没有优先级。

换成查表之后，中枢里没有表达式求值，也没有 DSL 解析器。这不是重构的副产品，是直接少掉的攻击面：

  • 没有求值器可以注入。表达式求值器天然要面对任意深度、任意类型的输入；现成的求值库历史上反复出过沙箱逃逸、原型链污染、正则灾难回溯。现在中枢只把 capability 和 out 当两个字符串拿去匹配索引，不把它当代码。
  • 没有 DSL 要维护。自己发明的表达式语法就是自己发明的解析器——解析器是 fuzzing 的经典目标，还得同时维护语法文档、错误信息、兼容性。删掉整套 DSL，就删掉了这一整类缺陷。
  • 配置期的检查变强了。表达式能不能写错要到求值（甚至到真跑）才知道；edges 是静态数据，可以在配置期把每条边的两端能力都校验一遍——指向不存在能力的行，根本进不了表。
  • 路由不再依赖 payload。旧模型里，payload 的任何一个字段都可能改变路由结果；现在 payload 只被当作 params 传给节点，完全不参与中枢的路由决策。伪造 payload 也就伪造不出路由。

一句话：安全边界不只是「中枢不掌握命令」，还包括「中枢不解释任何用户提供的逻辑」。求值器、优先级排序、择一——这三样一起去掉，中枢的路由部分就退化成一张固定的表和一个索引查询。

信任边界与代价

这套边界不是免费的。把代价写清楚，比再堆一层防御更像一个工程决策。

token 泄露 = 继承这台执行器全部标签
拿到执行器 token 的人可以冒充这台机器接单，也就继承了它能跑的全部已申报能力，以及它所属执行器池的派发面。这是「中枢不掌握 argv」的必然代价：中枢不知道能力背后是什么程序，就无法按能力粒度再授权。
不做过度防御
不搞 per-capability ACL，不搞短时二次签名，不做「中枢签名后节点验签再执行」的链式校验 —— 这些机制都要求中枢理解能力背后是什么，正好把丢掉的东西请回来。要缩小半径就缩小执行器：给高风险能力单独注册一台机器，用 max_instances 限制扩散面。
只出站长连接
node agent 主动向中枢发起长连接，中枢不开放任何入站端口。内网机器不需要打洞、不需要公网回调地址，中枢也不成为新的攻击面入口。
最坏情况是什么
中枢完全被打穿：攻击者能读事件与结果、能反复点名已申报的能力、能伪造 params。但不能新增能力、不能改 argv、不能拿到机器上的凭据。伤害上限被钉在「这些能力被以奇怪的参数跑了很多次」。
知道代价，就别假装能消掉它。我们选择用「执行器本地定义能力 + 中枢只认名字 + 中枢不解释任何表达式」换掉一大类远程执行风险，剩下的风险通过缩小执行器权限面来管理，而不是通过更多协议层。
