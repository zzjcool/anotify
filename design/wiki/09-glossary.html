术语表

前面八页用到的名词、字段名、状态名都在这里，一个词一行，只给一句话。写代码、读 trace、查配置时对照用；每条的定义展开在对应正文页，这里不重复论证。

本页只收当前模型的词汇。旧模型的求值类名词已整体作废，不在此列——若在别的文档里看到它们，按 _MODEL-V2.md 的废弃表处理。

能力定义

这一组是最底的一层，也是最原始的一层。先把词序记住：能力定义 → 节点 → 图， 下面的词条都只在这个方向上解释：能力先由中枢定义，节点只能声明自己有哪些已定义的，边只连能力。

能力定义 capability
一份由中枢提前写好的定义：name@version + params_schema + outputs。出口名只能来自这里——节点没有命名权，只能说「我声明了哪个能力」。它是最小的原子：一个动作 + 一组可能的出口，不包含其它能力。定义里没有 kind——那是节点侧推导的。存在 capability_versions 表，append-only。
能力版本 capability@version
能力的具名引用，如 review@1。两个版本就是两个能力定义：review@1 与 review@2 可并存，旧节点继续声明 @1，迁移期不强制升级。代价是图里同名能力会出现两个版本，所以控制台必须显式显示版本号。
参数结构 params_schema
能力定义里的 JSON Schema。派发前用它校验 params，不合格就不建任务。它是「参数不对」与「图不对」「行为不对」区分开的那一层——没有它，参数错误会被当成分支没走到。
出口集 outputs
能力定义里那句「这个能力可能怎么结束」，如 [fix, clean]。它是契约，不是申报，节点无权增减。它同时是节点 kind 的推导依据：outputs 全为空的能力只能把节点推成 end。
内置能力 builtin
随项目发布的能力（capabilities/builtin/），由项目维护、进 git 走 review。本期共 10 个：github / cron / watch / http / review / implement / test / notify.phone / notify.webhook / log。表里的 source = builtin。
自定义能力 custom
用户自己在中枢配置目录里追加的能力。同一套格式、同一套版本化，加载后与内置没有区别，只靠 source = custom 区分来源。
未知能力 unknown_capability
节点声明的能力指向一个中枢里不存在的定义。拒绝该声明，不自动创建同名能力——能力必须先在 git 里有定义。
版本不受支持 unsupported_capability_version
能力名在、但那个版本不在。和 unknown_capability 分开报，是因为修法不同：一个是名字写错，一个是版本号写错。
参数不合格 param_schema
剪枝原因之一：params 没通过目标能力的 params_schema，不建任务，trace 上记 pruned / reason=param_schema。与 no_edge 区分：那是图里没这行边，这是边在、参数不对。

节点

节点 node
参与流转的一台机器：一份身份 + 若干实例，本地持有一批 argv 与凭据。它只声明自己有哪些已定义的能力，不定义能力、不命名出口。存在 nodes 表。
种类 kind
推导的，不手写。由节点声明的能力自动算出：全部 outputs 为空 → end；有非空 → pipe；没有任何节点声明它 → origin。所以不存在「写错 kind」这种配置，也不会有一类「kind 不符」的校验错误——不存两份就不可能不符。
源头、触发器 origin
只有出口的位置，负责产生事件：GitHub webhook、cron、watch、外部 API。它不是一台机器——没有任何节点声明那个能力，事件本身就是链的起点，所以永远不会被派任务。
管道 pipe
有进有出的节点，比如声明了 review@1 / implement@1 / test@1 的机器——这三个能力的 outputs 都非空。任务落在它身上，跑完必须回报 out。
终点 end
只有入口的节点，跑完不产生下游：推手机、写日志。它声明的能力全部 outputs 为空，所以 out 恒为 null。
推手机
最常见的一个 end 节点，能力是 notify.phone。尽力而为、可丢、不回报 result，没有租约也没有重试。
能力清单 manifest
节点上报的「我声明了哪些能力」：capabilities: [{capability, version}] 加各自的 sticky / idempotent 等声明。不写 outputs（出口由能力定义给定），不含 argv 原文，也不写 kind（推导）。
节点 id node_id
一台节点的稳定标识，和凭据一一对应。改名字不改 id。图里从不出现它——边只连能力，换节点不影响图。
实例 node_instance
节点进程（手）。一台节点可以跑多个实例，各自申报 concurrency / inflight / status。存在 node_instances 表。
标签 label
中枢赋给节点的分组名，用来圈定候选实例。能力声明决定「能不能做」，标签决定「让谁做」。
在跑数 inflight
实例当前正在跑几个任务。派发按它做「最少负载优先」。
并发 concurrency
能力级并发上限，节点本地声明。实际并发取三层上限的 min。
max_instances
一台节点允许跑几个实例，默认 20。防的是凭据扩散：每个实例一份 token，越多越难收。

能力与出口

上一组说的是「能力定义长什么样」，这一组说的是「它怎么被用起来」：节点怎么声明、出口怎么选、边怎么查。 「能力」本身不在这里重复定义（见 能力定义 组）——一个词只有一条。

声明能力 capabilities[]
节点在本地配置里声明「我有哪些已定义的能力」，如 review@1。它不写 outputs，出口集合由能力定义给定。但它不需要实现这些出口——出口名是别的能力的名字，由那些能力的节点去做。
出口 output / port
能力定义里的一个命名点（outputs 数组的一个元素）。跑完之后节点选一个，走法就是回报它的名字。它是字符串，不是条件。出口名就是一个能力名——报 fix 就派 fix@1。路由的原子坐标是 (能力, 出口)。
边 edge
(from_capability, from_port) → to_capability 三元组，路由表的一行。两端都是能力定义，不引用任何机器——换节点不影响图。
出口表 edges
全部边的集合，路由的唯一依据。主键 (from_capability, from_port, to_capability)，查询是一次索引命中。存的是 capability_versions.id（cap_...）而不是 name@version，所以改名、加版本都不影响已有的边。
from_capability
边的起点，产出口的那个能力（cap_...）。触发器的这一端也是能力定义，如 github@1。
from_port
边从哪个出口出发。必须是 from_capability.outputs 里的一个，静态检查会拒给不存在的出口名。触发器的这一列就是能力的出口名，如 pr_opened。
to_capability
边的终点，下一个能力（cap_...）。同一个 (from_capability, from_port) 可以有 N 行，就是 N 个下游。
源的出口声明 emits
触发器在 config.yaml 里声明「我产出哪些事件、各通向哪些能力」。中枢只收到这些事实，不收到任何 webhook 逻辑。
路由 routing
取 (source, type) 或 (能力, out) 当键，查 edges 拿 N 行，再用目标能力的 params_schema 校验参数、按能力找声明了它的节点。没有条件求值、没有优先级、没有表达式。
参数表 argv
每个能力声明对应的真实参数数组，写在节点本地 ~/.anotifyd/config.yaml 的 capabilities[].argv，永不上传。中枢不知道它长什么样。
execve
唯一执行方式：拿 argv 数组直接 exec，不经 shell。禁止 /bin/sh -c，所以参数不会被二次解析。
幂等 idempotent
能力声明是否只读无副作用，默认 false。它决定节点下线时任务怎么收场：true 直接放弃，false 放弃加告警加人工确认。
可续传 resumable
能力声明对应的命令是否支持断点续传。true 时节点下线可重派到新机器，从中断点继续。
粘性 sticky
这个能力在派发时是否要求固定实例（共享工作目录、增量编译）。默认关闭——结果存在中枢，下游不需要回原机器。

任务

任务 Task task
「让某个能力在某个节点上跑一次」的记录加它的执行状态，同时就是 trace 上的一个 span。最小调度单位。
任务 id tsk_
任务 id 前缀，值同时充当该任务的 span_id。trace 上看到的每个任务 span 都有对应的 tsk_ 行。
派发 dispatch
查表得到 N 个能力，全部建任务（每个只建一个，不是每个节点建一个），然后按能力找声明了它的节点。不择一、不排序、不丢弃。
回报 report
节点跑完提交 status + out（外加 summary / artifacts）。中枢只认回报，不反推业务语义。
结果 result
终态时节点回报的内容，上限 8KB。更大的输出留在节点本地，回执只带截断后的结果和本地日志位置。
出口回报 out
我选了哪个出口，null 表示到此为止。一个字段表达两件事：有没有下游、有哪个下游。只在跑完之后才说得出来。
状态 status
九态状态机里的当前值，是唯一能回答「这个任务卡在哪」的字段。status 与 out 正交：失败也可能要走修复分支。
幂等键 idempotency_key
去重键：同一个 key 的重复投递应当只落一个任务。本期范围里没有定义这个字段，重复触发就是重复任务，防重复靠把图收紧加 daily_budget 兜底。
生命周期 lifecycle
能力声明可声明四项：expiresInSec 硬过期到点即放弃绝不重派 / retryable 是否允许中枢重派 / maxAttempts 重派上限 / resultTtlSec 到期只清 result 不清行。

运行时

九态状态机
pending → assigned → acked → running → succeeded / failed / canceled / abandoned，另有 lease_expired 中间态。中间态不是终态。
租约 lease_until
这个任务被某实例占用的截止时刻。心跳每 10s 把它推到 now + 30s；心跳停了就是失联。
租约到期 lease_expired
租约失效的中间态。attempts 没用尽就回 pending 重派，用尽则 abandoned。
接单 ack
接单确认，不是完成。节点说「这单我接了」，租约才正式计时；结束只看 result 回报。
心跳 heartbeat
每 10s 一次续租，不是保活探针。TTL 30s 除心跳 10s = 允许连丢两次；判定由中枢做，不由节点自报。
attempts
中枢派发次数，租约回收也算一次。上限 3，退避 10s → 60s → 300s。
internal_attempts
节点在机器上自己重试的次数，不消耗中枢 attempts。由节点本地 capabilities[].retries 约束。
退避 backoff
重派的间隔序列 10s → 60s → 300s。重派期间不通知人，用尽才转 failed 进 DLQ。
放弃 abandoned
不重试、必通知。不等于成功，也不等于静默丢弃；和 failed 的区别正在「不重试」。
死信 DLQ
重试耗尽的投递落到这里等人工看，不静默消失。这是 pipe 必须回报的代价。
扇出 fanout
一次查表拿到 N 行就建 N 个任务，互不依赖、互不等待。实现就是同一事务里 INSERT 多行，本期无条件支持。收集（join）不做。
接力 chain
任务回报的 out 查到 edges 里的一行，就建下一跳任务。同一条 trace_id 延续，hop 加一，path 追加能力名。
落点表 node_pins
粘性路由的查表结果。首次选完写进去，之后同一 key 一律查表，不重新算。默认派发不碰这张表。
sticky_key
由 trace、目标能力、选择器三段算出的哈希。只在能力声明了 sticky 时使用。

安全与限额

闸 G1
allow_chain：不显式开启就不接力。默认关，不可配。
闸 G2
max_hops：深度上限，默认 10，硬顶 32。它是外显上界，真正的终止性由 path 去重保证。
闸 G3
path 去重：目标能力已在本次行程里就静默剪枝。隐含生效，不可配。
闸 G4
max_tasks：单 trace 的任务数上限，默认 100，硬顶 1000。
闸 G5（已废弃）
付费任务数。已从设计里删掉，任何新配置都不该再引用这个编号。
闸 G6
max_duration：单 trace 总时长上限，默认 24h，硬顶 7d。到点不再派生，也是缺失 out 时的兜底。
硬顶
写在代码里的上限，配置只能往下改不能往上改。改硬顶等于改代码加发版，不走配置。
三层覆盖
同一类限额的三层配置：全局 env → 单图 → 代码硬顶。前面两层可改，最后一层只能改代码。
每日配额 daily_budget
这张图每天能建多少任务。用尽后新命中不建任务、记 pruned。成本可预测靠它加 max_tasks 两个数。
派生凭据 jti
派生 JWT 里的一次性 id。claim 还含 trace / span / hop / maxHop / branchBudget / exp，跳数由中枢签发，节点改不动。
branch_nonces
已消费 jti 的表。消费 jti、建任务、扣额度在同一个事务里，重放直接失败。
branchBudget
本次派生还剩多少额度，由节点自主分配。额度用尽必须可见，绝不静默失败。
budget_exhausted
额度用尽的三件套：返回 409、span 上写一条 event、控制台标注。少一件就等于静默失败。
凭据 token
节点唯一凭据，一一对应一个 node_id。泄漏即继承这台机器全部标签，这是已知代价；可撤销后重发。

版本

graph_versions
出口图的版本表，append-only：一整张图（全部 edges 行加各能力的 outputs）存一份快照。图是整体，拆开钉就回答不了「当时有没有这条边」。
node_manifest_versions
节点上报的能力声明清单的版本表。节点不报版本号，中枢按内容算哈希得到版本，所以「声称的能力」和「实际内容」不会分叉。
registry_versions
能力注册表的版本表。中枢只知道能力名，形状的变更也要钉版本。能力自身的定义以 capability_versions 为准，这张表记的是注册侧的视图。
content_hash
版本内容规范化后的哈希，带唯一约束。内容没变就不产生新版本，版本膨胀被挡住。
版本 id 格式
<prefix>_<UTC>_<hash8>，例如 grf_20261024T090402Z_5e7c1b0f。人眼能看出时间和前缀，机器能校验前八位哈希。
钉 hash 不钉时间
trace 上记的是不可变的版本 id，不是「按时间反查当时生效的版本」。补录、回滚、跨时区导入都会打乱时间顺序，但动不了已经算好的 hash。
叠加图 overlay
把「图里有什么」和「这次走了什么」叠在一张图上的视图。亮实线 = 走过，灰虚线 = 有边没走，红虚框 = 剪枝。

事件与行程

事件 Event event
系统里唯一的事实单位：外部触发写一行，任务回报也写一行，两者形状相同，过的是同一张出口表。
事件来源 event.source
事件从哪来，如 github / cron / watch / agent。和 type 一起构成查表的起点 origin:<名字>。
类型 type
事件类型，写成 <域>.<动作>，如 pull_request.opened、task.succeeded。它同时也是触发器的 from_port。
载荷 payload
事件携带的 JSON 主体。中枢只存不解释——路由不看它，所以它不会影响走哪条边。
链路 id trace_id
一次触发引起的全部工作共用的 id。根事件生成，后继事件与任务一律沿用，不新开。
span id span_id
一次工作的唯一标识。本项目里它就是任务 id（task.id），不另发号。
父 span parent_span_id
哪个任务派生出来的（tasks.parent_task_id）。根事件直接派生的任务，这一列为空。
跳数 hop
接力深度。根事件 0，每派生一次加一。上界由 max_hops（G2）管。
深度 depth
这个任务在派生链里的层级，与本任务 path 的长度一致。和 hop 说的是同一件事，一个从行程看、一个从跳数看。
行程 path
从根到本任务这条具体路径的能力名序列，用于去重剪枝。不是整条 trace 的能力集合——同一个能力在另一条分支上照样能跑。
剪枝 pruned
本该建任务却没建时留下的记录，必须带原因。静默指不报错不暂停，不是不记录。
no_edge
剪枝原因之一：edges 表里查不到 (from_capability, from_port) 这一行。图是静态的，所以这个原因不跑也能知道。
抑制 suppressed
本该发出去却没发的记录，用于回答「通知去哪了」。它是显式的丢弃，和「跑过但失败」区分开。
链路 Trace trace
一条完整链路的视图，按 trace_id 把事件、查表结果、任务状态聚到一起，是事后回答「走了哪条路」的唯一入口。
span Span
链路上的一段执行，有起止时间。本项目里 span 就是 task——一个任务一个 span，不另建表。一次查表没有时长，只在事件 span 上留痕。
四个「没做成」别混。pruned 是任务压根没建（表里没有这条边 / 行程里已有该能力 / 参数不合 schema / 被限额挡下）；suppressed 是本来要发的没发； failed 是跑过但失败、可重试；abandoned 是不再重试且必须通知。混用任何一个，事后就再也解释不清「这次为什么没发生」。

前缀速查

id 前缀一眼就能看出对象类型。标「本期不用」的，是这个前缀没有对应的对象——不是还没写，而是设计上就不需要。

前缀 代表 说明
evt_ 事件 event 外部触发与任务回报都用它，事件只追加不修改。
trc_ 链路 trace 本期不用：没有独立的 trace 行，链路是按 trace_id 把事件和任务聚合出来的。
spn_ span 本期不用：span_id 就是 task.id，走的 tsk_ 前缀。
tsk_ 任务 task 任务 id，与 span_id 同值。trace 上的任务 span 就是它。
cap_ 能力版本 capability_versions 能力的一个具体定义版本，格式 cap_<UTC>_<hash8>，append-only。edges 与 node_capabilities 存的都是这个 id。
grf_ 图版本 graph_versions 出口图版本，格式 grf_<UTC>_<hash8>，append-only。一份快照含全部 edges 与能力声明。
nmf_ 版本 node_manifest_versions 节点能力声明清单的版本，由内容哈希算出，不由节点自报。
reg_ 版本 registry_versions 能力注册表版本，例 reg_20261023T101500Z_a1b2c3d4。
nd_ 节点 nodes 节点身份 id，注册时由中枢发放，不接受自报、不接受改名。
inst_ node_instances 节点实例，一台节点可以有多个。带 concurrency 与 inflight。
fan_ 扇出批次 本期不用：没有「批次」这个对象，扇出只是一次查表后 INSERT 多建几行任务，不需要批次 id。
