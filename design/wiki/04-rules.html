规则与扇出

事件进来之后，规则决定派哪些任务；任务的结果又能变成新事件，继续往下派。这页讲清四件事：规则长什么样、为什么命中就全部下发、扇出为什么不是收集、以及允许成环时靠什么保证一定停得下来。

规则长什么样

一条规则就是一份声明式配置，三块内容：match 说「什么算命中」，action 说「命中之后做什么」，剩下四个字段是这条规则能花掉多少预算。没有脚本，没有表达式引擎，也没有节点图。 

// design/rules/github-pr.jsonc
{
  "id": "rev-pr",

  // 1. 什么算命中：全部满足才命中，缺省字段 = 不约束
  "match": {
    "source": "github",
    "type": "pr.opened",
    "payload.repo": "^acme/",
    "payload.draft": false
  },

  // 2. 命中之后做什么：派给节点（要回报）还是推手机（不回报）
  "action": {
    "sink": "machine",
    "kind": "command",
    "name": "review",
    "params": { "mode": "diff" },
    "selector": { "label": "go" }
  },

  // 3. 四个钳子：深度 / 任务数 / 总时长 / 每日配额
  "max_hops": 6,
  "max_tasks": 40,
  "max_duration": "6h",
  "daily_budget": 300
}
字段 类型 含义
id string 规则标识。成环剪枝、粘性路由、trace 都认这个名字；同名即同一环。
match object 条件集合，全部满足才算命中。支持 source、type 和 payload 的点路径（如 payload.repo）加正则；没写的字段表示不约束。
action object sink: machine 派任务到节点，必须回报、有租约、失败重试；sink: human 推手机，尽力而为、可丢、不回报。两者永不混用。发给节点的全部内容只有 {kind, name, params} 三段，外加上面的 selector（选节点标签）。
max_hops int 接力深度上限（闸 G2）。默认 10，硬顶 32。
max_tasks int 这条规则在一条 trace 里最多建多少个任务（闸 G4）。默认 100，硬顶 1000。
max_duration duration 一条 trace 的总时长上限（闸 G6）。默认 24h，硬顶 7d。到点后不再派生新任务。
daily_budget int 这条规则每天的建任务配额。用尽后新命中不建任务——成本可预测就靠它和 max_tasks 两个数。

命中 0 条规则时结果很干脆：不派任何任务。但这不是「什么都不发生」——trace 上留下一条 pruned 记着没命中的原因，否则事后没法回答「这次为什么没触发」。

多条命中，全部下发

一个事件可以和任意多条规则同时匹配。匹配结果不是一个「被选中的规则」，而是 N 个任务，一次性全部建出来。没有优先级，没有互斥，没有「取第一条命中的」。

pr.opened1 个事件
rev-pr → T1machine sink · 派 agent 审查
pr-notify → T2human sink · 推手机
label-guard → T3machine sink · 打标签
三条规则各自求值，互不知道对方存在。这里一个事件同时走了两类 sink：机器任务要回报，手机通知不回报。

三个任务之间没有任何依赖关系：T1 失败不会撤销 T2、T3，T3 成功也不代表事件「已被处理」。实现上扇出的代价几乎为零——一次 INSERT 多行而已，这也是它在本期被无条件支持的原因。

扇出不等于收集

这是两个方向相反的问题，在别的工作流产品里常常被混成一个词。扇出回答「这个事件要引起几件事」，收集回答「那几件事都回来了吗」。前者本期做，后者本期不做。

维度 扇出 fan-out 收集 gather / join
回答的问题 这个事件要引起几件事 那几件事都回来了吗
本期 无条件支持：N 条规则 → N 个任务 不做
难度 极低，一次 INSERT 多行 高：批次、计数、菱形依赖、部分失败要各自定义规则
缺失时的代价 没有。扇出本身就是默认行为，不需要开关 遇到「等一组都完成」的需求时，只能把等待塞进节点内部

没有收集，怎么「等一组都完成」

放进节点进程内部。节点 A 收到一个任务，自己在进程里并行跑三个子步骤，自己等齐，自己汇总，最后只回报中枢一个 result。对中枢来说，从头到尾就只有一个任务。

中枢只看到 Task T1
→
节点 A · 进程内
子步骤 1 · lint
子步骤 2 · 单测
子步骤 3 · 审查 diff
→
1 个 result汇总后回报
中枢侧只有一个任务、一份租约、一个 span；三个子步骤只存在于节点 A 的进程里。
代价要说清楚：节点内部的并行在 trace 上不可见。中枢只知道 T1 跑了多久、回了一个什么 result；三个子步骤各自耗时多少、哪个重试过、哪个失败了，都在节点自己的日志里。这是换取实现极简的代价，也是本期不做收集的直接后果。

接力与成环

接力：任务结果变成下一个事件

任务的结果不是终点。节点回报 result 时可以选择性地带一个派生事件，事件照常进日志、照常过规则，命中就继续派任务。这条链就叫接力。

任务结束，回报 result
节点把结果交给中枢：一段摘要，加上可选的派生事件。没带派生事件，这条链就到此为止——绝大多数任务都是这样。
派生事件写入事件日志
新事件有自己的 source、type、payload，但沿用同一个 trace_id，hop 加一。它在日志里和外部进来的事件长得一模一样。
规则重新求值
新事件走完整的匹配流程。这里没有「上一条规则的子规则」这种概念，接力不是嵌套，只是同一个循环再跑一遍。
建下一跳任务，path 加长一位
命中就建任务，新任务的 path = 父任务的 path 加上本条规则 id。没命中的话不建任务，trace 上记 pruned。

允许成环

审查 → 修复 → 复审是真实存在的工作流，不是配置写错了。所以本期不禁止环：禁止它等于让最有用的一种用法没法表达。取而代之的是让每个任务记住自己是怎么走到这里的，然后按记忆剪枝。

rev-pr规则
→
T1 审查path [rev-pr]
→
impl-fix规则
→
T2 修复path [rev-pr, impl-fix]
→
rev-pr 再命中已在 path 里 → 剪枝
← 回边：T2 的 result 派生事件 fix.pushed，规则 rev-pr 再次命中——环在这里被切断，不建 T3。
path 一直往前带：T1 是 [rev-pr]，T2 是 [rev-pr, impl-fix]。因此 T2 之后 rev-pr 的命中被判定为回到走过的路。

path 是这条路径，不是整条 trace

path 的定义很容易被误读成「这条 trace 走过的所有规则」。不是。它是从根到本任务这一条具体路径上的 rule_id 序列。区别在分叉时会立刻显现——两条分支各算各的，互不影响。

事件 E0根，path 为空
分支 1 · 起点是规则 A
规则 A
→
T1path [A]
→
规则 C
→
T3path [A, C]
分支 2 · 起点是规则 B
规则 B
→
T2path [B]
→
规则 C
→
T4path [B, C]
同一个 E0 扇出两条分支。C 在两条分支里都允许命中，因为 T3 的 path 是 [A, C]、T4 的是 [B, C]——各自都是第一次走到 C。
  • 往下推：T3 派生的事件若再命中 A，剪枝——A 已在 [A, C] 里。
  • 同一时刻：T4 派生的事件若命中 A，允许建任务——A 不在 [B, C] 里。同一个规则 id，在另一条分支上照样能跑。
  • 由此得出：保证终止的不是 max_hops，是 path 去重。路径最长 = 规则总数，走到头自然停。max_hops 只是深度方向的另一道保险。

剪枝是静默的，但必须可见

「静默」的意思是：不报错、不暂停、不弹窗、不惊动调用方。不是「什么都不记」。命中被剪掉时，trace 上要留一条 pruned 并写明原因，按下面四类之一：

  • 环：规则 id 已在本任务的 path 里。
  • 深度：超出 max_hops。
  • 预算：超出 max_tasks 或 daily_budget。
  • 时长：超出 max_duration，或未开启接力。

还要把剪枝和「没命中」分开记。没命中是 match 条件不成立；剪枝是条件明明成立了，却被环或预算挡下。两者混在一起，「为什么没发生」就再也解释不清了——而解释这件事正是这个产品的主要卖点。

防炸

扇出、接力、成环三条叠在一起会放大任务量，所以必须有钳子。和本页直接相关的有两个：

max_tasks（G4）
一条 trace 里这条规则最多建多少个任务。默认 100，硬顶 1000，硬顶只能改代码。超出后不再建任务，trace 上记 pruned: task_budget_exhausted。
单事件命中规则数
一个事件同时命中的规则数上限 50 条。第 51 条起不再建任务，同样记 pruned 加原因。防的是「一条兜底规则配得太宽，一个事件把整个节点池占满」。

三个钳子（G2/G4/G6）的数值都可以三层覆盖：全局环境变量 → 单条规则 → 代码里的硬顶。硬顶改不了配置，只能改代码。

预算用完时唯一正确的行为是不建任务 + 记 pruned。绝不静默丢弃：既不悄悄少建一个任务，也不把超出的部分折进另一个任务里。控制台和 trace 上都要能看到被挡下了几条、因为哪道闸。
