节点与执行

节点是一台机器，它声明自己有哪些能力；kind 不写，是推导的。 这页讲六件事：kind 怎么从声明里算出来、中枢与节点的分工边界、注册时的能力校验、租约与状态机、节点池怎么选人、下线时任务怎么收场。

kind 由声明推导

kind 不是填的，是算的：看它声明的能力有没有非空 outputs， 以及有没有任何节点声明过它。规则和 04 能力与出口 同一套，不重复。

节点声明的能力 kind 典型
没有节点声明（能力定义存在，事件从它的出口起步） origin webhook / cron / watch / 外部 API
有任一能力 outputs 非空 pipe review / implement / test
声明的能力 outputs 全为空 end 推手机 / 写日志 / 打回调 / 归档

前两行需要节点，第三行恰好相反——origin 没有任何节点声明它，事件一来就从能力定义的出口起步。

中枢不知道节点上有什么能力（argv 在本地）

节点在自己机器上维护一份实现表（能力 name@version → argv），永不上传。 上传给中枢的只有一份能力名列表：名字 + 版本，没有 argv，没有出口，也没有 kind。 中枢知道「这个节点声明了哪些能力」，但不知道能力背后是什么程序、带什么参数、在不在。

节点本地的实现表（这份文件从不离开本机）不进中枢 
# 节点本地 ~/.anotifyd/config.yaml —— 这份文件从不离开本机
node: mbp-16

capabilities:
  - review@1                        # ★ 只写能力名，不写出口、不写 kind
    argv: ["git", "diff", "--name-only"]
    retries: 2                       # 节点内部重试，不消耗中枢 attempts
    idempotent: true                 # 只读，重跑无副作用
    concurrency: 2                   # 实现级并发上限

  - test@1
    argv: ["make", "test"]
    retries: 0
    idempotent: false                # 默认值：有副作用
    resumable: false
    concurrency: 1
中枢只知道这个节点声明了哪些能力名与版本，不知道背后是什么程序、带什么参数。

上报到中枢的 manifest 里只有一份 capabilities 列表——能力名 + 版本，没有 outputs，也没有 kind。 出口集合 {fix, clean} 长在能力定义里：节点既没有位置写它，也没有命名权。

节点上报的 manifest只有能力名 + 版本 
// 节点上报的 manifest（注册 / 心跳时）—— 只有能力名列表
{
  "capabilities": [
    { "capability": "review", "version": 1 },
    { "capability": "test",   "version": 1 }
  ]
}
没有 argv，没有 outputs，也没有 kind。
节点声明 review@1只说有哪些能力，不写出口 →
中枢 capability_versions + edgesreview@1 的出口是 {fix, clean} →
下一跳派给谁节点不知道，也不需要知道
出口集合来自能力，下一跳来自 edges，两层都不在节点手里。 节点只负责「我干完了，走了 fix 这个门」：fix 在不在允许集合里由能力定，门后通向谁由中枢的 edges 表定。这正是分工——能力管命名，中枢管连线，节点管执行。
中枢{capability, version, params} →
agent 出站长连接WebSocket · 不开放入站端口 →
节点查自己的表能力名@version → argv →
execve(argv[])不经过 shell
线上只跑这三个字段。节点收到 {capability, version, params}，拿「能力名 + 版本」查本地实现表得到 argv，直接 execve(argv[])；查不到就回报 unknown_capability。中枢不改写命令、不猜参数、不拼命令行。

DB 里没有 argv 字段，也没有 shell 字符串字段。执行一律 execve(argv[])，禁止 /bin/sh -c：参数不会被二次解析，也就没有注入面。中枢整个被拿走，也拼不出一条真实命令。

注册时的能力校验

节点上报能力名的那一刻，中枢做一次闭卷考试：列表里每一项都必须能在 capability_versions 里查到（名字和版本都对得上）。三条拒绝理由，没有第四条。

拒绝理由 触发条件 中枢处理
unknown_capability 能力名在 capability_versions 里不存在（如申报 git.fetch@1） 拒绝这一项，其余项照常注册
unsupported_capability_version 名字存在，但这个版本没有定义（如申报 review@3，中枢只有 review@1） 拒绝这一项，不降级到 @1
报了 outputs 节点想在声明里自己加出口（如附 outputs: [fix]） 拒绝这一项——出口由能力定义给定，节点只报能力名

能力不存在，就不允许注册这个能力。中枢不接受自由字符串：capabilities 里写下的每个名字都要能查到能力定义， 否则这一项直接作废。 现在中枢手里有一份白名单，名字不在名单上就没有这个能力，也没有「先注册上再补能力」这条路。

注册响应：逐项判决坏的作废，好的照常注册 
// 注册响应：逐项判决，坏的作废，好的照常注册
{
  "accepted": [{ "capability": "review", "version": 1 }],
  "rejected": [
    { "capability": "git.fetch", "version": 1, "reason": "unknown_capability" }
  ]
}

为什么删掉了 kind_mismatch。kind 是推导出来的，不是节点自报的字段，所以不存在「和定义不符」这种可能。 这条旧理由针对的是「节点手写 kind」那种模型，现在它连输入都没有—— 节点报的是能力名，同一个节点可以同时声明 review@1 和 notify.phone@1，推出来是什么就是什么。

「声明 review@1 就得能走 fix 和 clean」是个误解。节点声明的只是「我认得这个名字」， outputs 是它跑完可以报出的名字，不是「我得把 fix 和 clean 都实现出来」。 fix 和 clean 各自是独立的能力定义，各带自己的版本，由别的节点声明。 review 报出 fix，中枢就去派 fix@1——回头找的不是 review。 所以要更小的粒度，本来就只需定义一个更小的能力，不存在「在旧能力上开洞」这回事。

凭据与标签

节点身份由中枢发放，不由节点自述。标签挂在身份上，所以「谁是不是能跑 review 的机器」是中枢侧的事实，不是节点说了算。

node_id
注册时由中枢生成并写进凭据。节点拿到的是哪个就是哪个，不接受自报、不接受改名。
token
节点唯一凭据，一一对应一个 node_id。可撤销后重发；撤销即这台节点全部标签一起失效。
标签 labels
绑在 node_id 上，中枢赋值。出口表按标签挑节点，不写机器名、不写 IP。
泄漏的代价
token 泄漏 = 继承这台节点的全部标签。这是必然代价，不做过度防御——不搞短时令牌轮换、不搞节点内二次鉴权。 想缩小爆炸半径，就少给标签、多拆机器。

状态机与租约

中枢不知道任务在这台机器上跑到哪一步，它只知道租约还在不在。状态推进全部由节点上报事件驱动，中枢只做两件事：续租、超时回收。

主路径
pending →
assigned →
acked →
running →
succeeded
终态 · acked / running 都可能落到
acked / running
failed · 重试耗尽 canceled · 人取消 / 配置撤销 abandoned · 节点下线 / 硬过期
租约失效 · 中间态，不是终态
assigned / acked / running →
lease_expired
attempts 未用尽 · 回 pending，重派 attempts 用尽 · abandoned
ack = 接单确认，不是完成。节点说「这单我接了」，租约才开始正式计时；任务真正结束只看 result 事件。把 ack 当完成，所有长任务都会在超时后被判重跑。
assign 20s
ack 10s
心跳 · 每次续租 …
result
租约 TTL 30s max_attempts 3 退避 10s / 60s / 300s
派发后 20s 内没等到 ack 就直接 lease_expired。之后每 10s 一次心跳把过期时间推到 now + 30s，心跳停了就是节点失联，剩下的 TTL 里仍无上报即回收。每次回收算一次 attempt。

节点内部重试 vs 中枢重派

两套重试解决两类问题，不能互相替代。节点内部重试是「这台机器上再试一次」，中枢重派是「换一台机器再来」。

维度 节点内部重试 中枢重派
谁定义次数 节点本地 capabilities[].retries（不上传） 能力 lifecycle.maxAttempts（中枢侧）
是否消耗中枢 attempts 否。中枢只看到一次调用 是。每重派一次 attempt + 1
触发条件 实现非零退出、网络抖动 租约过期、节点下线、节点上报可重试错误
退避 节点自己定 10s → 60s → 300s
审计影响 记在节点侧；trace 上是同一个 span 每个 attempt 一个 span，换节点就换 node_id

节点池：两级

一个节点 = 一份身份 + 若干实例。身份（nodes）管脑、标签、配额；实例（node_instances）管手、并发、存活。 一台机器可以起多个实例，但只有一份身份。

nodes身份 / 脑 · labels · max_concurrency 8 · max_instances 20
node_instances #1concurrency 4 · inflight 2 · alive node_instances #2concurrency 4 · inflight 4 · alive node_instances #3concurrency 4 · inflight 0 · draining
身份一份，手可以多只。实例掉线只影响自己名下的任务；所有实例都掉线，才算这个节点下线（见下文下线分级）。 max_instances = 20 是硬顶，防止一份 token 复制出一片节点。
实例申报 · node_instances.concurrency 实现级 · capabilities[].concurrency 节点级 · nodes.max_concurrency
实际并发 = min(三者)谁申报得小听谁的
三个上限同时生效。并发是本地事实，不上提到能力层——同一台机器同时跑几份 review@1 取决于它自己的手， 而不是能力规定。一份实现不许同时跑 5 份，就不会跑 5 份，哪怕整套池子还空着。 派发策略只有一条：最少负载优先——在标签命中的节点里比 inflight / concurrency，取最小的；全满就排队，不溢出到标签不匹配的节点。

粘性路由：开在能力定义里，节点自己开不了

先分清两件事。任务的 result 存在中枢（上限 8KB），所以下游读结果不需要回到原机器—— 这一层跟粘性无关。真正需要粘性的只有一种情况：连续任务要共享本地产物， 比如同一个工作目录、刚编译出来的中间文件、未提交的 worktree。

本期默认不粘。因为本期不做收集，下游本来就拿不到上游的本地产物； 而同一个 trace 的多条分支（机器 / 人）本来就不该挤在同一台机器上。 粘性开在能力定义里：中枢侧的能力定义写 sticky: worktree，或者在控制台按能力名开启， 中枢才会去查 node_pins。节点自己开不了粘性——能力是共享契约， 粘性该由能力决定，而不是由某台机器决定。

能力类型 需要粘性吗 派发方式
纯计算 / 只读（lint、审查、探索） 不要 纯负载均衡，每次挑最空的实例
共享工作区（连续改同一个 worktree、增量编译） 要 能力定义里 sticky: worktree，同 key 钉同一个实例
手机（end） 不要 不进节点池，不参与派发

能力定义开了粘性，才走下面这条链路。

sticky_keysha256(trace_id ∥ capability_id ∥ selector) →
查 node_pins →
命中 → 粘住原 node_id
未命中 →
按负载选一台节点 →
写 pin，之后一律查表
pin 一旦写就不再重算。rebalance 只处理失效 pin（节点下线、实例全满），不重排全局—— 每次全局重排都会让一半任务的中间产物白跑。
node_pins 表结构DDL 
CREATE TABLE node_pins (
  sticky_key   TEXT PRIMARY KEY,   -- sha256(trace_id ∥ capability_id ∥ selector)
  node_id      TEXT NOT NULL,      -- 选中就钉死，不随负载漂移
  selector     TEXT NOT NULL,      -- 当时命中的标签，失效判断用
  created_at   INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL,
  FOREIGN KEY (node_id) REFERENCES nodes(node_id)
);

-- 写 pin 与建任务在同一个事务里：任务在，pin 一定在。
-- rebalance 只扫 node_id 已下线 / 实例全满的 pin，重新选一台节点并改写 node_id。

往哪走：out 写在结果里

中枢只需要知道一件事：这一次跑完，接下来派哪个能力。 它不判断「整条链有没有结束」——那件事没有系统级的消费者，命令跑完了就是跑完了。 而「派哪个」中枢也不能猜：它不知道某个能力的业务语义，只知道名字和版本。

但这件事不能写在能力声明里。实现还没跑，谁也不知道它会走到哪个出口—— 成功要跑完才知道，失败也要跑完才知道。让声明提前承诺「我一定会走 fix」， 等于让节点在开局就赌。 所以 out 是 result 里的一个字段，不是声明里的常量。
执行完成成功 / 失败都算 →
result 里带 out出口名 或 null →
中枢查 edges 表有边就派，没边就到头
out 一个字段同时回答两件事：有没有下游（null = 没有）、有哪个下游（"fix" = 走这条边）。 旧的 terminal 布尔字段只答得出第一件，还得再猜一次走哪条；换成出口名之后，一件就够了。
result 载荷示例status + out + summary + artifacts 
// 节点回报的 result（≤8KB）
{
  "status": "succeeded",
  "out": "fix",          // ★ 干完了，走 fix 这个出口
  "summary": "发现 2 处类型错误，交给修复分支",
  "artifacts": ["tsk_8f21a3c0"]
}

{
  "status": "failed",
  "out": null,           // ★ 失败，且这条线断在这里
  "error": "build exited 1, 无后续"
}
out 是出口名或 null，跑完才知道。

它描述的是「这一次」，不是「这个能力」。同一个 review@1， 这次改完了就回报 null 收工，下次发现新问题就回报 "fix" 接着走——同一个能力，两次的 out 可以不同。 中枢不预判、不反推，只读这一个字段；拿到之后做一次查表：edges 里有 (能力, 出口) 这一行就往下派，没有就到头。

为什么失败也要带这个字段

失败和继续是两个独立的维度。一次失败可能让链停在这里（out: null）， 也可能触发一条「修复」分支（out: "fix"）。 中枢不判断哪种该发生，它只读节点回报的事实，然后查表。

status out 含义
succeeded "fix" 干完了，往下走。查 edges：(能力, fix) 指向谁就派谁。
succeeded null 干完了，到头了。这条线在这里结束。
failed "fix" 失败，但触发了修复分支。同样查表派下一跳。
failed null 失败且断在这里。没有下一跳，链在这里结束。

节点漏报怎么办

缺失、迟到、或格式不对时，中枢一律按「没回报」处理——不替它猜一个出口。 后果很直接：这一跳不派，链在记录上停在这里，但不伪造一个「到头」。 三道兜底保证任务行不会永远挂着：

租约兜底
任务最终都会被租约重置到一个终态（含 abandoned），不会永远 running。
超时置终态
max_duration 耗尽时强制落 abandoned，out 保持空——不填 null 冒充已回报。
漏报可见
这种任务在 trace 上单独标出，并且计数进控制台。「有 N 个任务未回报出口」是给人看的告警，不是自动补一个假出口。
推手机这类 end 能力，本期一律报 out: null。推送没有下游、不需要接续，天然到头。 但以后接审批时，人点完「通过」可能触发下一跳——那时它报的就不是 null 了。 所以走 result.out 这条通道，而不是把「到头」写死在代码里。

下线、过期与生命周期

节点掉线时，它手上的任务没有一个能「继续跑」。区别只在于重派是否安全—— 这由实现自己的本地声明决定（同一能力的不同机器可以有不同的事实），不让中枢猜。

实现声明（节点本地） 这类实现 下线时任务处理
idempotent: true 只读：git fetch、构建、查询 abandoned，不重派；下一次事件自然再来一次
idempotent: false（默认） 有副作用：写库、发版、通知 abandoned + 告警 + 人工确认，绝不自动重跑
resumable: true 可断点续传的批处理 重派到新机器，从中断点继续

abandoned ≠ 成功，也 ≠ 静默丢弃。它和 failed 的区别是：不重试、但默认通知。 默认值是有副作用的 idempotent: false，所以「拿不准要不要重跑」时，结论永远是不跑，叫人看。

任务能活多久、能不能重来、结果留多久，写在能力定义的 lifecycle 下—— 换一台机器实现同一个能力，拿到的限制是同一套。

属性 含义 到点 / 触发后
lifecycle.expiresInSec 硬过期时间 到点直接 abandoned，绝不重派
lifecycle.retryable 是否允许中枢重派 false = 一次性；实现 idempotent: false 时被强制为 false
lifecycle.maxAttempts 中枢重派次数上限 用完即 failed / abandoned
lifecycle.resultTtlSec 结果保留时长 到期只清 result，不清任务行（审计还在）

分工是这样的：这四项在能力定义里（和 params_schema、outputs 同级），是共享契约； 节点本地只管「我自己内部重试几次」（retries）和「我重跑有没有副作用」（idempotent），这两项是本地事实。

retryable 是中枢的意愿，idempotent 是实现的事实。 中枢可以决定「想不想重派」，但碰上 idempotent: false 的实现，意愿无效—— 重跑一个已经发过版的任务，代价比失败更大。接力与链路的次数上限见 04 能力与出口。
