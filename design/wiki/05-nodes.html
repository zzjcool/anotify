节点与执行

统一模型下「节点」不再只指一台执行任务的机器：触发器、机器上的一个能力、一个终端，都是节点。这页讲五件事：节点按端口形状分成哪三种、中枢与节点的分工边界、租约与状态机、节点池怎么选人、下线时任务怎么收场。

节点有三种，不是一种

旧模型里「节点」只指跑任务的机器。统一模型把它放宽了：一切参与流转的东西都是节点—— 一个 webhook、机器上的一个能力、一个收通知的手机。它们不是三套机制，是同一个东西的三种端口形状。

source · 源
只有出口入 ✗ · 出 ✓

webhook / cron / watch / 外部 API。产生事件，不接任务。

worker · 工作节点
有进有出入 ✓ · 出 ✓

机器上的 review / implement / test。接任务，跑完再选一个出口。

sink · 终端
只有入口入 ✓ · 出 ✗

推手机（human sink）、写日志。收了活就结束，不产生下游。

分类只有一条依据：端口形状。不看它跑在哪、用什么语言、由谁维护、是不是人。
kind 入 出 例子
source · 源 ✗ ✓ GitHub webhook、cron、watch、外部 API
worker · 工作节点 ✓ ✓ 机器上的 review / implement / test
sink · 终端 ✓ ✗ 推手机（human sink）、写日志

没有第四种。一个东西要参与流转，它要么只能产生事件（source），要么既能接也能往下走（worker）， 要么只收不发（sink）。判据只有两个问题：「有没有入」「有没有出」，组合起来只有三种答案。 以后无论冒出来什么新东西——一个 IM 回调、一次定时扫描、一个审批环节——都先拿这两个问题量一遍，答案会把它塞进这三类里。

中枢不知道节点上有什么能力

节点在自己机器上维护一份能力表（能力名 → argv），永不上传。中枢只知道「这个节点申报了哪些能力」， 不知道能力背后是什么程序、带什么参数、在不在。 

# 节点本地 ~/.anotifyd/config.yaml —— 这份文件从不离开本机
node:
  command_timeout_sec: 900

capabilities:
  - name: git.fetch          # 中枢只认这个名字
    argv: ["git", "fetch", "--prune", "origin"]
    outputs: [done]           # 会用到的出口名，不是目的地
    retries: 2                # 节点内部重试，不消耗中枢 attempts
    idempotent: true          # 只读，重跑无副作用
    concurrency: 2            # 能力级并发上限

  - name: test.unit
    argv: ["make", "test"]
    outputs: [fix, done]     # 走 fix 去修，或走 done 收工
    retries: 0
    idempotent: false         # 默认值：有副作用
    resumable: false
    concurrency: 1
能力声明 outputs: [fix, done]我会用到这两个出口名 →
中枢 edges 表(test.unit, fix) → implement →
下一跳派给谁节点不知道，也不需要知道
outputs 是「我会用到的出口名」，不是「我会去哪」。 能力只说自己可能走哪几个门，门后面通向谁由中枢的 edges 表决定——节点不该知道整张图长什么样。 这正是分工：节点负责「我干完了，走了 fix 这个门」，中枢负责「fix 这个门通向 implement」。
中枢{kind, name, params} →
agent 出站长连接WebSocket · 不开放入站端口 →
节点查自己的表name → argv →
execve(argv[])不经过 shell
线上只跑这三个字段。节点收到 {kind, name, params}，拿 name 查本地表得到 argv，直接 execve(argv[])；查不到就回报「不认识这个能力」。中枢不改写命令、不猜参数、不拼命令行。
DB 里没有 argv 字段，也没有 shell 字符串字段。执行一律 execve(argv[])，禁止 /bin/sh -c：参数不会被二次解析，也就没有注入面。中枢整个被拿走，也拼不出一条真实命令。

凭据与标签

节点身份由中枢发放，不由节点自述。标签挂在身份上，所以「谁是不是 review 节点」是中枢侧的事实，不是节点说了算。

node_id
注册时由中枢生成并写进凭据。节点拿到的是哪个就是哪个，不接受自报、不接受改名。
token
节点唯一凭据，一一对应一个 node_id。可撤销后重发；撤销即该节点全部标签一起失效。
标签 labels
绑在 node_id 上，中枢赋值。出口表按标签挑节点，不写机器名、不写 IP。
泄漏的代价
token 泄漏 = 继承该节点的全部标签。这是必然代价，不做过度防御——不搞短时令牌轮换、不搞节点内二次鉴权。 想缩小爆炸半径，就少给标签、多拆节点。

状态机与租约

中枢不知道任务在这台机器上跑到哪一步，它只知道租约还在不在。状态推进全部由节点上报事件驱动，中枢只做两件事：续租、超时回收。

主路径
pending →
assigned →
acked →
running →
succeeded
终态 · acked / running 都可能落到
acked / running
failed · 重试耗尽 canceled · 人取消 / 配置撤销 abandoned · 节点下线 / 硬过期
租约失效 · 中间态，不是终态
assigned / acked / running →
lease_expired
attempts 未用尽 · 回 pending，重派 attempts 用尽 · abandoned
ack = 接单确认，不是完成。节点说「这单我接了」，租约才开始正式计时；任务真正结束只看 result 事件。把 ack 当完成，所有长任务都会在超时后被判重跑。
assign 20s
ack 10s
心跳 · 每次续租 …
result
租约 TTL 30s max_attempts 3 退避 10s / 60s / 300s
派发后 20s 内没等到 ack 就直接 lease_expired。之后每 10s 一次心跳把过期时间推到 now + 30s，心跳停了就是节点失联，剩下的 TTL 里仍无上报即回收。每次回收算一次 attempt。

节点内部重试 vs 中枢重派

两套重试解决两类问题，不能互相替代。节点内部重试是「这台机器上再试一次」，中枢重派是「换一台机器再来」。

维度 节点内部重试 中枢重派
谁定义次数 节点 manifest.capabilities[].retries 能力 lifecycle.maxAttempts
是否消耗中枢 attempts 否。中枢只看到一次调用 是。每重派一次 attempt + 1
触发条件 能力非零退出、网络抖动 租约过期、节点下线、节点上报可重试错误
退避 节点自己定 10s → 60s → 300s
审计影响 记在节点侧；trace 上是同一个 span 每个 attempt 一个 span，换节点就换 node_id

节点池：两级模型

一个节点 = 一份身份 + 若干执行器。身份（nodes）管脑、标签、配额；执行器（node_instances）管手、并发、存活。 一台机器可以起多个实例，但只有一份身份。

nodes身份 / 脑 · labels · max_concurrency 8 · max_instances 20
node_instances #1concurrency 4 · inflight 2 · alive node_instances #2concurrency 4 · inflight 4 · alive node_instances #3concurrency 4 · inflight 0 · draining
身份一份，手可以多只。实例掉线只影响自己名下的任务；所有实例都掉线，才算这个节点下线（见下文下线分级）。 max_instances = 20 是硬顶，防止一份 token 复制出一片执行器。
实例申报 · node_instances.concurrency 能力级 · capabilities[].concurrency 节点级 · nodes.max_concurrency
实际并发 = min(三者)谁申报得小听谁的
三个上限同时生效。一个能力不许同时跑 5 份，就不会跑 5 份，哪怕整套池子还空着。 派发策略只有一条：最少负载优先——在标签命中的节点里比 inflight / concurrency，取最小的；全满就排队，不溢出到标签不匹配的节点。

粘性路由：只在任务真的共享本地产物时才需要

先分清两件事。任务的 result 存在中枢（上限 8KB），所以下游读结果不需要回到原机器—— 这一层跟粘性无关。真正需要粘性的只有一种情况：连续任务要共享本地产物， 比如同一个工作目录、刚编译出来的中间文件、未提交的 worktree。

本期默认不粘。因为本期不做收集，下游本来就拿不到上游的本地产物； 而同一个 trace 的多条分支（机器 / 人）本来就不该挤在同一台机器上。 粘性是按能力声明开启的：节点在 manifest.capabilities[].sticky 里说 「这个能力要求固定实例」，中枢才会查 node_pins。

能力类型 需要粘性吗 派发方式
纯计算 / 只读（lint、审查、探索） 不要 纯负载均衡，每次挑最空的实例
共享工作区（连续改同一个 worktree、增量编译） 要 声明 sticky: worktree，同 key 钉同一个实例
human sink（推手机） 不要 不进节点池，不参与派发

声明了粘性的能力，才走下面这条链路。

sticky_keysha256(trace_id ∥ capability ∥ selector) →
查 node_pins →
命中 → 粘住原 node_id
未命中 →
按负载选一个节点 →
写 pin，之后一律查表
pin 一旦写就不再重算。rebalance 只处理失效 pin（节点下线、实例全满），不重排全局—— 每次全局重排都会让一半任务的中间产物白跑。 
CREATE TABLE node_pins (
  sticky_key   TEXT PRIMARY KEY,   -- sha256(trace_id ∥ capability ∥ selector)
  node_id      TEXT NOT NULL,      -- 选中就钉死，不随负载漂移
  selector     TEXT NOT NULL,      -- 当时命中的标签，失效判断用
  created_at   INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL,
  FOREIGN KEY (node_id) REFERENCES nodes(node_id)
);

-- 写 pin 与建任务在同一个事务里：任务在，pin 一定在。
-- rebalance 只扫 node_id 已下线 / 实例全满的 pin，重新选节点并改写 node_id。

谁能终结一条链：out 写在结果里

中枢有一件事必须知道：这条链还会不会往下走。因为「收敛」要发通知， 而通知发出去就不能收回。这个判断中枢不能猜——它不知道某个能力的业务语义，只知道名字。

但这件事不能写在 manifest 里。能力还没跑，谁也不知道它会走到哪个出口—— 成功要跑完才知道，失败也要跑完才知道。让 manifest 提前承诺「我不会继续」， 等于让节点在开局就赌，赌错了就是手机提前响。 所以 out 是 result 里的一个字段，不是 manifest 里的声明。
执行完成成功 / 失败都算 →
result 里带 out出口名 或 null →
中枢查 edges 表有边就派，没边就到头
out 一个字段同时回答两件事：有没有下游（null = 没有）、有哪个下游（"fix" = 走这条边）。 旧的 terminal 布尔字段只答得出第一件，还得再猜一次走哪条；换成出口名之后，一件就够了。 
// 节点回报的 result（≤8KB）
{
  "status": "succeeded",
  "out": "fix",          // ★ 干完了，走 fix 这个出口
  "summary": "发现 2 处类型错误，交给修复分支",
  "artifacts": ["tsk_8f21a3c0"]
}

{
  "status": "failed",
  "out": null,           // ★ 失败，且这条线断在这里
  "error": "build exited 1, 无后续"
}

它描述的是「这一次」，不是「这个能力」。同一个 review， 这次改完了就回报 null 收工，下次发现新问题就回报 "fix" 接着走——同一个能力，两次的 out 可以不同。 中枢不预判、不反推，只读这一个字段；拿到之后做一次查表：edges 里有 (能力, 出口) 这一行就往下派，没有就到头。

为什么失败也要带这个字段

失败和继续是两个独立的维度。一次失败可能让链停在这里（out: null）， 也可能触发一条「修复」分支（out: "fix"）。 中枢不判断哪种该发生，它只读节点回报的事实，然后查表。

status out 含义
succeeded "fix" 干完了，往下走。查 edges：(能力, fix) 指向谁就派谁。
succeeded null 干完了，到头了。这条线在这里结束。
failed "fix" 失败，但触发了修复分支。同样查表派下一跳，不能收敛。
failed null 失败且断在这里。可以收敛，通知里点明失败。

节点漏报怎么办

缺失、迟到、或格式不对时，中枢一律按「未回报」处理（保守，不收敛）—— 宁可晚收敛，也不提前误报。代价是可能永远不收敛，所以要有三道兜底：

租约兜底
任务最终都会被租约重置到一个终态（含 abandoned），不会永远挂着。
缺省补齐
终态任务若没有 out，按「未回报」计入，直到 max_duration 用尽。
超时收敛
max_duration 耗尽时强制收敛，并标注「有 N 个任务未申报出口」——不静默。
本期 human sink 一律 out: null。推送没有下游、不需要接续，天然到头。 但以后接审批时，人点完「通过」可能触发下一跳——那时它报的就不是 null 了。 所以走 result.out 这条通道，而不是把 null 写死在代码里。

节点下线分级

节点掉线时，它手上的任务没有一个能「继续跑」。区别只在于重派是否安全——这由能力自己的声明决定，不让中枢猜。

能力声明 这类能力 下线时任务处理
idempotent: true 只读：git fetch、构建、查询 abandoned，不重派；下一次事件自然再来一次
idempotent: false（默认） 有副作用：写库、发版、通知 abandoned + 告警 + 人工确认，绝不自动重跑
resumable: true 可断点续传的批处理 重派到新节点，从中断点继续
abandoned ≠ 成功，也 ≠ 静默丢弃。它和 failed 的区别是：不重试、但默认通知。 默认值是有副作用的 idempotent: false，所以「拿不准要不要重跑」时，结论永远是「不跑，叫人看」。

任务生命周期属性

能力可以声明一个任务能活多久、能不能重来、结果留多久。四项，都在 lifecycle 下。

属性 含义 到点 / 触发后
lifecycle.expiresInSec 硬过期时间 到点直接 abandoned，绝不重派
lifecycle.retryable 是否允许中枢重派 false = 一次性；能力 idempotent: false 时被强制为 false
lifecycle.maxAttempts 中枢重派次数上限 用完即 failed / abandoned
lifecycle.resultTtlSec 结果保留时长 到期只清 result，不清任务行（审计还在）

retryable 是中枢的意愿，idempotent 是能力的事实。 中枢可以决定「想不想重派」，但碰上 idempotent: false 的能力，意愿无效——重跑一个已经发过版的任务，代价比失败更大。 接力与链路的次数上限见 04 能力与出口。
