本期范围

这一页把线画清楚：哪些东西本期就有、哪些明确不做、哪些留了扩展点但先不实现。范围不清的项目会变成 n8n 的劣化版，所以宁可现在写死。 本轮新增的是最底层——能力定义：中枢先把能力写下来（名字、版本、参数、出口），节点再声明自己有哪些。

本期做的

十三项。每一项都能落到具体的表、字段或状态机上，没有「后续再细化」的占位。 第一项是能力定义层——它决定了下面每一行里「出口」这个词的含义。

模块 本期做到的
能力定义层 能力先定义（name@version + params_schema + outputs），节点只能声明自己有哪些已定义的能力，不能自己编能力名，也不能自己加出口。内置能力随项目发布，用户可在中枢配置目录里追加自定义能力；review@1 与 review@2 视为两个能力、版本并存，迁移期不强制全量升级。节点侧 kind（origin / pipe / end）由它声明的能力推导，不写进定义也不写进配置。
事件 统一的 events 表记录 source / type / payload / trace_id / span_id，cron、webhook、watch 与外部 API 都写进同一张表。
出口表（edges） 显式声明 (能力, 出口) → 能力 三元组，派发就是一次索引查询：查得到就全部下发，查不到就到头。无 match 求值、无条件表达式、无优先级。派发前多一道：用目标能力的 params_schema 校验 params。
扇出 查表返回 N 行就全部下发，一次 INSERT 写成 N 行任务，互不排斥。
接力 节点回报的 out 拿去查表得到下游能力，再按能力找声明了它的节点；allow_chain 显式开启才允许。
成环 允许成环（审查 → 修复 → 复审）；环在配置期由 edges 静态可见，运行期用 path 里能力名去重做剪枝，剪枝在 trace 上可见。
任务租约 TTL 30s、心跳 10s、max_attempts 3、退避 10s → 60s → 300s；pending → assigned → acked → running → succeeded | failed | canceled | abandoned。
节点池 两级：nodes 管身份与脑、node_instances 管实例；三层并发上限取 min，派发按最少负载优先。
粘性路由 按能力声明开启（manifest.capabilities[].sticky），默认纯负载均衡。开启时 sticky_key = sha256(trace_id ∥ capability ∥ selector)，写 node_pins 后一律查表；rebalance 只处理失效 pin。
版本钉住 图配置（含 edges）、能力版本（capability_versions）、节点能力清单、注册表四对象 append-only 版本，trace 钉住不可变的版本 id（content hash），不钉时间。
六道闸 G1 allow_chain、G2 max_hops、G3 环检测、G4 max_tasks、G6 max_duration，默认收紧 + 代码硬顶。
出口回报 节点在 result 里回报 out（出口名或 null，跑完才知道），路由只认这个，不反推业务。缺失按未回报计，不替它猜。
通知 推手机：end 节点（notify.phone），out 恒为 null。尽力而为、可丢。

内置能力清单

随项目发布的就这十个，放在 capabilities/builtin/，进 git、走 review。 表里只有能力与它的出口——没有 kind，因为 kind 是节点侧推导出来的，不属于能力本身。 出口名由这张表给定，节点只能声明、不能扩展——但它不需要「实现」自己报出的出口：fix 和 clean 各自是独立能力，由别的节点声明。 用户自己的能力放中枢配置目录，同一套格式、同一套版本化，加载后与内置能力没有区别（source 字段区分来源）。

能力 outputs
github@1 pr_opened / pr_merged / issue_opened
cron@1 tick
watch@1 changed
http@1 received
review@1 fix / clean
implement@1 verify / give_up
test@1 pass / fail
notify.phone@1 —
notify.webhook@1 —
log@1 —

注册时校验两件事：能力存在（否则 unknown_capability）、版本受支持（unsupported_capability_version）。 不存在「kind 不符」这种错——kind 是推导出来的，不存两份就不可能不符。 派发时多一步：params 不符合目标能力的 params_schema 就不建任务，记 pruned / reason=param_schema。

组织：图属于组织，不属于个人

单库、多组织。借鉴 Tailscale 的 tailnet 模型：一次部署服务所有人， 每个组织有自己独立的节点、能力定义和出口表，相互之间零可见。 

CREATE TABLE orgs (
  id         TEXT PRIMARY KEY,        -- org_xxx
  name       TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL
);

-- 一个用户可属多个组织（人跨组织共享，图不共享）
CREATE TABLE org_members (
  org_id  TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role    TEXT NOT NULL DEFAULT 'member',  -- owner | admin | member
  PRIMARY KEY (org_id, user_id)
);
对象 属于谁 为什么
capability_versions / edges 组织 图是组织的流程资产；两家公司同名能力可以定义不同
nodes / events / tasks 组织 你的机器不能接我的任务，事件日志必须隔离
users / passkeys / sessions / api_keys 人 人跨组织共享身份，不需要每个组织一个账号
devices（推送目标） 人 手机是你的，不是组织的；组织被删手机还在

首次注册自动建组织。和 Tailscale 一样：任何人不经审批注册进来， 系统立刻给他建一个个人组织（他就是 owner），代码里因此不存在「没有组织」的分支。 要协作就邀请别人进组织，要隔离就再建一个。

节点 token 必须带 org_id。这是安全边界，不是数据整理： 拿 A 组织的 token 不能连到 B 组织的图。同理，事件入库、任务派发、图配置全都先过组织校验。

本期不做的

每一条后面都写了「为什么现在不做」和「什么条件下会做」。不做不是因为难，大多数是因为做错了会让产品变成另一个东西。

不做的 为什么不做 什么时候可能做
条件路由 / 表达式路由 不做。路由靠显式出口，不支持 if payload.x > 5 then ... 这种条件。条件路由需要在中枢里放一个表达式求值器，而且一旦路由依赖 payload，图就不再可静态分析——配置期看不到哪些边会被走、「为什么没触发」也不再是查表能回答的问题。 明确有需求再说。做的话是路由层重设计，不是加一个开关
动态边（运行期修改路由表） 不做。edges 变动需要新版本（走版本钉住）：旧 trace 钉旧 hash，新 trace 钉新 hash。运行期改表会让「当时它为什么走这条路」变得不可复现。 不做。改路由就发新版本，代价是一行版本号
收集 / join 要回答「那几件事都回来了吗」，得引入批次、计数、菱形依赖、部分失败语义，是整套新状态机。 等「节点内部并行」这个替代方案被反复抱怨不够用时，再单独设计
能力组合 / 子流程复用 不做。能力是原子：它是「一个动作 + 一组可能的出口」，不包含其它能力，也没有父、没有引用、没有拼装——这样 outputs 才是封闭集合，查表才不需要展开一层嵌套。组合/复用是同一块空缺（把几条链当一个动作调），真要做得先答「参数怎么传、出口怎么合并、内部跳数算不算 hop」，一套都还答不上来。这也是组合能力的预留位置：将来若支持，就在这里开口，而不是给单个能力加父能力。 等内置能力 + 自定义能力这一层被真实用满、且出现「同几条链反复手写」的具体案例时再谈；届时也先量出复制粘贴的成本
batching 把多条事件攒成一批再执行，会打乱「一次事件一条 trace」的可解释性。 出现明确的批量写入场景（如一天一次的全量扫描）时，按触发源做而不是按边做
拖拽画布 画布意味着图模型，图模型意味着 DAG 语义、布局存储、协同编辑；我们的图是显式声明的出口表，文本就能表达。 暂时不打算。这是与 n8n 的定位分界线，不是待办
任意代码执行 中枢一旦能存代码，就回到「中枢知道要跑什么」，安全边界直接失效。 不做。需要复杂逻辑就在节点本地写成一个声明了已定义能力的东西
中枢存第三方密钥 中枢存谁的密钥，谁就有动机把中枢变成攻击目标；凭据留在节点侧才符合边界。 不做。集成需要凭据时，凭据由节点自身环境提供
大量第三方集成 五十个集成是产品运营成本，不是内核能力；先把事件契约做稳。 内核稳定后按用户需求逐个加，优先 webhook 能覆盖的那批
运行期 DAG 校验 图是显式声明的出口表，环在配置期就看得见，画得出也查得出，静态检查在配置期已经做完；运行期再多一道 DAG 校验既换不来新的信息，还会和「允许成环」直接矛盾。运行期只靠 path 去重剪枝。 不做。「允许环」是有意的产品决定，不是待修的缺陷
跨组织共享 Tailscale 的 node sharing 是单独一层语义：把一个能力显式租给别的组织，要处理授权、撤销、计量。先把单组织的图画稳。 edges 不放跨组织边；将来用一张显式的共享表桥接
人工审批环节 审批需要挂起态、超时策略、审批人身份与通知重试，是另一套生命周期。 等「中断型任务」语义设计完成后再做，先用通知 + 人工触发替代

关键澄清：扇出做，收集不做

这两个词经常被混成一件事，其实是一个问题的两端。我们只做前一半，并且明确不做后一半。

扇出 · 本期做

回答的是「这个事件要引起几件事」。查表拿到 N 行就写 N 行任务，一次 INSERT，没有额外状态。

难度极低，收益直接：一个 PR 既派 agent 审查，也推手机通知。

收集 · 本期不做

回答的是「那几件事都回来了吗」。需要批次 id、计数器、菱形依赖、部分失败的判定标准。

难度高，而且一旦引入，任务就不再是独立的，整条链路都要围着批次重写。

没有收集，怎么实现「等一组都完成」？放在节点内部。A 在自己进程内并行、自己等待、自己汇总，最后回报中枢一个 result；对中枢来说这始终是一个任务。代价是 A 内部那层并行在 trace 上不可见。

预留的扩展点

edges 表本身已经是实现了的东西，不算预留。真正算留白的是下面五条：一条明确不留，一条在模型里不存在，一条只剩一句解释，两条留了位置。

条件路由 · 不预留
没有地方留，也不打算留。条件路由要的是一个表达式求值器，它会同时推翻三件事：中枢不解释用户逻辑、图可静态分析、「为什么没触发」可以只靠查表回答。硬把入口先留出来，等于给以后的自己一个把求值器装回来的方便。真要做是一次路由层重设计，不是填一个已经挖好的坑。
能力子集声明 · 不存在这个概念
不是「本期不做」，而是模型里没有这个位置。节点声明 review@1 只表示「我认得这个名字」； outputs 是它跑完可以报出的名字，不是它要实现的子功能——fix 和 clean 各自是独立能力， 由别的节点声明。所以「我只会 fix 不会 clean」这种说法本来就无处可写，也不需要预留列。
收集 join · 预留位置
位置留在任务行的 parent_task_id 上：子任务与根任务的关系现在就查得出来，真要做收集时分两步——建批次表、按 parent_task_id 回填历史分组，链路数据不用重算。同时配置里写 join / join_on 一律在校验期直接报错，不静默忽略（静默忽略会让人以为收集生效了，然后在生产里等一个永远不会来的结果）。
存储可替换 · 长期方向，本期不做
想要的东西：中枢只存最基础的数据，能力定义、任务、日志这些尽量落在用户自己那一侧， 由插件的接口来提供。这样中枢足够薄，数据主权归用户。
本期实际要做的只有一件事：把 internal/store 从具体类型收敛成接口。 现在 13 个包直接持有 *store.DB，62 个方法挂在它上面，不先收敛成接口，任何后端替换都无从谈起。 这一步和插件无关也该做——它是笔早欠下的技术债。
但有一条不能靠插件解决的物理约束：中枢必须能原子地读到路由要用的数据，否则就路由不了。 一次派发要在同一个事务里完成「查 edges → 校参数 → 建 N 个 tasks」， 租约、ack、心跳、重派同样要求这些状态在中枢手里。 把 edges 或 tasks 放到远端，等于每次派发跨一次网络、每次续租跨一次网络， 事务性和租约语义都会被拆散。所以「全部都外置」在实现上不成立， 能外置的是产出物（artifacts）、老事件归档和任务历史这三类。
动态扇出 fanout · 预留位置
位置留在两处：一是 edges 表天然就是 N 对 N——一行变多行就是变宽，不需要新的图结构；二是节点回报与派生新事件走同一个上报入口，以后要加新的派生类型，只需在载荷里加一个帧，不动连接、鉴权与重试逻辑。

一句话收尾：「本期做不到」是排期问题 —— 知道怎么做但还没做；「以后一定做」是已经写进路线的承诺 —— 而拖拽画布、任意代码执行、中枢存密钥不属于这两类，它们不是排期，是方向。
