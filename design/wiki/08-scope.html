本期范围

这一页把线画清楚：哪些能力本期就有、哪些明确不做、哪些留了扩展点但先不实现。范围不清的项目会变成 n8n 的劣化版，所以宁可现在写死。

本期做的

十一项。每一项都能落到具体的表、字段或状态机上，没有「后续再细化」的占位。

能力 本期做到的
事件 统一的 events 表记录 source / type / payload / trace_id / span_id，cron、webhook、watch 与外部 API 都写进同一张表。
规则 match 条件 + action，多个条件各自可解释；命中 0 条也记 trace，标 pruned 与原因。
扇出 多条规则同时命中则全部下发，一次 INSERT 写成 N 行任务，互不排斥。
接力 任务结果可以产生新事件，新事件再命中规则；allow_chain 显式开启才允许。
成环 允许成环（审查 → 修复 → 复审），用 path 里 rule_id 去重做剪枝，剪枝在 trace 上可见。
任务租约 TTL 30s、心跳 10s、max_attempts 3、退避 10s → 60s → 300s；pending → assigned → acked → running → succeeded | failed | canceled | abandoned。
节点池 两级：nodes 管身份与脑、node_instances 管执行器；三层并发上限取 min，派发按最少负载优先。
粘性路由 sticky_key = sha256(trace_id ∥ rule_id ∥ selector)，首次写入 node_pins 后一律查表；rebalance 只处理失效 pin。
版本钉住 规则、节点 manifest、注册表三对象 append-only 版本，trace 钉住不可变的版本 id（content hash），不钉时间。
六道闸 G1 allow_chain、G2 max_hops、G3 环检测、G4 max_tasks、G6 max_duration，默认收紧 + 代码硬顶。
通知 human sink：推手机，尽力而为、可丢、不回报结果；与 machine sink 永不混用。

本期不做的

每一条后面都写了「为什么现在不做」和「什么条件下会做」。不做不是因为难，大多数是因为做错了会让产品变成另一个东西。

不做的 为什么不做 什么时候可能做
收集 / join 要回答「那几件事都回来了吗」，得引入批次、计数、菱形依赖、部分失败语义，是整套新状态机。 等节点内并行这个替代方案被反复抱怨不够用时，再单独设计
batching 把多条事件攒成一批再执行，会打乱「一次事件一条 trace」的可解释性。 出现明确的批量写入场景（如一天一次的全量扫描）时，按触发源做而不是按规则做
拖拽画布 画布意味着图模型，图模型意味着 DAG 语义、布局存储、协同编辑；我们的规则是文本 + 参数。 暂时不打算。这是与 n8n 的定位分界线，不是待办
任意代码节点 中枢一旦能存代码，就回到「中枢知道要跑什么」，安全边界直接失效。 不做。需要复杂逻辑就在节点本地写成一个命名命令
中枢存第三方密钥 中枢存谁的密钥，谁就有动机把中枢变成攻击目标；凭据留在节点侧才符合边界。 不做。集成需要凭据时，凭据由节点自身环境提供
大量第三方集成 五十个集成是产品运营成本，不是内核能力；先把事件契约做稳。 内核稳定后按用户需求逐个加，优先 webhook 能覆盖的那批
DAG 校验 规则之间是运行期动态命中的，没有静态图可校验；能校验的只有 path，已经做了。 只有在真的引入静态流程图之后才有意义
多租户 UI 自托管单组织是当前形态，租户隔离会渗透到每张表和每条查询。 出现托管版需求时，先在数据层加 tenant_id，UI 随后
人工审批节点 审批需要挂起态、超时策略、审批人身份与通知重试，是另一套生命周期。 等「中断型任务」语义设计完成后再做，先用通知 + 人工触发替代
子流程复用 复用要求参数化与版本引用，会逼出模块系统，复杂度陡增。 规则数量到需要抽公共部分的规模时再做，届时复用规则版本对象

关键澄清：扇出做，收集不做

这两个词经常被混成一件事，其实是一个问题的两端。我们只做前一半，并且明确不做后一半。

扇出 · 本期做

回答的是「这个事件要引起几件事」。N 条规则命中就写 N 行任务，一次 INSERT，没有额外状态。

难度极低，收益直接：一个 PR 既派 agent 审查，也推手机通知。

收集 · 本期不做

回答的是「那几件事都回来了吗」。需要批次 id、计数器、菱形依赖、部分失败的判定规则。

难度高，而且一旦引入，任务就不再是独立的，整条链路都要围着批次重写。

没有收集，怎么实现「等一组都完成」？放在节点内部。A 在自己进程内并行、自己等待、自己汇总，最后回报中枢一个 result；对中枢来说这始终是一个任务。代价是 A 内部那层并行在 trace 上不可见。

预留的扩展点

不做不代表什么都不留。下面三处是刻意的留白：不实现能力，但把将来的入口放在正确的位置，避免以后靠改协议硬塞。

fanout 表不建
但留 parent_task_id
任务行上有父任务引用，子任务与根任务的关系现在就查得出来。真要做收集时分两步：建批次表、按 parent_task_id 回填历史分组，链路数据不用重算。
派生消息走单一接口
节点回报结果和节点派生新事件走同一个上报入口。要加新的派生类型，只需在载荷里加一个帧，不动连接、鉴权与重试逻辑 —— 长连接协议已经按「可扩展帧」设计。
join 字段写了直接报错
规则里出现 join / join_on 之类的字段，配置校验期直接拒绝并说明本期不支持。不静默忽略 —— 静默忽略会让人以为收集生效了，然后在生产里等一个永远不来的结果。

一句话收尾：「本期做不到」是排期问题 —— 知道怎么做但还没做；「以后一定做」是已经写进路线的承诺 —— 而拖拽画布、任意代码节点、中枢存密钥不属于这两类，它们不是排期，是方向。
