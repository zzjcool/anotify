本期范围

这一页把线画清楚：哪些能力本期就有、哪些明确不做、哪些留了扩展点但先不实现。范围不清的项目会变成 n8n 的劣化版，所以宁可现在写死。

本期做的

十二项。每一项都能落到具体的表、字段或状态机上，没有「后续再细化」的占位。

能力 本期做到的
事件 统一的 events 表记录 source / type / payload / trace_id / span_id，cron、webhook、watch 与外部 API 都写进同一张表。
出口表（edges） 显式声明 (能力, 出口) → 能力 三元组，派发就是一次索引查询：查得到就全部下发，查不到就到头。无 match 求值、无条件表达式、无优先级。
扇出 查表返回 N 行就全部下发，一次 INSERT 写成 N 行任务，互不排斥。
接力 执行器回报的 out 拿去查表得到下游能力；allow_chain 显式开启才允许。
成环 允许成环（审查 → 修复 → 复审）；环在配置期由 edges 静态可见，运行期用 path 里能力名去重做剪枝，剪枝在 trace 上可见。
任务租约 TTL 30s、心跳 10s、max_attempts 3、退避 10s → 60s → 300s；pending → assigned → acked → running → succeeded | failed | canceled | abandoned。
执行器池 两级：runners 管身份与脑、runner_instances 管实例；三层并发上限取 min，派发按最少负载优先。
粘性路由 按能力声明开启（manifest.capabilities[].sticky），默认纯负载均衡。开启时 sticky_key = sha256(trace_id ∥ capability ∥ selector)，写 runner_pins 后一律查表；rebalance 只处理失效 pin。
版本钉住 图配置（含 edges）、执行器能力清单、注册表三对象 append-only 版本，trace 钉住不可变的版本 id（content hash），不钉时间。
六道闸 G1 allow_chain、G2 max_hops、G3 环检测、G4 max_tasks、G6 max_duration，默认收紧 + 代码硬顶。
出口回报 执行器在 result 里回报 out（出口名或 null，跑完才知道），收敛只认这个，不反推业务。缺失 out 按未回报计（保守，不收敛）。
通知 推手机：end 角色，out 恒为 null。尽力而为、可丢。

本期不做的

每一条后面都写了「为什么现在不做」和「什么条件下会做」。不做不是因为难，大多数是因为做错了会让产品变成另一个东西。

不做的 为什么不做 什么时候可能做
条件路由 / 表达式路由 不做。路由靠显式出口，不支持 if payload.x > 5 then ... 这种条件。条件路由需要在中枢里放一个表达式求值器，而且一旦路由依赖 payload，图就不再可静态分析——配置期看不到哪些边会被走、「为什么没触发」也不再是查表能回答的问题。 明确有需求再说。做的话是路由层重设计，不是加一个开关
动态边（运行期修改路由表） 不做。edges 变动需要新版本（走版本钉住）：旧 trace 钉旧 hash，新 trace 钉新 hash。运行期改表会让「当时它为什么走这条路」变得不可复现。 不做。改路由就发新版本，代价是一行版本号
收集 / join 要回答「那几件事都回来了吗」，得引入批次、计数、菱形依赖、部分失败语义，是整套新状态机。 等「执行器内部并行」这个替代方案被反复抱怨不够用时，再单独设计
batching 把多条事件攒成一批再执行，会打乱「一次事件一条 trace」的可解释性。 出现明确的批量写入场景（如一天一次的全量扫描）时，按触发源做而不是按边做
拖拽画布 画布意味着图模型，图模型意味着 DAG 语义、布局存储、协同编辑；我们的图是显式声明的出口表，文本就能表达。 暂时不打算。这是与 n8n 的定位分界线，不是待办
任意代码执行 中枢一旦能存代码，就回到「中枢知道要跑什么」，安全边界直接失效。 不做。需要复杂逻辑就在执行器本地写成一个已申报的能力
中枢存第三方密钥 中枢存谁的密钥，谁就有动机把中枢变成攻击目标；凭据留在执行器侧才符合边界。 不做。集成需要凭据时，凭据由执行器自身环境提供
大量第三方集成 五十个集成是产品运营成本，不是内核能力；先把事件契约做稳。 内核稳定后按用户需求逐个加，优先 webhook 能覆盖的那批
运行期 DAG 校验 图是显式声明的出口表，环在配置期就看得见，画得出也查得出，静态检查在配置期已经做完；运行期再多一道 DAG 校验既换不来新的信息，还会和「允许成环」直接矛盾。运行期只靠 path 去重剪枝。 不做。「允许环」是有意的产品决定，不是待修的缺陷
多租户 UI 自托管单组织是当前形态，租户隔离会渗透到每张表和每条查询。 出现托管版需求时，先在数据层加 tenant_id，UI 随后
人工审批环节 审批需要挂起态、超时策略、审批人身份与通知重试，是另一套生命周期。 等「中断型任务」语义设计完成后再做，先用通知 + 人工触发替代
子流程复用 复用要求参数化与版本引用，会逼出模块系统，复杂度陡增。 能力数量到需要抽公共部分的规模时再做，届时复用图配置版本对象

关键澄清：扇出做，收集不做

这两个词经常被混成一件事，其实是一个问题的两端。我们只做前一半，并且明确不做后一半。

扇出 · 本期做

回答的是「这个事件要引起几件事」。查表拿到 N 行就写 N 行任务，一次 INSERT，没有额外状态。

难度极低，收益直接：一个 PR 既派 agent 审查，也推手机通知。

收集 · 本期不做

回答的是「那几件事都回来了吗」。需要批次 id、计数器、菱形依赖、部分失败的判定标准。

难度高，而且一旦引入，任务就不再是独立的，整条链路都要围着批次重写。

没有收集，怎么实现「等一组都完成」？放在执行器内部。A 在自己进程内并行、自己等待、自己汇总，最后回报中枢一个 result；对中枢来说这始终是一个任务。代价是 A 内部那层并行在 trace 上不可见。

预留的扩展点

edges 表本身已经是实现了的东西，不算预留。真正算留白的只有下面三条：一条明确不留，两条留了位置。

条件路由 · 不预留
没有地方留，也不打算留。条件路由要的是一个表达式求值器，它会同时推翻三件事：中枢不解释用户逻辑、图可静态分析、「为什么没触发」可以只靠查表回答。硬把入口先留出来，等于给以后的自己一个把求值器装回来的方便。真要做是一次路由层重设计，不是填一个已经挖好的坑。
收集 join · 预留位置
位置留在任务行的 parent_task_id 上：子任务与根任务的关系现在就查得出来，真要做收集时分两步——建批次表、按 parent_task_id 回填历史分组，链路数据不用重算。同时配置里写 join / join_on 一律在校验期直接报错，不静默忽略（静默忽略会让人以为收集生效了，然后在生产里等一个永远不会来的结果）。
动态扇出 fanout · 预留位置
位置留在两处：一是 edges 表天然就是 N 对 N——一行变多行就是变宽，不需要新的图结构；二是执行器回报与派生新事件走同一个上报入口，以后要加新的派生类型，只需在载荷里加一个帧，不动连接、鉴权与重试逻辑。

一句话收尾：「本期做不到」是排期问题 —— 知道怎么做但还没做；「以后一定做」是已经写进路线的承诺 —— 而拖拽画布、任意代码执行、中枢存密钥不属于这两类，它们不是排期，是方向。
