总览

这页先给结论：Anotify 现在是什么、由哪几层组成、和 workflow 引擎差在哪、剩下九页各讲什么。看完再挑感兴趣的进。

一句话

Anotify 从一个「Agent 完成通知终端」，升级为事件中心 + 执行节点：触发源产生的事件都进同一本事件日志，可解释的规则决定它引起几件事，最后落成机器上的一个任务，或者你手机上的一次震动。

五层结构

整条管道只有五层，每层职责单一：触发源不管规则，规则不管执行，任务不管命令长什么样。通知和 trace 不是层，是挂在旁边的两条出路。

触发源cron · webhook · watch
→
事件日志source · type · payload
→
规则match + action
→
任务租约 · 重试 · 状态机
→
节点node agent 执行 argv

旁挂（不是层，是两条出路）

通知 · human sink推手机 · 尽力而为 · 不回报
trace · 可观测为什么触发 · 走了哪条路
两类 sink 永不混用：human sink 是可丢的通知，machine sink 是必须回报结果的节点任务。同一条规则可以同时指向两者，它们各自记账。

一次事件如何变成手机震动

最短的一条路只有四步，中间不经过任何用户脚本：事件进来、进日志、规则命中、推送出去。

PR 合并 → webhooksource: github
→
写入事件日志type: pr.merged
→
规则命中action: 推手机
→
手机震动human sink
把第三条规则的 action 换成「派任务」，第三个盒子就变成「任务下发」，最后一个盒子换成 node agent 执行后结果回流成新事件。两条路共用同一个事件日志、同一个 trace。

为什么不是 workflow 引擎

它借用了 workflow 引擎的几个名字（触发、条件、动作），但要你写的只有「命中什么、做什么」。整条链路的形状不由画布规定，执行细节留在节点自己的进程里。

维度 本设计 n8n / Temporal 类
编排从哪来 规则是数据：match + action 存在库里，可版本化、可解释 画布上的 DAG，或代码里的 workflow 定义
执行与凭据 命令注册在你机器上，凭据永不出本机；中枢只发 {kind, name, params} 执行在平台 worker 或你部署的集群；集成凭据常存在平台侧
时间尺度 没有 workflow 运行时长上限，靠租约 + max_duration 收口 受运行期上限与执行历史大小的约束
失败长什么样 trace 上逐条件可见：哪条规则剪了、path 为什么断、卡在哪一步 翻 workflow history 或执行日志，人肉还原
本期边界 不做拖拽画布、任意代码节点、DAG 校验、join 收集 这些正是它们的主场
不比拼集成数量。定位是可解释的自动化——事件为什么触发、走了哪条路、卡在哪一步。拖拽画布、任意代码节点、中枢存密钥、几十个现成集成，这些不做，避免变成 n8n 的劣化版。
