总览

这页先给结论：Anotify 现在是什么、由哪几层组成、和 workflow 引擎差在哪、剩下九页各讲什么。看完再挑感兴趣的进。

一句话

Anotify 从一个「Agent 完成通知终端」，升级为事件中心 + 节点网络：能力先定义（中枢侧、版本化），触发源产生的事件都进同一本事件日志，中枢拿它去查一张显式的出口表，得到若干个下游能力，最后派给声明了那个能力的一台机器、落成一个任务，或者你手机上的一次震动。

六层结构

整条管道有六层，每层职责单一：能力定义不管运行，触发源不管路由，出口表不管执行，任务不管命令长什么样。通知和 trace 不是层，是挂在旁边的两条出路。

能力定义name@版本 · params_schema · outputs
→
触发器无人声明 → origin
→
事件日志type · payload
→
出口表能力 → 能力
→
任务租约 · 状态机
→
节点一台声明了能力的机器

旁挂（不是层，是两条出路）

通知 · end推手机 · 尽力而为 · 不回报
trace · 可观测走了哪条边 · 为什么到头
第一层是能力定义，它先于一切。能力规定了参数结构、出口名；节点只能声明自己有哪些已定义的能力，不能自己发明能力名，也不能自己加出口。第四层（出口表）是唯一的路由依据：它没有条件、没有优先级、也不需要求值：把（能力, 出口）这一对填进去，返回几行就往几个能力派，而不是往几台机器派。最后一层是节点：它只声明「我有 review@1」，origin / pipe / end 是从这份声明算出来的，不手写。终点也分两种：推手机是可丢的通知（outputs 为空 → end），干活的任务必须回报结果（pipe），它们各自记账。

一次事件如何变成手机震动

最短的一条路只有四步，中间不经过任何用户脚本：事件进来、进日志、查一次出口表、推送出去。

PR 合并 → webhook能力 github@1 · 无人声明 → origin
→
写入事件日志type: pr.merged
→
查出口表(github@1, pr.merged)
→
手机震动end · notify.phone@1
把这条边指向的能力从 notify.phone@1 换成 implement@1，第三个盒子就变成「用 params_schema 校参数 → 找声明了这个能力的节点 → 建任务」，最后一个盒子换成 pipe 执行后回报出口、再查一次表。两条路共用同一本事件日志、同一个 trace_id。

为什么不是 workflow 引擎

它借用了 workflow 引擎的几个名字（触发、节点、边），但整条链路上没有一处需要求值：路由靠查表，边的存在与否就是全部答案。形状不靠画布规定，执行细节留在节点自己的进程里。

维度 本设计 n8n / Temporal 类
路由 显式出口表，查表派发，没有条件求值 画布上的 DAG，或代码里的 workflow 定义
谁能定义节点 能力先定义（中枢侧、版本化），节点只能声明自己有哪些已定义的能力，拿不到出口命名权 节点自由组合：谁拖画布谁就能随手加一个新节点，出口自己编
执行与凭据 声明了能力的节点跑在你机器上，凭据永不出本机；中枢只发 (能力, 版本, 参数) 执行在平台侧或你部署的集群；集成凭据常存在平台侧
时间尺度 没有 workflow 运行时长上限，靠租约 + max_duration 收口 受运行期上限与执行历史大小的约束
失败长什么样 trace 上逐条可见：查表查到了哪几行、哪条边不存在、path 为什么被剪 翻 workflow history 或执行日志，人肉还原
本期边界 不做拖拽画布、任意代码执行、DAG 校验、join 收集 这些正是它们的主场
不比拼集成数量。定位是可解释的自动化——事件为什么触发、走了哪条边、卡在哪一步。拖拽画布、任意代码执行、中枢存密钥、几十个现成集成，这些不做，避免变成 n8n 的劣化版。
