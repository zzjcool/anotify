产品

Anotify · 产品设计

Agent 完成任务后，把通知自动送到你的所有设备。以下是产品定位、目标用户、核心功能与使用流程。

🎯
产品定位

一个「完成即通知」的 Agent 通知平台。Agent 结束工作后通过事件 Hook 自动上报， 后端用 Web Push 把结果推送到用户的手机 / 桌面 / 网页，让用户无需盯着终端就能知道任务是否完成。

👤
目标用户

使用 AI 编码助手（pi、Claude Code 等）、CI 流水线、后台任务的开发者。 希望任务在后台跑时能及时收到完成 / 失败通知，而不是频繁刷新。

💎
核心价值

无需密码（Passkey）；无需轮询；支持 iOS / Mac / PC / Android 全端； 单二进制易部署；提供工作台管理通知与上报 Key。

核心功能
Agent 完成通知核心

监听 Agent 结束事件，自动上报并推送完成 / 失败 / 中断状态。

Passkey 无密码登录鉴权

输入用户名 + 生物识别 / 设备密钥一键登录，无需密码。

API Key 上报接入

每个工作台生成一个 Key，Agent / 脚本用它 POST 上报通知。

多端订阅推送送达

iOS Safari（已验证）、Mac、PC、Android 均可订阅，一次推送全端到达。

多端管理

鉴权 · 多设备

Passkey 跨设备登录怎么处理？

用户在电脑创建 Passkey，想在手机上登录时，手机不一定认得出电脑的 Passkey。 关键在于 Passkey 是否「同步」。Anotify 同时支持以下三层方案，保证任何情况都能登录。

方案 A · 平台同步（首选）依赖系统 Passkey 同步

Passkey 若由平台同步器管理——Apple iCloud 钥匙串、Google 密码管理器、Microsoft 账户——会被自动同步到该用户同一生态的所有设备。 电脑创建的 Passkey 会出现在手机 / iPad 上（同一 Apple ID 或 Google 账户），用户无需任何额外操作，直接识别登录。 （多数用户的默认场景）

方案 B · 一次性连接引导新设备（推荐）先临时获得登录态，再绑定新 Passkey

当新设备无法识别已有 Passkey（跨生态或不同步）时，Anotify 提供「添加新设备」引导：用户在已登录的电脑上点「添加新设备」， 系统生成一个一次性连接（带短时效的临时登录 token）。 手机打开这个连接 → 临时获得登录态 → 引导为这台手机创建一个绑定当前账号的新 Passkey。 绑定成功后手机即可独立免密登录，临时连接随之作废。

方案 C · 恢复码（终极兜底）一次性恢复码备用登录

注册成功后，Anotify 生成一组一次性恢复码（类似 2FA 备用码），用户妥善保存。 若用户丢失所有设备、无法用 Passkey 登录，可用用户名 + 恢复码登录，再为新设备注册新 Passkey。 （恢复码一次性使用，用后作废，可重新生成）

① 事件触发（Agent 端 · pi 扩展）Hook

用户在 pi 安装 Anotify 扩展，扩展监听 agent_settled 事件——该事件在 Agent 真正结束（无重试、无后续任务）后触发。 扩展自动收集 agentId / cwd / status / durationMs / model 等上下文。 也可以显式调用自定义工具 notify 上报更丰富的内容（中间进度、自定义标题）。

② 上报（HTTP 契约）接口 
POST https://api.anotify.dev/v1/notify

Content-Type: application/json

{ "agentId": "build-01", "sessionId": "sess_8f3a", "cwd": "/repo",

  "body": "构建成功", "model": "claude-4", "link": "pi://sess_8f3a" }
③ 鉴权 + ④ 路由（服务端）后端

Go 后端用 API Key 的 哈希 在数据库查找对应工作台 → 定位所属用户。 然后查询该用户所有已订阅设备（iOS / Mac / PC / Android 的 push endpoint 与密钥）。 若无已订阅设备，则返回 400 提示先订阅。

⑤⑥⑦ Web Push 推送（服务端 → Apple 服务）推送

服务端用 web-push 对通知载荷做 端到端加密（用订阅的 p256dh / auth 密钥）， 用 VAPID 私钥签名，POST 到设备的 endpoint。 对 iOS / Mac 是 Apple 的 web.push.apple.com，对 PC / Android 是 FCM 或各浏览器服务。

⑧⑨ 接收与显示（设备端）前端

设备浏览器已注册 Service Worker（sw.js）并订阅。 Apple 服务通过 APNs 下发 → 浏览器唤醒 Service Worker → 触发 push 事件 → 调用 showNotification() 展示通知横幅。 即使 App 已切后台或被关闭也能收到——这是 Web Push 的核心价值。

⚠️ iOS 前提 必须先把站点「添加到主屏幕」standalone 运行，否则 Safari 不提供 Notification / Push API。
✅ 已验证 本仓库已完成 iOS Safari 的订阅 + 服务端推送全链路实测，后台状态也能送达。
🔒 安全 载荷端到端加密，API Key 仅存哈希，VAPID 私钥只在服务端。

架构 · 核心决策

消息队列抽象 · 数据库先行，预留 MQ 演进

Anotify 的通知推送本质是一套 pub/sub 消息队列。 为兼顾「单二进制易自托管」与「未来可扩展」，我们把队列抽象成接口： 前期用 SQLite 实现，后期可平滑替换为 NATS / Redis Streams / Kafka，业务代码零改动。

它和 MQ 是一回事 · 概念映射
MQ 概念 Anotify 对应
Producer 生产者 Agent（POST /v1/notify 上报）
Message 消息 Notification（title/status/body/deviceTags…）
Topic / Routing key deviceTags 标签路由键
Broker / Exchange 后端路由分发器
Consumer 消费者 WebSocket 长连接 + Web Push 订阅（两类消费端）
Consumer group 一个用户的所有接收设备
Offset 位移 Last-Event-Id / resume_token
Ack 确认 WebSocket 的 ack 帧
Retention / TTL 24h 重放缓冲 · 通知 ttl
Broker 抽象接口（Go）

抽象边界划在 Publish / Subscribe / Ack / Replay 上，不在 HTTP 或 WS 处理器上——这样两条接收通道都只是 Broker 的消费者。 

type Message struct {
    ID         string    // 消息 ID
    UserID     string    // 所属用户
    Title      string    // 标题
    Status     string    // success|error|interrupted|info|warning
    Body       string    // 正文
    Link       string    // 深链
    DeviceTags []string  // 路由键（= topic）
    Priority   string    // 优先级
    TTLSeconds int       // 有效期
    CreatedAt  time.Time
}

type Broker interface {
    // 生产：Agent 上报 → 入队
    Publish(ctx context.Context, msg *Message) error

    // 消费：订阅某用户的通知流；tags 为空 = 全订阅
    Subscribe(ctx context.Context, userID string, tags []string) (Subscription, error)

    // 确认：标记消息已被某消费者处理（at-least-once）
    Ack(ctx context.Context, msgID, consumerID string) error

    // 重放：断线续传，返回 sinceID 之后未确认的消息
    Replay(ctx context.Context, userID, sinceID string, limit int) ([]*Message, error)

    Close() error
}
两条接收通道都是 Broker 的消费者 
 Agent ─POST→ /v1/notify ─→ broker.Publish(msg)
                                          │
                              ┌───────────┴───────────┐
                              ▼                       ▼
                      WS 派发器 (消费者1)        Push 派发器 (消费者2)
                      Subscribe(userID, tags)   Subscribe(userID, nil)
                              │                       │
                      写 WebSocket 帧            逐设备 Web Push 发送
标签路由 → Broker 侧 订阅时按 deviceTags 过滤，相当于 topic subscription，只把匹配的消息推给该消费者。
状态过滤 → 消费者侧 all/error/success 是每台设备的偏好，由派发器在发送前逐设备判断，与标签路由相互独立。
演进路径 · 数据库先行，按需接 MQ
现在SQLiteBroker

单机自托管默认。单二进制零依赖：messages 表即队列，进程内派发 + 定时清理过期消息。个人/小团队通知量完全够用。

中期NATS / Redis Streams

多副本部署、接收插件变多时接入。轻量级持久订阅，运维成本低，适合大多数规模。

远期Kafka / RabbitMQ

大规模、多团队、高吞吐场景。生态最全，但自托管较重，作为可选而非默认。

为什么数据库先行是对的： Anotify 的核心价值是「单二进制易自托管」。若一开始强依赖 Kafka/NATS，会劝退绝大多数自托管用户。 接口抽象让早期用户不被锁死——规模上去后改配置注入 MQ 实现即可，HTTP/WS 处理器与业务逻辑零改动。 这也是 Gitea（进程内→Redis 队列）、n8n（内存→Bull/Redis queue mode）验证过的成熟路径。
落地 · 表结构

SQLiteBroker 实现 · 表结构 / 索引 / 过期清理

Phase 1 单机部署时，WS 连接与 notify 处理器在同一进程，因此队列是「两条路径」的合体： 进程内广播负责实时（快），DB 表负责回放 / 历史 / 崩溃恢复（稳）。 Broker 接口隐藏这个二分，换 MQ 时由 MQ 同时接管两条路径。

① 初始化与消息表
-- 连接初始化 PRAGMA
PRAGMA journal_mode = WAL;      -- 单写多读：notify 写入时，WS 派发器可读
PRAGMA synchronous  = NORMAL;   -- 持久性/性能平衡
PRAGMA busy_timeout = 5000;     -- 写锁等待 5s
PRAGMA foreign_keys = ON;       -- deliveries 级联删除

-- messages：消息日志（队列 + 历史，单一事实源）
CREATE TABLE messages (
    id           TEXT PRIMARY KEY,             -- KSUID，如 "ntf_01J8XA…"（全局唯一、时间有序）
    user_id      TEXT NOT NULL,                -- 分区键：按用户隔离
    seq          INTEGER NOT NULL,             -- 每用户单调递增序号（= replay 的 offset）
    title        TEXT NOT NULL,
    status       TEXT NOT NULL,                -- success|error|interrupted|info|warning
    body         TEXT NOT NULL DEFAULT '',
    link         TEXT NOT NULL DEFAULT '',
    device_tags  TEXT NOT NULL DEFAULT '[]',   -- JSON 数组（路由键，broker 侧过滤）
    priority     TEXT NOT NULL DEFAULT 'normal',
    ttl_seconds  INTEGER NOT NULL DEFAULT 86400,
    payload      TEXT NOT NULL,                -- 完整 JSON（含 metadata/agentId 等未规范化字段）
    created_at   INTEGER NOT NULL,             -- unixepoch 秒
    expires_at   INTEGER NOT NULL,             -- created_at + ttl（可投递截止）
    UNIQUE (user_id, seq)
);
② 持久消费者位移
-- durable consumer（给稳定插件用）
CREATE TABLE consumer_offsets (
    consumer_id  TEXT NOT NULL,             -- 如 "home-bridge"
    user_id      TEXT NOT NULL,
    last_seq     INTEGER NOT NULL DEFAULT 0,-- high-water mark
    updated_at   INTEGER NOT NULL,
    PRIMARY KEY (consumer_id, user_id)
);
③ 投递记录（观测性）
-- 仪表盘 "3/4 设备已送达" 的数据源
CREATE TABLE deliveries (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id   TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    consumer_id  TEXT NOT NULL,             -- 设备 / 连接
    channel      TEXT NOT NULL,             -- webpush | websocket
    status       TEXT NOT NULL,             -- pending|sent|delivered|acked|failed
    error        TEXT NOT NULL DEFAULT '',  -- 失败原因（如 410 Gone）
    attempts     INTEGER NOT NULL DEFAULT 0,
    created_at   INTEGER NOT NULL,
    updated_at   INTEGER NOT NULL
);
索引（就 3 个，各有明确用途） 
CREATE UNIQUE INDEX idx_messages_user_seq     ON messages(user_id, seq);       -- 回放/按用户读取的核心
CREATE        INDEX idx_messages_user_created ON messages(user_id, created_at); -- 历史列表 + 统计 + 保留清理
CREATE        INDEX idx_messages_expires      ON messages(expires_at);          -- 可投递性检查
CREATE        INDEX idx_deliveries_msg        ON deliveries(message_id);
CREATE        INDEX idx_deliveries_consumer   ON deliveries(consumer_id, updated_at);

device_tags 是 JSON 数组，不走 SQL 索引——标签过滤在派发器进程内做（个人量级足够）。 将来若需在 SQL 层按标签查，再拆 message_tags(message_id, tag) 关联表（现在属过度设计）。

核心

前后端路径分离 · 为 CDN 缓存加速设计

Anotify 采用 静态资源与 API 路径彻底分离 的架构：前端产物部署到独立静态路径， 可整体交给 CDN 做长缓存；后端 API 走独立路径，响应不被缓存、保证实时性。 这样既能利用 CDN 全球加速大幅降低静态资源加载耗时，又不会破坏通知/订阅等动态接口的时效性。

🛣️静态 / 动态 分域名

前端静态资源挂在 cdn.anotify.dev（走 CDN，长缓存），API 走 api.anotify.dev（不缓存）。同一份 Go 二进制，路由按路径 / Host 分发。

🗃️embed.FS 内嵌前端

构建期把前端 dist/ 用 go:embed 打进二进制，单文件分发；运行时按需开启 CDN 前缀重写，开发/生产零切换成本。

🖼️Content-Hash 指纹

打包工具给 JS/CSS 文件名加内容哈希（app.a1b2c3.js），CDN 可 无限期缓存（immutable），发版只换文件名。

🧭API 版本化

所有动态接口带 /v1 前缀（/v1/notify），与静态资源路径不冲突，便于未来升级与缓存策略按前缀区分。

架构

部署与请求拓扑

静态资源链路（CDN 缓存）
浏览器 / Agent → CDN
cdn.anotify.dev → Origin
/static/* 命中缓存 90%+
动态接口链路（不缓存 / 仅边缘）
Agent / 前端 → 网关 / LB
api.anotify.dev → Go API
/v1/* → SQLite 实时 · 无缓存
CDN 带来的性能收益（估算）
首屏加载：静态资源走 CDN，全球边缘节点就近返回，减少 60~80% 加载耗时
Origin 压力：静态请求命中缓存，回源率 < 10%，Go 服务只处理 API
发版平滑：哈希文件名 + immutable，旧缓存自动失效，无缓存穿透风暴
路径分离

路径约定与路由分发

静态资源路径 cdn 
/static/
├── index.html
├── assets/
│   ├── app.a1b2c3.js      # 内容哈希
│   ├── app.f4e5d6.css
│   └── logo.7a8b9c.svg

可整体上 CDN，配置 Cache-Control: public, max-age=31536000, immutable（哈希文件）。index.html 短缓存 + 协商，SW 注册路径固定。
API 路径 api 
/v1
├── auth/register      POST · Passkey 注册
├── auth/login         POST · Passkey 登录
├── workspaces         GET/POST
├── workspaces/:id/key GET · 生成上报 Key
├── devices            GET/POST · 订阅管理
├── notify             POST · Agent 上报
└── notifications      GET · 历史记录
设置 Cache-Control: no-store，保证通知实时、权限即时校验。与静态路径完全隔离，互不干扰缓存策略。
Go 服务端如何分发（单二进制内） 
func main() {
    mux := http.NewServeMux()
    mux.Handle("/v1/", authMiddleware(apiHandler())) // 动态 API
    mux.Handle("/static/", cacheMiddleware(staticHandler())) // 静态资源

    // 访问静态资源时，按配置重写 CDN 前缀
    //   dev:   /static/...  → 本地 embed.FS
    //   prod:  /static/...  → cdn.anotify.dev/static/...（CDN 优先回源）
    http.ListenAndServe(":8080", mux)
}
开发环境直接本地服务 embed 资源；生产环境把 static 交 CDN，API 原样走 Go。同一份代码，通过环境变量切换 CDN 前缀，无需改业务逻辑。
缓存策略

CDN 缓存分级

不可变资源
/static/assets/*.js|css|img
immutable max-age=31536000

内容哈希命名，CDN 缓存 1 年，命中即返回，永不回源。发版 = 换新文件名。

入口文档
/static/index.html
max-age=60 etag 协商

短缓存 + ETag，保证新版本资源引用能尽快被拿到，又不至于每次全量回源。

动态 API
/v1/*
no-store

完全禁止缓存，保证通知、鉴权、订阅的实时与一致。可加边缘 WAF / 限流。

回源率对比：路径分离 vs 未分离
✅ 分离后：静态回源率 < 10%，API 全实时，互不干扰
❌ 未分离：静态被长缓存会误伤 API，或 API 不缓存拖累静态，两难
📌 结论：路径/域名分离是 CDN 加速的前置条件，一次设计，长期受益
