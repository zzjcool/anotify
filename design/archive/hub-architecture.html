01 — 为什么要转

一条管道，对比一条闭环

旧产品的每一步都是单向的：任务结束 → 通知人。它不知道「谁在干活」「成没成」「要不要重试」。 新产品把同一份基础设施变成闭环，通知只是闭环的一个出口。

⚠️
这不是重构，是产品转向。 旧产品是管道（无闭环），新产品有闭环（谁执行、成没成、要不要重试）。 好消息：Web Push、Passkey 认证、设备管理、构建链、19 套 e2e 全部保留， 一行不用改。

03 — 一次事件的旅程

点开每一步看细节

场景：GitHub 上有 PR 被打开。左列是 8 个时刻，右侧是那一步实际发生的事情， 以及这一步的 trace 字段长什么样 —— 让你看到 trace 是怎么一层层长出来的。

外部系统POST /v1/in/github/src_8aK

GitHub 在 PR 被打开时向中枢推一条 webhook。中枢用 source 级 secret 校验 X-Hub-Signature-256，验不过直接 401，不进事件表。 

POST /v1/in/github/src_8aK
X-Hub-Signature-256: sha256=9f2c…
X-GitHub-Event: pull_request

{ "action": "opened",
  "repository": { "full_name": "acme/api" },
  "pull_request": { "number": 123, "user": { "login": "alice" },
                    "head": { "ref": "feat/x" },
                    "title": "重构事件层" } }
这一步只做两件事：验签、判重。不做解析。
TRACE 字段 trace 尚未建立
验签通过后，③ 写入事件表的那一刻才产生 trace_id —— 所以这一步还没有 trace。
中枢source 的抽取映射

原始 payload（可能 20–100KB）不解析、只透传。 另外从里面抽出少量字段放到 attributes —— 这是唯一可查询、可路由、可索引的一层。 

// 抽取映射（source 上配置）
{ "repo":   "repository.full_name",   → acme/api
  "author": "pull_request.user.login", → alice
  "branch": "pull_request.head.ref",   → feat/x
  "number": "pull_request.number" }     → 123

// 去重键：(tenant, source, dedupe_key) UNIQUE
dedupe_key = sha256("pull_request:123:opened")
GitHub 重发同一条 webhook → 静默去重返回 200。不会重复执行、不会重复花钱。
TRACE 字段 仍未建立
这一步只算抽取与去重，还没落库 —— 所以既没有 trace_id 也没有 span。
③ 写入事件表时，中枢才在当前事务里生成 trace_id 与根 span_id。
中枢INSERT INTO events

事务内生成 seq（全局单调），这个整数同时是控制台 SSE 和节点 WS 的续传游标。 payload 超过 64KB 就截断并记下完整原文的哈希。 

{ "id": "evt_2fQ…", "seq": 91824,
  "source": "github", "type": "pr.opened",
  "subject": "acme/api#123",
  "summary": "alice 打开了 PR：重构事件层",
  "attributes": { "repo": "acme/api", "author": "alice" },
  "payload": { … }, "payload_truncated": 0,
  // ★ trace 元数据是普通字段（§12.2.4）
  "trace_id": "trc_7f2", "span_id": "spn_0000",
  "parent_span_id": null, "hop": 0,
  "rule_version_id": "reg_…T101500Z" }

04 — 接力

A 完成 → B 继续 → B 完成 → 通知人

这是本产品从「单跳触发器」变成「可编排中枢」的关键。但接力会引入图环路 —— 一条 webhook 能放大成 N 次 LLM 调用，所以它默认关闭、显式开启、全程可归因（见下一节）。

hop 0
evt_1 · github / pr.opened
acme/api#123
↓ 规则 rev-pr 命中（allow_chain 无关，源头事件）
hop 1
🔍 tsk_A 审查 · laptop
succeeded
→ artifacts: branch feat/x/review
↓ 派生 agent/task.succeeded（default_notify=false）
hop 2
🔧 tsk_B 修复 · desktop
succeeded
→ artifacts: commit a1b2c3d
↓ 派生 agent/task.succeeded（同样不通知）
hop 3
✅ tsk_C 测试 · desktop
succeeded
🔔 chain.settled → 唯一一条通知
「rev-pr → fix → test 全部完成，用时 23 分钟」
无 pending / leased / running 任务 → correlation = settled
✓ 传指针，不传载荷
// B 拿到的不是 A 的上下文
// 而是 A 留下的世界状态
prompt: "按审查意见修复"
      + "分支 feat/x/review"
      + "commit a1b2c3d"
agent 通过共享世界状态协作，比搬运上下文更可靠、更省 token、更可审计。
✗ 不能做的事
  • · 把 A 的长文本塞进 B（撞 8KB 上限）
  • · 中枢存 A 的完整日志
  • · 在规则里写代码做分支
链失败时
默认只重试失败的那一跳，不重跑整条链（A、B 的副作用已经真实发生了）。 失败立即通知，不等收敛。
05 — 本期范围

扇出做，收集不做

一个 PR 上来，既要派 agent 去审查，也要给我手机推一条通知。 这两件事毫无关系，必须都发生。
所以扇出本期就有。真正难的不是扇出去，是「收回来」—— 那个我们不做。

扇出和收集是两个正交的问题（我一开始把它们混成了一个）
扇出（这个事件要引起几件事）
✅ 无条件支持 —— N 条规则命中就派 N 个任务，N 是多少我们不管
难度：极低（一次 INSERT 多行）
收集（那几件事都回来了吗）
❌ 本期不做 —— 没有汇聚、没有批次计数、没有 join
难度：高（批次 / 计数 / 菱形 / 部分失败）
本期的形状：任意扇出、任意成环，但没有收集
e1 PR 打开 → 命中 3 条规则
t1a agent 审查 → e2a … t1b 推手机 ✓ t1c 写日志 ✓
三条线各自独立延伸、互不等待 —— 没有任何机制把它们「收」到一起
为什么扇出这么便宜
只是「多写几行」。不需要额外表、额外 API、计数、seal
为什么收集这么贵
要记账、要判断「到齐了吗」、要处理部分失败、要防重复触发
本期删除
✗汇聚 / 批次计数 / batching.windowMs
✗规则里的 join 字段（写了直接报错）
✗fanout.* 动态扇出消息（扇出靠规则命中，不需要消息）
✗规则里的 join 字段（写了直接报错）
本期保留（别删错）
✓branchBudget 扇出额度 + G3b 闸 —— 扇出本期就有
✓parent_task_id / inputs — 扇出的 N 个任务共享同一父
✓hop 和 depth 两个字段 — 现在相等，分叉后才分开
✓OTel 的 trace_id / span_id / parent_span_id
✓node_pins 粘性路由 — 同链连续任务落同一机器
没有收集，怎么实现「等一组都完成」 放到节点里
中枢看到的
派 1 个任务给 A、收 1 个 result。完全不知道 A 内部开了 3 个并行分支。
节点 A 内部做的
并行启动 3 个子任务 → 自己等它们都返回 → 汇总 → 回报一个 result
好处
中枢保持极简：无批次、无计数
代价
A 内部并行在 trace 上不可见
明确接受
这是本期的取舍
扇出必须有总量闸，否则 500 条规则命中就写满 DB
max_tasks 默认 100 / 硬顶 1000
一个 trace 内任务总数上限
每事件命中规则数 ≤ 50
防止单次扇出过大
超出时不建任务，记 pruned: task_budget_exhausted。 绝不静默丢弃。
本期允许成环：靠 path 剪枝，不靠深度限制 真实场景：审查 → 修复 → 复审 
e1 ──▶ r1(rev-pr) ──▶ t1 ──▶ e2
                                 │
                     ┌───────────┘
                     ▼
               r2(impl-fix) ──▶ t2 ──▶ e3
                                        │
                               ┌────────┘
                               ▼
                         r1(rev-pr) ← 回边！
                         path 已含 /rev-pr/ → 静默剪枝
同一个 rule_id 在 path 里最多出现一次 → 路径最长 = 规则总数 → 必然终止
为什么允许：真实的审查循环就是这样。 禁止它等于禁止最有价值的场景。
1:1 让环的处理更简单
线性链上判断只需一次字符串包含检查，不需要图遍历。
剪枝是静默的，但不能不可观测
trace 上必须显示「这里有一条被剪掉的回边 + 原因」。否则用户看到「链走到这里就停了」却不知道为什么。
多条规则同时命中 → 全部下发 不是互斥选择 
候选 = { r | r.enabled ∧ r.match 命中 ∧ G1/G2 允许 }

0 条  → 不派任务（记 pruned span event，reason=rule_not_matched）
N 条  → 一个事务里 INSERT N 个任务

   e1 ──┬──▶ t1a（agent 审查）
        ├──▶ t1b（推手机）      ← 三条都在跑，互不等待
        └──▶ t1c（写日志）
我上一版说「按 priority 只取第一条」是错的： 那会让「同一个 PR 既派 agent 审查、又推手机通知」变成不可能 —— 而这恰恰是最基础的用法。
06 — 执行树

A → {C, D} → E：这不是一条链，是菱形

你举的 PR → A → 提前定义好「可能继续发往 C、D」→ C、D 都完成后给 E，这个形状暴露了三个必须正面回答的问题。 下面逐个说清 —— 其中第二个会直接决定这个功能是不是工作流引擎。

一次 OR 扇出 + 汇聚
cor_7f2
🔍 tsk_A 审查 done
laptop · 4m12s
╱ 2 条规则同时命中 ╲
🔧 tsk_C 修复 done
hop 2 · depth 2
🧪 tsk_D 补测试 done
hop 2 · depth 2
╲ 合并 ╱
📋 tsk_E 汇总 跑 1 次
inputs: [C, D]
C、D 是同一个 hop 层，但算 2 个原子任务。 这就是为什么 hop 和 depth 必须分开。
问题 ① E 的幂等键是什么？
现在是 sha256(event_id ∥ rule_id)。 C 和 D 各派生一个事件 → E 会跑两次。
问题 ② 要「等齐两个」才能跑 E 吗？
要等齐 = 需要跨任务状态 + 超时语义 + 迟到处理。 这就是工作流引擎的入口。
明确越界 —— 我们不做真 join
答案 ② 改成时间窗口批处理
窗口期内同一 (correlation, rule) 只建一个任务； 后到的事件追加进 inputs[]。 
"batching": {
  "windowMs": 5000,      // 0 = 不合批
  "appendInputs": true
}
这是批处理，不是 join。 UI 必须明示（否则用户以为有 join）。
允许环 —— 但环是「剪枝」不是「报错」 你提的 max hop 就是终止保证
回边是正常的：「每日巡检」把自己挂上去、 「测试失败 → 修复 → 再测试」直到变绿。
test ──▶ fix ──▶ test 剪枝
path = /test/ → 再遇 test → 已在 path 中 → 不创建
✗ 旧设计：拒绝 + 暂停整条链 + 写 chain.blocked
→ 控制台被刷满，correlation 卡在 paused
✓ 新设计：静默剪枝，只在 trace 记「已剪枝 + 原因」
→ 附带好处：不需要「已触发过」去重表，路径前缀检查就够
G2（max_hops）是唯一防死循环的闸：只要路径上 rule_id 不重复，循环必然终止。 max_hops 就是这条规则的上界外显。 只有超预算（任务数 / 付费数 / 时长）才是真拦截 + 通知。

09 — ack 与状态归属

ack 是「接单」，不是「完成」

你说「下发需要节点 ack，ack 表示完成，没 ack 的就是执行中」。 方向对，但「没 ack = 执行中」会在断线时撒谎 —— 笔记本合盖后，所有任务都显示执行中，包括那些已经跑完甚至机器已关机的。

谁观察到的事实，谁权威

2

10 — 安全（中枢永不下发命令）

最重要的一条：中枢永不下发命令

一旦中枢能下发命令行，中枢被入侵就等于所有节点 RCE。 而中枢只是一个 Go 二进制 + 一个 SQLite 文件，它是所有资产里最不该承担这个爆炸半径的地方。

中枢（可能被攻陷）
它只能表达这个：
{
  "kind": "cmd",
  "name": "review",     // 只是个名字
  "params": {
    "prompt": "审查 PR #123…"
  }
}
数据库里没有 argv 字段。
它在物理上表达不出「执行 rm -rf /」。
节点（本地 config，永不上传）

🔑 标签绑 node_id

12 — 粘性路由

第一次 hash 定节点，之后查表粘住

节点池有了负载均衡，就引入两个新问题：同一批工作还能落在同一台机器上吗、 节点下线了怎么办。你的方案是 hash + 查表 + 死了不管 —— 我采纳，但有一处必须分级。

先分清两层：计数不需要粘性，数据才需要
计数层 —— 与节点无关
「B、C、D 都落定了吗」是一次 DB COUNT(*)。 B 在 node1、C 在 node2，完全不影响。
数据层 —— 这里才需要粘性
E 要读 B、C 的产出。若 result ≤8KB 存在中枢，E 在哪都能跑； 若是大产物（diff、镜像、worktree），就必须落在同一台机器。
三行算法
sticky_key = sha256(trace_id ∥ rule_id ∥ node_selector)

① 查 node_pins → 有  → 路由回那个节点（粘住）
②              → 没有 → 按最少负载选一个 → 写入 pin
③ 节点失效时   → 只处理那一个 pin，不重排全局
key 里要有 trace_id
不同 trace 独立，否则第一个就占满
要有 rule_id
review 和 notify 可在不同机器
用 hash 不用随机
重启后仍算到同一节点，可复现
这比一致性 hash 简单得多：hash 只用于首次选择，之后一律查表 —— 根本不存在「环重排」问题。
⚠️ 「下线了不管」只对小副作用任务成立 必须分级
反例：B 是「修复代码并 git push 到分支」，在 node1 跑到 90% 时被拔网线。 按「死了不管」→ B 记为 abandoned，但 node1 磁盘上有半完成 worktree， 甚至可能已经 push 了一半。手动重跑就会产生重复 commit / PR。
命令类型节点下线时理由
idempotent: true abandoned，不重派 只读（lint / 审查 / 探索），重跑无害但也没必要
idempotent: false abandoned + 告警 + 人工确认 默认值。有副作用（push / deploy），半完成状态危险
resumable: true 重派到新节点 节点侧有 checkpoint，知道自己进度
默认是 idempotent: false（保守）：未声明的命令在节点下线时不自动重派。 原则是「宁可少做，绝不多做」。
「当死消息」≠「丢弃」
✗ 直接删掉 → trace 永久缺一块，用户看不到发生过什么
✓ 标 abandoned 留在表 → 图上看得见「这里死了」
✓ + 通知 → 用户知道要人工介入（默认行为）
三种「非成功」终态
状态重试通知
failed按 max_attempts按规则
abandoned❌ 不重试✅ 默认通知
canceled❌按规则
任务自己的属性：过期多久、能不能重投 规则可声明 
{
  "action": { "kind": "cmd", "name": "review" },
  "lifecycle": {
    "expiresInSec": 3600,     // 硬过期：到点直接 abandoned，绝不重派
    "retryable":    true,     // false = 一次性执行
    "maxAttempts":  3,        // 覆盖中枢默认
    "resultTtlSec": 604800    // result 保留 7 天
  }
}
属性默认作用
expiresInSec 继承 trace 余额 硬过期：排队超时也变 abandoned，不重派。避免「2 小时前的部署任务终于轮到」
retryable true false = 一次性。被 idempotent:false 强制为 false
maxAttempts 3 中枢重派上限，与节点内部重试无关
resultTtlSec 永不删 到期只清 result 不清行 —— trace 图仍完整
retryable vs idempotent 别混了： idempotent 说「重跑会不会有副作用」（节点能力）； retryable 说「允许重跑吗」（任务策略）。 节点说「重跑危险」是硬约束，规则只能更保守、不能更激进。
rebalance：只有一种情况才真的需要重新选节点
情况pin处理
节点暂时离线（pod 重启） 保留 任务等租约超时 → 重派时仍用这个 pin（节点可能回来）
节点被移除 / 吊销 失效 删 pin，重新选新节点 —— 这才是真正的 rebalance
节点能力变了（不再提供该命令） 不可用 立即重选 + 更新 pin + 写审计

       last_seen_at 降序 取第一个
为什么不用轮询
轮询假设任务耗时相近。但 LLM agent 一个跑 30 秒、一个跑 30 分钟 —— inflight 是真实负载的直接观测，不需要估算。
诚实说明短板：长任务 + 短任务混合时，短任务会集中在少数实例。 真解法是耗时预估或 work stealing，本期不做 —— 先积累样本。
并发自报的安全边界：可以「少」，不能「多到害别人」
攻击后果是否有害
谎报更低的 concurrency 少接任务 无害（自己吃亏）
谎报更高并真的并行跑 自己 OOM / 超时 / 烧自己额度 只伤害自己
谎报 1000 并抢走任务后不执行 任务占着租约到过期 → 拒绝服务 ⚠️ 真实风险
① 池级上限
nodes.max_concurrency
② ack 超时 20s
不 ack 就重派
③ 自动降权
连续抢到不 ack → inflight 视为满 + 告警
14 — 节点声明什么

节点说明「我能干什么」，而不是「我上报什么」

这里有一个容易搞混的地方：事件类型是 source 产生的，不是节点上报的。 节点应该暴露的是「我能执行哪些动作、要花多少钱、需要什么参数」—— 这样你在建规则时，系统能立刻告诉你「这条规则现在跑不了」。

① 事件类型 节点不上报
事实的种类
pr.opened · task.succeeded
由 source 产生。节点不产生业务事实，它只执行。
② 动作类型 节点上报
节点能干什么
review · deploy · build
这才是要暴露的 —— 它决定规则能不能落地。
③ 参数 schema 建议性
形状约定
prompt: string (≤16KB)
只用于编辑器补全与预检，写入永不拒绝。
节点连上来时，自报这份 manifest
hello 帧 
{ "manifestVersion": 1,
  "nodeId": "nod_x",
  "reported": { "os": "darwin", "arch": "arm64" },
  "concurrency": 2,
  "commands": [
    { "name": "review",
      "kind": "cmd",
      "costClass": "paid",        // ← G5 成本计量
      "params": {                   // ← 建议性
        "prompt": { "type": "string",
                     "maxBytes": 16384,
                     "required": true } },
      "produces": ["task.succeeded",
                    "task.failed"],
      "description": "用本地 pi 审查 PR" }
  ] }
manifest 里永远没有 argv / cwd / env
中枢连「命令怎么跑」都不该知道，只该知道「能不能跑、要花多少钱、要什么参数」。
这只解决一个「上线即失效」的问题
没有 manifest 时：规则里写 capability: review，而恰好没有任何节点提供它 → 任务全部 pending → 撞 attempts 上限 → abandoned 进 DLQ。

用户会先配好一切，然后才发现自己配了个空的东西。 这不是小毛病，它会直接吃掉信任。
所以保存规则时立刻预检三条
⚠
至少一个在线节点提供 review
⚠
review 需要 prompt，你有没有给
⚠
标签 gpu=true 现在有没有匹配节点
附带好处：控制台能按 params 自动生成表单；建规则时就能预估「这是付费链，每跳 $$」。

按字面画全连线，3 个 source × 3 个 sink × 3 个节点 = 15 条线 + 9 条虚线， 大部分边不表达任何意图，用户看不出该干嘛。 正确的粒度是类型级二部图。

17 — 怎么用

三个真实场景，从零到跑起来

每个场景都从「一条命令」开始，最后落到「手机上收到什么」。

场景 1 最低门槛
「我只要一条 curl 就收到通知」
这是旧产品最宝贵的用法，必须保留。现在它变成「一条规则 + 一个端点」。
①
控制台 → 新建规则 → 选「通知我」（自动生成）
②
复制 API Key
③
跑这一行
curl -X POST https://hub/v1/events \
 -H "Authorization: Bearer evt_…" \
 -d '{"source":"api",
     "type":"deploy.done",
     "subject":"部署完成",
     "summary":"构建成功"}'
📱 手机收到：「部署完成 · 构建成功」
同一个端点还能顺手触发 agent —— 配第二条规则 attributes.env == prod → cmd:deploy-verify 即可。
场景 2 核心场景
「PR 一开，我的笔记本自动跑 agent 审」
这就是你最初想要的：有个东西去触发 AI。AI 在你自己的机器上跑，中枢不碰你的代码和 key。
①
控制台 → 节点 → 添加节点，复制一次性 enroll token
②
给节点打标签 env:dev（中枢侧赋，不由节点自报）
③
在机器上装 anotifyd，写本地 commands
# 1. 装并接入
anotifyd enroll --token ent_…
anotifyd

# 2. 本地定义命令（中枢永远看不到）
#    ~/.anotifyd/config.yaml
commands:
  review:
    argv: [pi, -p, "{prompt}"]
    cwd: ~/code
    allow: true
④
控制台 → 触发源 → GitHub，拿到 webhook URL + secret
⑤
填进 GitHub 仓库 Settings → Webhooks
⑥
建规则：pr.opened → cmd:review，目标 labels.env=dev
PR 打开 → 手机收到「审查开始」→ 审完手机收到「审查完成，3 条意见」，点开直接跳到 PR。
场景 3 最省事
「这个页面变了就告我」
不用装节点，中枢自己抓。适合盯价格、盯招聘页、盯文档更新、盯某个 API 的返回。
①
控制台 → 触发源 → 页面监控
②
填 URL、间隔、以及「变了的判断方式」
③
用同一套 notify 规则模板
# 触发源配置（控制台表单）
url: https://example.com/pricing
every: 30m
diff: content-hash   # 只存哈希，不存全文
→ 无变化：不发事件（default_notify=false）
→ 有变化：evt · watch.changed
关键设计：无变化不发事件。 否则 30 分钟一次 × 10 个源 = 每天 480 条噪音，你的通知会被自己淹没。
中枢只存内容哈希 + 前后摘要，不存整个页面（体积无界 + 可能含敏感信息）。
三种场景的能力对照
场景需要装节点需要 LLM中枢能看到的适合
一条 curl 通知 ✗ ✗ 只有事件本身 部署完成、备份完成、脚本跑完
PR 触发 agent ✓ ✓ 事件 + 任务终态摘要（8KB 上限） 代码审查、自动修复、测试补全
页面监控 ✗ ✗ 内容哈希 + 前后差异摘要 盯价格、招聘页、文档、API
18 — 我们不是什么

能做的事，和明确做不了的事

n8n / Dify 自己拥有执行环境：流程在它们的服务里跑，代码在它们沙箱里执行，模型 key 存在它们库里。 这决定了它们必须做成可视化 DAG 编辑器。 我们走反方向 —— 执行归节点，中枢只编排意图。

✅ 我们能做，它们做不到 架构根因级差异
未触发的逐条件解释
它们的触发是 imperative 的，失败时系统里没有对象可供解释。我们 events 表存一切，没命中也有事件。
长时任务无上限
n8n 30 秒 / Cloud HTTP 5 分钟 / 自托管 AI 节点仍 60s；Gumloop 非企业档超限直接 reject。我们跑在你自己机器上，中枢只管租约。
凭据永不进中枢
n8n 的加密密钥明文存 ~/.n8n，queue mode 下所有 worker 共享同一把。我们没有这个字段。
实时取消
Windmill 官方承认「cancel 要等 agent 自己的 check interval」。我们走 WS 帧实时 + kill 整个进程树。
❌ 它们能做，我们不做（且不该做） 主动放弃
1500+ 应用集成
n8n 的护城河。我们只有 2 个适配器 + 通用 webhook，剩下的靠 curl。
拖拽画布
用 1/50 的工程量竞争必然输。而且会失去「可解释性」这个卖点。
真 DAG：join / 补偿事务 / 确定性重放
那是 Temporal 的活。我们只有时间窗口批处理近似。
模型网关 / 托管 key
那会失去全项目最强的安全差异点。
⚠️ 三条不能当卖点的（调研后自我纠正） 行业默认 ≠ 差异化
曾以为是卖点实际情况
只出站长连接 查了 7 个产品，无一例外都只需要 agent 出站。Buildkite 原话：「There is no need to forward ports or provide incoming firewall access」。这是入场券。
开源自托管 n8n 早就是。HN 老用户原话：「我选 n8n 而非 Zapier 正因为能自托管」。
能解释为什么没触发 ✅ 这条成立（明确市场空白），但要清醒：Windmill 已证明这形态有人想到，大厂随时可免费化。
什么时候不该用我们 主动告知比含糊更有信任
你的需求应该用为什么不用我们
把 Gmail 和 Notion 连起来Zapier / n8n它们有 400+/1500+ 集成
可视化编排 LLM 应用对外提供 APIDify / Coze我们刻意不做画布
真 DAG：条件分支 / join / 补偿事务Temporal / Argo我们只有事件驱动的多跳派发
把训练任务送到云 GPURunPod / Modal方向相反：我们送事件到你的机器
团队没人会用终端Zapier / Gumloop我们要求装 anotifyd 并写 YAML
最需要警惕的失败形态：一旦开始做拖拽画布 / 任意代码节点 / 中枢存 key / 加 50 个集成 —— 就变成 n8n 的劣化版。 我们的护城河只有三条：中枢永不持执行权（所以能被攻陷而不失守）· 图是涌现的（所以能事后长出新行为）· 可解释的求值（所以排障便宜）。
19 — 不做什么
↑ 先看：我们和 n8n / Dify 有什么不同

这张清单比功能清单更重要

这个项目历史上砍过两次功能（双向回复、severity），理由都一样： 零消费方的功能 = 纯成本。同一把尺子用在这里。

🚫
任意代码规则 / 脚本沙箱
支持成本高 + 你没法在 UI 上解释「为什么没触发」
🚫
工作流 DAG / 条件分支 / 汇聚节点
那是 Temporal 的活。需要真 DAG 的人应该去用 Temporal
🚫
中枢下发命令行
一旦能下发 = 中枢被入侵就是所有节点 RCE。DB 里没有这个字段
🚫
中枢存 agent 全量日志
体积无界 + 日志里全是 secret。只存摘要 + 尾部按需拉取
🚫
插件 SDK / 可安装触发器
本期只要通用 webhook + GitHub/GitLab 适配器
🚫
现在换 Postgres / 拆微服务 / 上 K8s
单二进制自托管是核心卖点，不是遗留包袱
🚫
声明式 reconcile / 期望状态收敛
LLM 任务昂贵、长时、有副作用、不可幂等 —— 是作业队列，不是 kubelet
🚫
双向对话（人回复 → 注入 agent）
已否决过，本设计不重开。人和 agent 之间是单向的
📌
一条容易误判的边界，请 review 时对照： 接力引入了「节点 → 中枢」的结果回报通道，外观上很像把已经删掉的双向回复加回来。 但它不是同一件事：删掉的是「人回复通知 → 注入 agent」（对话）； 这里是「机器回报任务终态 → 调度器才能决定重试」（调度闭环的必要条件）。
