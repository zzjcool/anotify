Anotify · 模型片断

边缘节点：任务怎么下发、下游怎么触发、能力怎么定义

只讲一段：中枢 ↔ 边缘节点（Anotify Agent）↔ 能力进程。 全模型只有四样东西——能力（入参 + 端口）、link（端口 → 下游，带可选字面量）、 emit（唯一的产出通道）、digest（记账）。其余都是推导量。

术语统一：边缘节点 = Anotify Agent 能力声明里没有"出参类型" 参数怎么拼是能力自己的事 端口只有名字

01能力怎么提前定义

定义只有四块：入参 schema、端口名、实现、digest。 注意它没有「出参类型」——产出要求由 link 推导（见 02/03）。

review @2
可执行 · 有节点声明
① 入参 params_schema
"params": { "required": ["diff"], "properties": { "diff": { "type": "string" }, "lines": { "type": "integer" } } }
② 端口 ports（只有名字）
fix push partial
端口没有 schema、没有类型、没有保留字。它能去哪个下游由 link 决定。
③ 实现（在产物里）
entrypoint: run.sh · files: 3 · timeout: 900s
④ digest（系统算，没人手写）
sha256:9f3c…a17e
同一个能力，两个端口各接各的
fix fixer@3 notify@1 1 : N
push pusher@1
partial 未接下游 = 到此为止（合法）
link 表（中枢持有）
fromporttoliterals
reviewfixfixer@3{}
reviewfixnotify@1{"to":"u_123"}
reviewpushpusher@1{}
literals 是常量覆盖：{"to":"u_123"} 让你改收件人时不用改脚本、不用重新部署节点。 没有引用映射（{{result.x}}）——参数怎么拼是能力自己的事。
02任务怎么下发

一个 assign 帧就是一次派发的全部内容。它不带命令（执行内容来自本地缓存的产物）， 但必须把「跑哪份字节」和「每个端口要产什么」都说清楚。

assign 帧
{ "type": "assign", "task_id": "tsk_8f21a3c0", "capability": "review", "version": 2, "digest": "sha256:9f3c…a17e", // 跑哪份字节 "params": { "diff": "…", "lines": 42 }, "ports": ["fix", "push", "partial"], "expects": { "fix": { "schema": { "required": ["issue", "title"], "properties": { "issue": { "type": "string" }, "title": { "type": "string" } } }, "targets": [ { "capability": "fixer", "needs": { "issue": "string" } }, { "capability": "notify", "needs": { "title": "string" } } ] }, "push": { "schema": { … }, "targets": [ … ] } } }
每个字段为什么存在
digest节点只执行这一份字节；本地没有它 → 明确报缺，不跑"近似版本"
params入参。已经过下游 params_schema 全量校验
ports封闭集合：emit 报的名字不在里面 → 当场拒绝，不用等进程退出
expects.schema机器门槛：该 port 所有下游要求的并集（减去各自 literals）。节点拿它做严格校验
expects.targets给人/LLM 看的：这个口能去哪、各自要什么——据此主动拼对，而不是被拒了再猜
expects 是推导量，不落库：中枢在派发那一刻从 link 算出来。 同一 port 的多个下游要求同一字段不同类型 → 保存 link 时就拒，所以节点拿到的 expects 不可能自相矛盾。
03下游怎么触发（emit 的两条路）

能力调用 anotify-agent emit （同一个二进制，父子进程，走本地 socket）。 校验通过 → 中枢去重后按 link 派发；校验不过 → 当场拒绝，实现补齐再发。

通过 emit → ack → 下游
① emitagent 本地 socket
② 校验port ∈ ports · data ⊨ expects[port]
③ 转发emit 帧 → 中枢
④ 去重UNIQUE(task_id, seq)
⑤ 派发link(fix) → fixer, notify
⑥ ack进程拿到 0，继续跑
ack 两级：默认「已落盘」（毫秒，本地 outbox）；--wait-routed 才是「已派发到下游」（一次 RTT）。 默认语义写进契约，调用方不用猜。
被拒 缺字段 / 类型不对 / 超限
$ anotify-agent emit --port fix --data '{"issue":"#42"}' emit rejected: port "fix" 要求 {issue, title} missing: title (string) exit code 2 # 补齐后重发，同一次运行里可以多次 emit $ anotify-agent emit --port fix \ --data '{"issue":"#42","title":"空指针"}' ok seq=2
拒绝一次 emit ≠ 任务失败。实现拿到非 0 和缺什么，可以补上再发。 这正是「在最早的地方发现参数问题」——而不是等中枢静默剪枝、然后去 trace 里考古。
扇出 = 两种叠加，互不排斥
静态 1:N
同一个 port 上接了多条 link。一次 emit 派发 N 个子任务。
fixfixernotify
动态多次 emit
一次运行里 emit 多次（同一个口或不同的口）。LLM 中途输出就是这条。
seq1 fixseq2 fixseq3 push
04六条纪律（每一条都能单独解释为什么）
节点不持全图
边缘节点只知道本次任务的 ports 和 expects，任务结束就丢。link 由中枢定义与管辖—— 否则加一台机器就会改变链路，两台机器的不一致没有任何机制能发现。
唯一写者
去重表、任务行、剪枝记录只有一个写者（中枢）。所以 emit 的 ack 必须来自中枢； 想省延迟，省的是等待（本地 outbox），不是把中枢移出路径。
阻塞 ack
emit 是有副作用的动作。fire-and-forget 会让「emit 成功但中枢没收到」变成静默丢事件—— 这是这套系统一直在消灭的失败方式。异步是显式的逃生口，不是默认。
状态来自进程
退出码 / 信号 / 租约到期，都是确定事实。端口只表达业务去向（fix / push）， 不承担状态语义，也没有保留字。
digest 记账
任务钉住「跑的是哪份字节」。名字解决「我要最新」，摘要解决「证明当时是那份」。 历史 trace 因此永远可解释，本地变体也不会被静默使用。
端口没有 schema
一个 port 接 N 个下游时，"这个 port 的类型"没有唯一解。所以门槛由中枢从 link 推导成 expects，在 emit 那一刻生效。
