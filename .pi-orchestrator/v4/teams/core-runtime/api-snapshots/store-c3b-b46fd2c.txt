package store // import "github.com/zzjcool/anotify/internal/store"

Package store 提供 SQLite 数据访问层。

迁移机制：schema.sql 是单一事实源，按 `-- +migration N name` 切块， 每个编号版本在一个事务内应用并记入
schema_version 表；失败必须返回错误， 不允许静默跳过（见 migrate.go）。

const MaxTaskParamsBytes = 120 << 10
    MaxTaskParamsBytes 是单条任务 params 的硬上限（120 KiB = 122880 字节）。

    这是**传输层**限制：节点把整份 params 塞进子进程环境变量，而 Linux 对单个 env/argv 串的硬上限是
    MAX_ARG_STRLEN = 131072，超过 execve 直接 E2BIG。 留 ~8KiB 余量给前缀与其它 argv 后取 120KiB。

const RoleAuto = "auto"
    RoleAuto 是 RegisterUser 的**入参专用**值，永不落库：它要求本函数在自己那个 事务里数一次 users，据此决定角色 —— 0
    个用户 ⇒ RoleAdmin（首个注册用户是超管， 契约 §2.1），否则 RoleMember。

    为什么必须在**同一个事务**里判：调用方「先查 count、再 INSERT」是两次独立的 连接池操作。连接池放开到
    8（store.go defaultMaxOpenConns，#240）之后，两个并发 首注册可以先后读到 count=0，于是**双双拿到
    admin**（凭空多出一个超管账户）。 移进本函数后，count 与 INSERT 共享同一个 BEGIN IMMEDIATE 事务（写锁在事务起点
    就持有），后一个注册者的 BeginTx 会等到前一个提交后才开始 —— 它必然读到已提交 的那一行，因此只可能有一个 admin。

    注意：本值是 role 字段的第三种取值，**不能**被其它写用户路径（CreateUser / UpdateUserRole）接受；它们仍只认
    admin|member。

const TaskRejectSlotUnavailable = "slot_unavailable"
    TaskRejectSlotUnavailable 是 task.reject.reason 的第二个合法值（A3 正式扩码）。

    T3 会把 `stale_config | slot_unavailable` 写进共享封闭集合；在 T3 的 delta 到货前 store
    本地先接受它，因为「容量不可用」不能拿 stale_config 伪装（父裁决）。

    形状规则只有一份（artifact.Validate）；这里只把它归成一个 store 层的哨兵错误。

var ErrDeploymentExists = errors.New("store: deployment already exists")
    ErrDeploymentExists 同一 (node, capability, digest) 已经部署过。

var ErrDuplicateUserCode = errors.New("store: user_code 唯一冲突")
    ErrDuplicateUserCode 表示插入授权会话时短码 UNIQUE 约束冲突。 调用方应据此重试生成新短码，而非向用户报错。

var ErrEmitIDConflict = errors.New("emit_id_conflict")
    ErrEmitIDConflict 表示同一逻辑任务里同一个 emit id 被用于**不同**的请求（to/data）。

    它是 emit 网关的 409 `emit_id_conflict`：调用方必须换一个 id（或用新 id 重发）。 静默按第一次的请求重放会让「我改了
    data 怎么没生效」变成一个查不出来的问题。

var ErrEmitNamespaceDenied = errors.New("namespace_unauthorized")
    ErrEmitNamespaceDenied 表示节点未获授权访问任务所属命名空间。

    它是**授权**失败（不是身份失败）：节点身份是真的，但它没被授权碰这个 ns。 单独一个哨兵是为了让上层能把「不该派给它」与「伪造身份」分开记日志。

var ErrNodeIdentityMismatch = errors.New("node_identity_mismatch")
    ErrNodeIdentityMismatch 表示 emit 声明的节点身份与库里那条节点不一致。

    它挡的是「拿到别人令牌的进程替自己冒领」：一次 emit 的执行权属于 某个节点 + 某个 attempt，两者都必须和权威事实对上。

var ErrNotFound = errors.New("store: record not found")
    ErrNotFound 表示记录不存在。

var ErrNotImplemented = errors.New("store: not implemented")
    ErrNotImplemented 是「还没实现的 store 方法」的哨兵（重构期脚手架，#55）。

    今天没有任何实现返回它：TestNoStubRemains 用它当门禁——新增方法若是空壳， 必须返回本错误，这样那条用例会在 CI 里立刻点名。

var ErrParamsTooLarge = errors.New("params_too_large")
    ErrParamsTooLarge 是 params 超限的哨兵（errors.Is 可用）。

var ErrRefUnresolved = errors.New("store: link ref unresolved")
    ErrRefUnresolved 表示**引用本身就不成立**（空串 / 空名字）：这是调用方的形状错误， 不是「查不到」。

    与 ErrNotFound 的分工：ResolveRef 查不到名字/版本时返回 ErrNotFound（那是数据事实， handler 翻
    404、配置期翻 ErrEdgeRejected）；只有「引用是空的」这种明显写错的情况 才走这个哨兵，文案里能立刻看出是参数问题。

var ErrReservedEventSource = errors.New(`"route" 是保留来源名（剪枝记录专用）`)
    ErrReservedEventSource 表示有人把保留来源名当普通来源用。

    业务事件若用了 `source='route'`，会被事件流过滤掉（**静默消失**）、并在 trace
    视图里被当成剪枝。这种丢数据的失败必须当场报错。

var ErrResourceVersionInvalid = errors.New("store: resource version invalid")
var ErrUpgradeBreaking = errors.New("upgrade_breaking")
    ErrUpgradeBreaking 是「新版本会破坏已有的 name 型 link」的哨兵错误。

    handler 用 errors.Is 判它 → HTTP 409 + 结构化 body；具体的「变了什么 + 哪些 link」 在
    *UpgradeBreakingError 里（errors.As 取），供前端直接列出来让人确认。

var ErrVersionConflict = errors.New("store: capability version already exists with different content")
    ErrVersionConflict 表示 (namespace, name, version) 已经存在，但执行正文**不同**。

    版本行不可变：同一个 name@version 不许换内容覆盖，也不会被静默改写成别的版本号。 判定用
    artifact.SameContent（digest 相等）；next / displayName 是既定例外。

    形态里有时间戳和内容 hash 前 8 位——但这两者都**不足以保证唯一**：

type Artifact struct {
	// P2 起产物不再是一个行身份：它是能力行正文的**派生**（Capability Spec v3 §11）。
	// 曾经留过一个空的 ID 字段做兼容，P2b 已删：没有行身份就没有 ID，
	// 任何调用方读到它只会得到一个永远为空的假标识。
	NamespaceID  string `json:"namespaceId"`
	CapabilityID string `json:"capabilityId"`
	Digest       string `json:"digest"`
	// Spec 是整份产物的 canonical JSON（CanonicalJSON 的结果，含 metadata 与 spec）。
	Spec []byte `json:"spec"`
}
    Artifact 是一份能力产物的**派生值**（Capability Spec v3 §11.2）。

    P2 之后它不再是表里的一行，而是「能力行的正文 + metadata」拼出来的整份产物： digest 是能力行的 content_hash（≡
    产物 digest），Spec 是整份 canonical JSON。 之所以还留着一个结构体而不是返回 (digest, spec)：deploy
    帧、/v1/artifacts、撤销帧 三处都要同一份形状，拼三遍迟早会拼出三种 digest。

    字段取舍（契约 §11.2 / P2a）：
      - NamespaceID / CapabilityID / Digest / Spec 是内容的全部身份，都留着；
      - CreatedAt 删掉：没有行了，就没有落库时间（它唯一的作用是「新的在前」排序， 而按能力取只有一份）。

func (d *DB) AckCancelAuthorized(ctx context.Context, auth NodeAuthorization,
	in ReapedInputs, processGroupReaped bool) error
    AckCancelAuthorized 处理 `cancel.ack`：**当前认证身份 + 精确历史绑定**。

    它取代了旧的公开 AckCancel（只带 task/attempt/reaped，没有节点身份与历史
    lease/slot，无法证明「这是哪一次执行的哪个物理槽」）。语义分两种：

      - **当前 attempt + 取消在飞**：processGroupReaped=true 时在**同一事务**里把任务
        原子终结（cancelled/abandoned，按取消原因）并回收它自己绑定的槽；false 只表示
        「收到了」——不改相位、不释放槽、不清租约（等下一次可信回收）。
      - **历史 attempt**（任务已重排/已进入新 attempt）：旧授权不需要仍然 active， 但必须证明身份 +
        历史 node/task/attempt/lease/slot 全部相符；只回收那个旧槽， **不**碰新 attempt
        的相位/token/槽，也不恢复任何旧 result/emit。

    绑定不符（错 lease/slot/instance/节点）一律 fail closed（ErrLeaseMismatch /
    ErrNodeIdentityMismatch），不 no-op 假成功。

    幂等是**逐字节**的：一次 attempt 只被回收一次（reaped_at IS NULL CAS），重复 ACK 不重写
    ReapedAt/reclaim_reason、也不重写历史行的 phase/error/finished_at，更不碰 任务的当前相位/新
    attempt 的槽。历史行的失败原因/结果事实是只读的。

func (d *DB) AssignTask(ctx context.Context, taskID, nodeID, assignmentID string, proposedAttempt int) error
    AssignTask 记录**派发候选**：这次想派给哪个节点。

    它**不授执行权**：phase 仍是 pending、没有 lease、没有 attempt token。 真正授权发生在 GrantLease（节点
    accept 之后）——这样「派了但节点没接」 不会消耗尝试预算，也不会让一条 pending 任务凭空显示成 running。

    assignmentID 是这次候选的身份（中枢生成，随 task.assign 帧下发）；节点 grant 时
    必须带回同一个值，否则视为旧派发（ErrNoAssignment）。

    两条硬条件写在**同一条 UPDATE** 里（不先读后写）：
      - cancel_requested_at IS NULL：已请求取消的任务永不再被选点；
      - 目标节点必须仍 online（EXISTS 子查询）：draining/offline 的节点不接新任务。

    前面的节点状态读只用于给出准确错误，真正的判定在 UPDATE 的 WHERE 里（原子）。

    assignment 带**统一有界窗口**（AssignmentWindowSec，初值 30s）：它与节点侧 pending reservation
    用同一个截止时刻（task.dispatch.assignmentExpiresAt），窗口失效后 grant 不得再使用它。同一
    assignment/节点在窗口内重复 assign 是幂等的（不写第二份 reservation）。

func (d *DB) AuthorizeNamespace(ctx context.Context, userID, namespaceID string) error
    AuthorizeNamespace 是「这个用户能不能碰这个命名空间」的**唯一收口** （#204 安全语义 / #205 收口）。

    今天的安全语义（明确写在这里，避免以后误读）：
      - 一套部署 = 一个团队；
      - **本部署任何已登录用户，都可以访问任何存在的命名空间**；
      - 数据隔离只在命名空间这一级（图 / 事件 / 任务 / 源各自独立）， 组织那一级已经删除。

    将来若要按命名空间分权限：新增 `namespace_members` 表，**只改这一个函数** （以及 CreateNamespace
    时的成员写入），其余调用点的形状完全不变 —— 这就是 把它做成单一收口的目的。不要在各个 handler 里散着写归属判断。

    返回：
      - namespaceID 空 / `*`（AllNamespaces）→ ErrNamespaceRequired（HTTP 400）
      - userID 空或用户不存在 → ErrAuthRequired（HTTP 401）
      - 命名空间不存在 → ErrNamespaceNotFound（HTTP 404）
      - 否则 nil

func (d *DB) AuthorizeNamespaceForNode(ctx context.Context, namespaceID string) error
    AuthorizeNamespaceForNode 是 AuthorizeNamespace 的**机器主体**版本（#207 阶段 2）。

    为什么需要单独一个入口：WS 节点握手的主体不是登录用户，而是 opaque 节点令牌。
    令牌本身已经把命名空间钉死（`nodes.token_hash` → 那一行的 `namespace_id`，
    见 internal/ws/node_handshake.go），所以「已登录」这一环由令牌证明，
    这里只需要判断那个命名空间**仍然存在**（命名空间被删后，旧令牌必须立刻失效， 而不是继续拿着一个已消失的隔离边界当作用域跑任务）。

    与 AuthorizeNamespace 的关系：两者是同一个安全收口的两条主体路径， 判断都收敛在 store
    包内，**不要**在 internal/ws 里自己写存在性判断。 将来新增 `namespace_members` 时：用户路径改
    AuthorizeNamespace（按成员表判）， 机器路径保持「令牌合法 ⇒ 该命名空间下的机器已获授权」——节点令牌是
    按命名空间签发的，成员关系改变不追溯已有令牌，这一点必须显式保持。

    返回：namespaceID 空 / `*` → ErrNamespaceRequired；命名空间不存在 →
    ErrNamespaceNotFound。

func (d *DB) DeleteExpiredEvents(ctx context.Context, cutoff int64, limit int) (int64, error)
    DeleteExpiredEvents 删除 created_at 早于 cutoff 的事件（含剪枝留痕），单次最多 limit 行。

    **引用组安全**（父裁决）：只要同一个 (namespace, trace_id) 还有**任务行**，这条 trace 的事件就不删——trace
    视图里「根事件还在、链还在跑」是用户正在看的东西， 提前把根删掉会让一条活着的链路变成孤儿数据。任务行自己的保留期到了之后，
    下一轮就会把这些事件一起清掉（引用消失 = 保护失效）。

    **不按 source 过滤**：剪枝行同样是「只进不出」的增长来源，给它开特例等于把泄漏留在库里。

    注意本函数**不动去重记录**：去重窗的过期判定在接收路径按 expires_at 现算
    （见 InsertEvent），与事件实体是否被删无关。清理过期去重记录是另一件事
    （DeleteExpiredEventDeliveries），它只清窗口记录，绝不删事件实体。

    limit <= 0 直接返回 0 而不删：调用方传错时「少删」远好于「删全表」。

func (d *DB) DeleteExpiredPlaybookInstalls(ctx context.Context, cutoff int64, limit int) (int64, error)
    DeleteExpiredPlaybookInstalls 删除**未被引用**且 created_at 早于 cutoff 的安装回执。

    它是**独立 primitive**，不挂在任何自动 sweeper 里（父裁决：event/task/result 三类
    自动清理都不删回执）：回执是安装审计（谁在哪一版装了什么，receipt 原文就在行内）， 它的保留期是产品决策，不是「事件过期」的副作用。call
    它的人必须显式给 cutoff。

    引用保护（**检查与删除在同一个事务里**，否则「查完到删之前刚好有人引用」会删掉活引用）：
      - capability_versions.installed_from / sources.installed_from 指向的 → 永不删；
      - 被**保留的 trace** 引用的 → 永不删（安装动作以回执 id 作 trace 根时， 那条 trace
        的事件/任务还在，回执就是它的锚点）。

    引用列没有外键（回执可以被清、能力行不该跟着走），所以保护只能在这里显式判。 limit <= 0 直接返回 0（同
    DeleteExpiredTasks：少删好于删全表）。

func (d *DB) DeleteExpiredTasks(ctx context.Context, cutoff int64, limit int) (int64, error)
    DeleteExpiredTasks 删除可信终态观察早于 cutoff 的任务，单次最多 limit 行。 收到 Node
    result 用首 result_accepted_at；服务器裁定的未上报终态用 finished_at。 Node 报告的进程
    finish（可很旧/很未来）不驱动保留期。

    限批形式必须是 `DELETE ... WHERE id IN (SELECT ... LIMIT ?)`：`DELETE ... LIMIT` 需要
    SQLite 编译期开关，依赖它等于把可移植性交给构建产物的运气。 按可信观察时间排序：一批删不完时下一轮从更老的开始，积压再大也不会「新的先删」。

    **物理事实保留（G1-6S）**：任务行不能比它的执行事实先消失。只要还有一条 `task_attempts.reaped_at IS NULL`
    的 attempt（进程组是否回收没被可信事实证明）， 这条终态任务就不删：删了之后槽位绑定/历史 attempt 会随外键级联消失，旧进程再也
    无从对被回收，同一个物理槽可能被新任务复用。 代价（接受）：一个永远拿不到 reaped 事实的坏节点会把对应任务钉到人工处理。

    limit <= 0 直接返回 0 而不删：调用方传错时「少删」远好于「删全表」。

func (d *DB) EmitAuthorized(ctx context.Context, auth EmitAuth, rec *EmitRecord, tasks []*Task) (json.RawMessage, bool, error)
    EmitAuthorized 在**同一个事务**里完成「授权校验 + 幂等记录 + 建下一跳任务行」。

    事务内顺序（不可调整）：

     1. 节点身份：nodes 行存在，token_hash == auth.NodeTokenHash；
     2. 命名空间授权：authorized(node_configs.namespaces) ∩
        declared(nodes.declared_namespaces) 覆盖任务所属 ns；
     3. 执行授权：task.phase=running、task.node_id=auth.NodeID、 attempt/lease_id
        相等、sha256(auth.AttemptToken)==attempt_token_hash、 lease_until
        未过期、**没有取消在飞**；
     4. 幂等：emit_id 非空且已存在 → to_ref/data 相同回旧 result（first=false）， 不同 →
        ErrEmitIDConflict（**第 3 步不过就一律拒，已存在也不能绕过**）；
     5. 写入：插入 emit 行 + 同事务建子任务（任何一条失败整体回滚）。

    第 4 步为什么必须在授权之后：一条**已经失效**的执行（被取消 / 租约过期 / 被重派） 如果能靠「我上次已经 emit
    过」拿到回执，它就会认为自己仍然拥有执行权， 于是继续跑完并写终态——幂等变成了绕过授权的后门。

func (d *DB) GrantLeaseAuthorized(ctx context.Context, auth NodeAuthorization,
	taskID, assignmentID string, proposedAttempt, slot int, now int64) (
	leaseID, attemptToken string, attempt int, expiresAt int64, err error)
    GrantLeaseAuthorized 授予一次执行租约（**每次执行唯一授权入口**）。

    与旧 GrantLease 的区别不是「加了一个参数」：认证/授权/预算/绑定/快照都在 **同一个 BEGIN IMMEDIATE
    事务**里完成——没有任何「先 GetNode 校验再无条件写」 的窗口。事务内顺序：

     1. 当前节点身份（nodes.token_hash == auth.NodeTokenHash）；
     2. 任务当前候选：assignmentId + node 归属 + proposedAttempt **三项精确匹配**， 且窗口未过；stale
        请求只被拒绝，不改当前候选；
     3. namespace 交集（node 声明 ∩ 授权覆盖任务 ns）；
     4. attempt 预算（maxAttempts，超了直接终态）；
     5. 机器配置 applied 事实；
     6. 三层执行预算（grantBudgetOn：总量 / 跨 ns 同名能力 / pinned maxPerNode）；
     7. 把节点 accept 回报的真实 slot 绑到 (task, attempt, lease)；
     8. 落 attempt 机器快照（vars/limits/来源/revision/hash）+ 写任务执行授权事实。

    任何失败都不消耗 attempt、不占槽、不伪造 lease；容量拒绝回 pending + waiting_for_slot（有界退避）。

func (d *DB) InsertEvent(ctx context.Context, e *Event, now int64, windowSec int64) (inserted bool, err error)
    InsertEvent 写入一条外部事件（带**投递去重窗**的幂等）。

    判据走独立的 event_deliveries 表（source.md §3.3 D7/D12）：

        窗口内（expires_at > now，或 expires_at = 0 永久） → 回已有事件，inserted=false
        窗口已过                                        → **当成新事件**：新 eventId 落库，
                                                          去重记录换成新 eventId/acceptedAt/expiresAt
        没有 deliveryId                                 → 每次插入新行（不比较、不去重）

    为什么不靠 sweeper：窗口判定必须在**接收事务里**按 expires_at 现算。靠后台清理 会让「窗口刚过、sweeper
    还没跑」这段窗口里的投递被错误地吸收掉——而 sweeper 可能 一小时才跑一次。

    也不依赖 events 上的唯一索引：旧事件可能因为被 task 引用而**活过**去重窗 （见 DeleteExpiredEvents
    的引用保护），此时同 id 的新投递必须仍然能收进来。 去重是「窗口」，不是「永久的投递 id 唯一性」。

func (d *DB) InsertPruneEvent(ctx context.Context, e *Event) error

    多条相同的剪枝压成一条，反而掩盖了扇出规模。所以这里不做幂等（也不带 deliveryId）。

func (d *DB) InstallPlaybook(ctx context.Context, namespaceID, slug string, values map[string]any, dryRun bool) (*playbook.Receipt, error)
    InstallPlaybook 在**一个 BEGIN IMMEDIATE 事务**里完成一次安装（§4.4 / §4.6）。

    顺序固定：

        ① 读包体（事务内，走 tx）
        ② Render + 读库快照（installSnapshot，六个只读查询也走 tx）→ Plan
        ③ 有 conflict → 返回 *playbook.Error（完整 details / valuesDigest / conflicts / hint），0 写
        ④ INSERT 计划里的 **create 条目**（能力行 + next 投影；新源行 + token + targets 投影）
        ⑤ INSERT 回执行（masked values + digest + 回执原文 + ns/原 slug/原包 id 快照）
        ⑥ COMMIT；dryRun 在 ⑤ 之后 Rollback（同一路径，0 持久写）

    边界（卡上红线，写代码时不要越过去）：
      - Plan 说 reuse 的条目**一行都不碰**：不能调 CreateCapability / UpdateSource 的折叠更新路径，
        否则会偷改已存行的 next / displayName / targets（I-P1）。

func (d *DB) MaintainStats(ctx context.Context) ([]string, error)
    MaintainStats 是一次「运行期」的统计维护：先问 SQLite 需不需要刷新（按它的建议执行），
    再对会持续增长的大表做一次**确定性**漂移检查（#265）。

    为什么不能只跑 `PRAGMA optimize=0x2`（这是 #265 的第一版，已证伪）：它够不到
    **运行期漂移**。某个命名空间的 tasks 从 100 行涨到 1 万行时，sqlite_stat1
    里可能仍记着 100，规划器据此选错计划——表现是「索引明明建好了但查询很慢」，而且没有任何报错。
    实测（`TestMaintainStatsRefreshesDriftedStat1`）：100 → 2500 行（25×）后调 `=0x2`，
    返回**空建议集**，stat1 停在 100；所以「按需」那一半是安慰剂，必须自己判。

    两个层次（代价与收益对齐，既不无条件 ANALYZE 全库，也不把自己骗过去）：
      - `PRAGMA optimize=0x2`：只处理「表上有索引但没有 stat1 条目」（统计**缺失**）， 统计新鲜时是一次纯检查，成本趋近
        0；
      - `refreshDriftedStats`：只针对 `tasks`，把 stat1 里的行数估计与真实行数比， 差 ≥10 倍才
        `ANALYZE "tasks"`（统计**过期**）。一条 `count(*)` 的成本， 换来的是规划器不会拿着 100 行的估计去扫
        100 万行。

    返回被执行的语句（用于日志/测试断言）。空切片 = 这次不需要做什么。

    安全：执行的语句必须来自 SQLite 自己的建议且形如 `ANALYZE ...`（见 isAnalyzeSuggestion），
    或来自本包自己写死的 `ANALYZE "tasks"`。

func (d *DB) ReapTaskAttempt(ctx context.Context, in ReapedInputs) (bool, error)
    ReapTaskAttempt 是**历史 attempt** 的物理回收入口（旧授权无需 active）。

    它只做两件事：给该 attempt 记 reaped 事实、清它自己占的那个槽；**不碰**任务的 phase / 当前 attempt / 当前
    token / 新 attempt 的槽。重复调用幂等。

    拒绝规则（fail closed，不 no-op 假成功）：
      - 节点不存在或 token hash 对不上 → ErrNodeIdentityMismatch；
      - attempt 行不存在，或 node/lease/instance/slot 与历史绑定不一致 → ErrLeaseMismatch。

    旧 attempt 的 result / emit 仍由 CompleteTask / EmitAuthorized 拒（它们核对的是 **当前**
    attempt + lease + 未过期租约）；本入口不放行任何业务提交。

func (d *DB) ReclaimStaleSlots(ctx context.Context, nodeID string, observations []SlotObservation, now int64) (int, error)
    ReclaimStaleSlots 按**明确的实例事实**回收槽位绑定（绝不读任务相位做推断）。

    旧判定是「槽位指向的任务已不在 running → 清槽」——那是拿数据库状态冒充物理回收 事实：租约过期只吊销授权，进程组可能还在跑；hello
    重连也不证明旧进程已死 （rehello ≠ reaped）。现在只有满足全部条件的观察才会回收：
      - Busy 显式为 false（缺字段/未提到的 slot 都是未知，不是空）；
      - 观察里带相符的历史 taskId/attempt/leaseId（无匹配引用的 idle 记录不能清旧 busy）；
      - 观察时刻不早于该绑定的建立时刻（旧快照不能放掉它没看见的新占用）。

    回收只清**那一条** (instance, task, attempt) 绑定，并把该 attempt 记上 reaped 事实； 不改变任务
    phase / token / 新 attempt 的槽。返回真正回收的槽数（无事实 = 0，不是假成功）。

func (d *DB) ReconcileNode(ctx context.Context, nodeID string, applied []AppliedCapability, now int64) (ReconcileStats, error)
    ReconcileNode 用节点自报的 applied 列表对账它名下的部署行。

    判据（中枢覆盖语义，capability.md §2.4）：
      - digest 与期望一致 → applied（绿勾）
      - digest 不一致 → pending + reason 里写明两端 digest（stale，等重推）
      - 节点没上报这条能力 → pending（缺失，等重推）

    期望值取**能力行**的 digest（deploymentDigestSQL），不是 deployments.digest 列的副本：
    列里那份是建行那一刻的快照，而「这个能力现在的产物」只有能力行说了算。 老库里指向历史内容的行因此会自然收敛到当前内容。

    只动该节点名下的行；一个事务内完成（对账是「读一遍自报 + 写一批状态」，中间被插入 新部署时不会产生半新半旧的观测）。

func (d *DB) RecoverLostLeases(ctx context.Context, now int64) (int, int, error)
    RecoverLostLeases 回收**真正失联**的 running 任务（调度巡检的唯一入口）。

    两类候选人：租约到点的 running 任务，以及**所在节点已 offline** 的 running 任务。 `draining`
    **不是**失联：drain 的语义是「不再接新任务、把存量跑完」，在跑的 任务照常续租/回报结果（只有 offline 才是「这台机器不在了」）。

    决策分三条，判据来自任务行上钉住的 idempotent（不回读能力，避免「能力改过一次就换了语义」）：

        已请求取消                    → 终局（cancelPhase(原因)），**绝不 retry**
        幂等 且 attempt < maxAttempts → 回 pending + retry_backoff + 退避（会重跑）
        否则                          → abandoned（infra 原因，绝不重跑非幂等能力）

    **物理槽位不在这里释放**（任何分支都不）：租约过期只吊销授权，不证明进程组已回收； 节点 offline
    也只说明连接断了（会话死亡），不等于机器上的进程没了。物理槽必须由 可信事实回收：`cancel.ack` 的 reaped=true（当前
    attempt）或 ReapTaskAttempt / ReclaimStaleSlots 的明确实例事实（历史 attempt）。节点 offline
    时另一个入口 （MarkNodeOffline）会把槽位标成不可派发且**保留** busy 账本。

    返回 (重排条数, 直接终态条数)。

func (d *DB) RequestCancel(ctx context.Context, taskID, reason string, now int64) error
    RequestCancel 记录一次取消意图（取消与 grant 的**唯一线性化点**）。

      - pending：没有执行者，直接终态（cancelled / abandoned），不需要等 ack；
      - running：只落 cancel_reason + cancel_requested_at，等节点 cancel.ack 带回
        processGroupReaped=true 才置终态并释放槽位（进程可能还在跑）。

    读与写必须在**同一个事务**里（DSN `_txlock=immediate`，写锁在事务起点拿下）： 先读后写的两步之间如果被 grant
    插进来，就会把一条**正在跑**的任务无条件改成已取消， 而节点上的进程还在用着那个槽位。现在两种赢法都是对的：
      - 取消先赢（pending → 终态）：随后的 grant 看到终态/取消标记，直接拒；
      - grant 先赢（pending → running）：取消走 running 分支，只记意图，等 reap。

    重复取消是幂等的（返回 nil，保留第一次的原因）：网关重试/两个管理员同时点 不该变成 409。已终态 →
    ErrInvalidTransition（调用方翻 409）。

    now 由调用方给（测试可注入）；0 → Now()。配置从 system_config 读（GetSystemConfig），

func (d *DB) UpsertInstances(ctx context.Context, nodeID string, specs []InstanceSpec) ([]*NodeInstance, error)
    UpsertInstances 落库节点申报的实例槽位；超过 nodes.max_instances 返回 ErrTooManyInstances。

    UserCount 返回用户总数（用于「首用户判定」与仪表盘）。

func (d *DB) VerifyAttemptToken(ctx context.Context, taskID, token string) (*Task, error)
    VerifyAttemptToken 用明文令牌换任务（emit / task.result 的权威校验）。

    判据四条，缺一不可：库里 sha256 与传入一致、相位是 running、**没有取消在飞**、 **租约尚未过期**。旧 attempt
    的令牌必然对不上：每次 grant 都会换一个随机令牌并 覆盖哈希，于是「上一代执行的进程在重派后继续 emit」会被稳定拒掉。

    过期租约返回 ErrLeaseMismatch（与 emit 接受事务里的同一条判据同口径）： 这个函数被声明为
    task.result 的权威校验，不能声称「令牌对就算授权」却漏掉到期。 真正不可绕过的版本仍是 EmitAuthorized /
    CompleteTaskAt：它们在同一个事务里 重做全部判定，本函数只是快速失败与诊断。

    取消一发起就**立刻收回令牌**（返回 ErrTaskNotRunning → 网关 409 task_not_running）：
    被要求停下的执行体不该还能 emit 出新任务、也不该还能写终态——它的结局由 cancel.ack（processGroupReaped）裁定。

type EmitAuth struct {
	// TaskID 是发起 emit 的逻辑任务。
	TaskID string
	// NodeID 是提交这次 emit 的节点。
	NodeID string
	// NodeTokenHash 是节点身份令牌的 sha256（与 nodes.token_hash 比对）。
	NodeTokenHash string
	// Attempt / LeaseID / AttemptToken 是本次执行的三件套（过期或错一个就拒）。
	Attempt      int
	LeaseID      string
	AttemptToken string
	// Now 是判定租约未过期的时刻（0 → Now()）。
	Now int64
}

    为什么授权参数必须进同一个事务：`VerifyAttemptToken` + 另一个事务写派发， 中间会有一个窗口——任务刚好被取消
    / 租约刚好过期 / 被重派给新 attempt。 那个窗口里写下去的下游任务属于一次**已经失去执行权**的执行，

type EmitRecord struct {
	ID        string          `json:"id"`
	TaskID    string          `json:"taskId"`

	ToRef     string          `json:"toRef"`
	Data      json.RawMessage `json:"data"`

	// 四项都得对上）。它们可以属于一个已经过期/已撤销的 attempt，但必须是那一次的真实值。
	LeaseID string
	Slot    int
	// InstanceID 是内部键（可选加固）：给了就一并核对。
	InstanceID string
	Now        int64
	// Reason 是诊断来源（空 → node_report）。
	Reason string
}
    ReapedInputs 是「某个 attempt 的进程组已回收」这一事实在 store 内部的形状。

    它不是 wire DTO，也不允许被当成 DTO 镜像：G2 按 T3 冻结的最终帧字段映射进来 （共享
    protocol.ValidateCancelAck 在 G2 强制 leaseId 与 slot presence； store 的 int slot
    保持内部形状，不镜像 wire 指针）。

    关键语义：旧授权**不需要仍然 active**（lease 可过期、任务可已重排/终态）， 但必须证明「是哪个 attempt 的哪个绑定」：node
    身份（token hash）+ 历史 attempt 行里的 lease/instance/slot 全都对上才回收。

type SlotObservation struct {
	Slot int
	// Busy 为 nil 表示这次没有为该 slot 给出明确事实（未知），不得用于回收。
	Busy *bool
	// TaskID / Attempt / LeaseID 是这个占用的执行标识。
	TaskID  string
	Attempt int
	LeaseID string
	// AssignmentID / ProposedAttempt 是尚未 grant 的 reservation 标识（无 lease）。
	AssignmentID    string
	ProposedAttempt int
	// ObservedAt 是节点采集这条事实的时刻（0 = 不设保护）。观察到之后才建立的
	// 绑定（updated_at 更晚）不能被旧快照误放。
	ObservedAt int64
}
    SlotObservation 是当前连接对某个物理槽位「此刻在跑什么」的**明确事实**。

    它是槽位回收的唯一可信输入（G2 从 T3 最终帧映射；store 内部形状不镜像 wire）：
      - Busy 三态：nil = 未断言（未知），true = 明确仍在跑，false = 明确无进程；
      - busy=true 带 taskId/attempt/leaseId（已授权的执行）或 assignmentId/proposedAttempt
        （尚未 grant 的 reservation，**不伪造 lease**）；
      - busy=false 时必须带相符的历史 taskId/attempt/(leaseId)：无匹配引用的 idle 记录 不能清旧
        busy（rehello / 缺字段都不等于进程已死）。

    C3a 起 Busy=true 的 reservation 事实会落进**真实槽账本**（node_instances： busy_task
    + busy_attempt=proposedAttempt + busy_lease_id 为空 + busy_assignment_id
    + busy_expires_at），前提是能对上中枢当前候选（pending/同节点/同 assignment/同 proposed/
    窗口有效）。预算统计因此能看见「节点已经接住、但还没 grant」的真实占用；节点谎报一条 对不上候选的 reservation
    只会被忽略（不制造容量）。执行类的 Busy=true 不重绑：节点 不能凭一句 busy 重新定义某次历史执行的绑定。

    `nil` 数组 / 空数组 / 没提到某个 slot 都**不表示空闲**。

    UserPassword 是 users 表的密码列（迁移 8：第二套登录模型，与 Passkey 并存）。

    为什么单独一个类型、而不是给 User 加字段：/v1/auth/me 与 admin 用户列表都会直接 序列化
    User，密码哈希一旦挂上去就是一次真实泄露。哈希只走这条专用通道， 只在认证服务内部读一次、用完即弃。

    空串 Hash = 未设置密码（纯 Passkey 账号）；UpdatedAt = 最近一次设置/修改的 unix 秒， 0 表示从未设置。
