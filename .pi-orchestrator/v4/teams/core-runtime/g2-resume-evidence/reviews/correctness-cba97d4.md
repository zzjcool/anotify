## Findings（G2 diff 内缺陷）

| ID | 严重度 | 位置 | 证据与可复现行为 |
|---|---|---|---|
| G2-C1 | **critical** | `internal/ws/hub.go:423` | dispatch 的 `ConfigRevision` 取自 `node.ResourceVersion`，而 `sendWelcome` 在 `internal/ws/hub.go:360` 发送的是 `cfg.Revision`。`nodeColumns` 把 `node_configs.resource_version` 扫进 `Node.ResourceVersion`（`internal/store/node.go:219-222`）；schema 默认 `revision=0, resource_version=1`（`internal/store/schema.sql:209-210`），配置 PUT 又分别递增（`internal/store/config.go:761-783`）。真实 anode `HandleDispatch` 用 `appliedRev != f.ConfigRevision` 判断 stale（`cmd/anode/internal/runner/runner.go:409-410`）。**复现**：节点首次 hello 后 welcome 发 `configRevision="0"`（无配置行）或 `"1"`（有一条配置），dispatch 发 `"1"`/`"2"`；真实 Node 一律回 `task.reject stale_config`，任务进入 pending+waiting_for_config 退避，**永远无法执行**。G2 测试只断言非空（`internal/ws/ws_test.go:27-29`），所以假节点测试全绿也掩盖了此问题。 |
| G2-C2 | **major** | `internal/ws/hub.go:405-407` | `DispatchOnce` 每次扫描都给同一 pending 任务新 mint `assignmentID` 并 `AssignTaskAt`，未检查任务已有的未过期 assignment。`ListDispatchableTasks` 不过滤 assignment（`internal/store/task.go:608-622`），`AssignTaskAt` 对“不同 assignment”会直接覆盖（同文件 `693-696`）；真实 anode 持有旧 assignment 的 reservation 时会忽略新 dispatch（`cmd/anode/internal/runner/runner.go:391-402`）。**复现**：连续调用两次 `DispatchOnce`，任务 assignment A1→A2；节点若已用 A1 accept 会得到 `ErrNoAssignment`，且继续忽略 A2；任务被 30s reservation 卡住并每秒 churn。这与冻结契约“same-binding duplicate idempotent”冲突。 |
| G2-C3 | **major** | `internal/ws/handlers.go:86` | `task.reject` 只校验 wire `Node == sess.nodeName`（`handlers.go:81-84`），随后调用无身份的 `store.RejectAssignment(ctx, taskID, assignmentID, reason, now)`（`internal/store/task.go:761-824`）；store 事务只匹配 phase+assignment_id，不校验 assignment 的 `node_id == 当前认证节点`，也不存在 Authorized 变体。**行为**：任何已认证节点一旦获知别台的 assignmentId（泄漏/日志/旧帧），即可把别台候选清回 pending+退避；且这正是冻结卡禁止的 “Get-precheck + unguarded write”。修复需由 store owner 增加 `RejectAssignmentAuthorized(auth, …)`/同事务 node CAS；G2 至少应上报该签名 gap，而不是按已完成处理。 |
| G2-C4 | **major** | `internal/route/emit.go:114`（写剪枝事件） vs `:140`（EmitAuthorized） | emit 剪枝路径先调用 `recordPrune`（`internal/route/emit.go:114`，内部 `InsertPruneEvent` 无授权）再进入 `EmitAuthorized`（`:140`）。前置的 `VerifyAttemptToken`（`:91`；store `internal/store/task.go:1150-1180`）只校验 attempt token/phase/cancel/lease，**不校验当前节点凭证 hash/ns**。**复现**：running 任务的节点 token 已被 `SetNodeTokenHash` 轮换，旧会话带仍有效的 attemptToken，emit `to=consumer, data={}`（param_missing）→ `VerifyAttemptToken` 通过、剪枝事件已落库，随后 `EmitAuthorized` 以 401 `token_invalid` 拒绝；DB 多出一条 `source='route'` 事件，且该 eventId 不会返回给调用方。违反“先授权后写/回放”的冻结顺序；需 store 提供在同一 `EmitAuthorized` 事务内写 prune 记录的入口，或明确裁决该观察写入的例外。 |
| G2-C5 | **minor** | `internal/source/source.go:272-273` | `PreviewSource` 对每个 `StatePruned` 目标统一回填 `plan.Pruned[0].Reason`；而 `PlanFromSource` 的 pruned target 不写自身 Reason（`internal/route/route.go:195,204`；`prunedTarget` `218-225` 只置空串）。**复现**：源 targets=`[ghost, needs-env($(payload.env))]`，预览缺 payload → target[0] missing 正确，target[1] 应为 `param_missing`，实际显示 `downstream_missing`（第一条 Prune 的原因）。receipt 路径用 `plan.Pruned` 不受影响，仅 dry-run 每目标原因错误。 |
| G2-C6 | **minor** | `internal/ws/hub.go:720-742` | `deliverLogs` 向容量 1 的 `waiter.ch` 直接阻塞发送（`732/739/742`）；`RequestLogs` 在返回后才删除 waiter（`hub.go:644-700`，`ch` 在 `682` 创建）。节点对同一 requestId 连发两条 `logs_response` 时，第二条可能在第一条被消费/删除前到达，发送永久阻塞读循环，节点会话不再处理任何上行业务（仅自身受影响，但违反有界/非阻塞要求）。 |
| G2-C7 | **minor** | `internal/ws/hub.go:516-571` | `Deploy` 对显式 `nodeIDs` 不校验节点对目标 namespace 的授权/可部署条件，直接 `CreateDeployments`（`:549`）并向在线会话发 `capability.deploy`（`:571`）。store `CreateDeployments` 只检查 node 存在（`internal/store/deployment.go:238`），不校验 ns 授权；ack 侧虽在 `handlers.go:221-225` 拒绝未授权 ns，但已写入 pending 行并向未授权节点泄漏 name/version/digest。需在 producer 侧过滤 Explicit targets，或上报 store 的 `CreateDeploymentsAuthorized` 签名 gap。 |

## Protected pending（已知、不判为个人擅漏；但不能据此认为 full G2 ok）

1. **结构化日志协议缺口**：`LogsResponseFrame` 无逐条 `sequence/stream/text/at`；G2 明确 `Structured=false`，只做历史 node/attempt/requestId 关联，未伪造时间戳/空成功（`g2-resume-evidence/G2-WRITER-VERDICT.md` §4.1；`LOG-RECORDS-HANDOFF.md` R1–R8）。待父裁决 Node-log 补口。
2. **事件+任务跨事务缺口**：`InsertEvent`（`internal/store/event.go:83`）与 `CreateTasks`（`internal/store/task.go:254`）无原子组合；G2 事件先落、任务失败返回错误，不伪造成功回执，重复投递由窗口吸收（`internal/source/source.go:104-175`）。待 store owner 裁决。
3. **downstream_missing failed task 形状缺口**：`store.CreateTasks` 只允许 pending 起始，G2 只写剪枝观察并回 `taskId:null + pruned`，不捏造 failed task（`internal/route/emit.go` / `G2-WRITER-VERDICT.md` §4.3）。待父裁决。
4. **旧产品退役的跨 owner 引用**：`internal/server/mux.go:15` 仍 import 已删除的 `internal/executor`；`Makefile:65`、`Dockerfile:52`、`Dockerfile.agent:27`、若干 `scripts/` 仍构建 `./cmd/agent`。这属于 G3/G4 预期旧引用，非 G2 代码缺陷，但 upstream `go test ./...`/`make build`/`make contract` 在 G3/G4 前不可能全绿；不能拿 G2 包测试代替全仓门禁。
