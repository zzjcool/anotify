## 问题（已确认事实）

- `tasks` 只有 `cancel_reason` 一列（`internal/store/schema.sql:398`，仅 `-- +migration 1 baseline`）记录停止意图。
- `RequestCancel` / `RequestAbandon`（`internal/store/task.go:887-1000`）共用状态机，running 时只落 `cancel_reason`；`cancelPhase`（`task.go:1005+`）与 cancel.ack / 租约回收路径只能从 `cancel_reason` 封闭码反推意图。
- 因此 `POST …/tasks/{id}/abandon` 带**人话 reason** 时，ack 会落 `cancelled` 而非契约的 `abandoned_by_user`（#348 已文档化该限制；无 reason 的 abandon 正确）。
- 相关测试：`internal/server/resource_task_test.go:579-631`（人话 reason 原样落 cancel_reason）、`:1086`；`internal/store/dispatch_failure_test.go:368`。

## 实现（按 issue 正文）

1. `tasks` 增加 `stop_intent TEXT NOT NULL DEFAULT ''`（`cancel` | `abandon`；空 = 无停止意图）。
   - v4 schema 未发布：可直接改 baseline（用户已批准 v4 baseline 全量切换）；**仍须**保证新库重开幂等（`Open` 二次不报错），并在报告给出重开/往返证据。若选择追加 migration 块，必须幂等（SQLite 无 `ADD COLUMN IF NOT EXISTS`，用 `migrate.go` hooks 兜，见 DEVELOPMENT.md「schema 变更」）。
2. `RequestCancel` 落 `stop_intent='cancel'`，`RequestAbandon` 落 `'abandon'`（pending 直接终态的路径同样落库）；`cancel_reason` 保留原语义（人话 reason / 默认封闭码）。
3. `cancelPhase`（cancel.ack / 租约回收 / ack 回执）改读 `stop_intent` 判定：`abandon` → `abandoned_by_user`；`cancel` → `cancelled`。**不得**再靠 reason 字符串猜；未知/空 stop_intent 的存量行按现行为兜底（新库不会有，但别 panic）。
4. 不改 wire/DTO 语义（`stop_intent` 内部列，非 API 字段）；除非契约明确要求暴露，不加公开字段。

## 必须的回归（真实、具名）

- `abandon`（running + 人话 reason）→ 落 `stop_intent=abandon`；cancel.ack 后相位 = `abandoned_by_user`（不是 `cancelled`）。
- `abandon`（running + 无 reason）→ 默认码 + `abandoned_by_user`（原正确行为保持）。
- `cancel`（running + 人话 reason）→ 相位 = `cancelled`。
- `pending` 的 cancel/abandon 直接终态行为不变（`cancelled_by_user` / abandoned）。
- store 往返：写入后读回 `stop_intent` 一致；新库 `Open` 两次幂等。
- 既有校验（终态任务拒绝 RequestCancel 等）不删不弱化。
