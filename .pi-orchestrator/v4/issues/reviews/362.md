## Findings

**1. [minor] `internal/server/resource_capability.go:783` — stale-only 时 `Deployed.reason` 恒为 `NotDeployed`，`protocol.ConditionReasonStale`（`internal/protocol/enums.go:88`）仍零赋值。**
独立运行 stale-only 场景的实际值：`{"status":"False","reason":"NotDeployed","message":"1 台节点持有旧 digest（人工点部署才会下发）"}`。
闭集允许两者，且冻结文档的**示例本身**就是 `{type: Deployed, status: "False", reason: NotDeployed, message: "1 台节点持有旧 digest（…）"}`（`capability.md:117`），所以**不算违规**；PR 描述也主动声明了该取舍。但词表里的 `Stale`（`:381/:384` 定义 = 节点持有旧 digest）分支仍未启用，"升级待部署"与"从未部署"在机器码上不可区分，只能读中文 message。建议由 epic owner 二选一：emit `Stale`，或修文档示例/词表；不阻塞本 PR。

**2. [minor] PR 描述/issue 的「首次部署候选 checkbox 为空」因果与当前前端不符。**
`web-src/pages/capabilities.html:6332` 的 `#deploy-nodes` 候选来自 **nodes 列表**（`NODES`，`:1683` 用 `/v1/.../nodes` 填充），整页对 `status.nodes` **零引用**（grep `status.nodes` 无命中）；`depForNode` 只用来给已有部署打标。故 `status.nodes` 修好不会改变该模态框的候选集，issue 的「后果 ②」是过期/错误诊断。#335 `capability-actions` 的依赖应在合并后由 #335 收口方按真实 API 复跑确认（issue 已把这一步留给 #335，不是本 PR 的缺陷）。

**3. [note，pre-existing，不在 diff] `api/resource.yaml:1637` `CapabilityNodeState.state` 描述仍是 `deployed / pending / offline / …`。**
与冻结设计的闭集 `deployed/stale/missing` 不一致（base `2e4bb48` 已如此，非本 PR 引入）。既然本 PR 让 `stale` 真正落地，建议顺手把描述对齐（纯 description，不改形状）；不作为本 PR 的阻塞项。

**刻意不做核对**：`nodes[].state` 未 join `node_capabilities`（`capability.md §5` 写 `deployments × node_capabilities`）—— issue 明确允许保持现状并要求「若引入 join 必须有测试证明不改变既有可见集」，本 PR 选择不引入，符合 issue 边界，不判缺失。
