## 0. 用户的话（需求原话）

> "这里都不需要组，就是直接让用户填 script.echo,notify.phone 这样就可以了，
> 我们说过，具体调用什么交给具体的程序"
> "端口这个东西完全没必要体现出来啊，没意义啊"

端口是**路由键**（`emit` 的寻址参数），不是能力、也不是用户要表达的概念。
用户脑子里只有一件事：**这个能力跑完交给谁**。

## 1. 内部约定（对用户不可见）

- 一个能力**只有一个出口**，内部端口名固定为 `out`。
  有下游 → `outputs = ["out"]`；没下游 → `outputs = []`（终端能力）。
- 边：`fromPort = "out"`，`toRef` 是候选能力。
- 同一出口的多个下游 = **候选**（运行期按 priority + 同级轮盘选一个），语义不变。
- 协议帧、`edges.from_port` 列、`ANOTIFY_EMIT_PORTS` 的**形状都不变**，
  只是里面的端口名永远是 `out`。

## 2. 脚本侧

`emit` 的 `--port` 变成**可选**：

```bash
anotify-agent emit --data '{"touched":true}'          # 常规：单出口，自动填 out
anotify-agent emit --port done --data '…'             # 仅当能力有多个出口时才必须给
```

- 能力只有一个出口（绝大多数）→ `--port` 省略，agent 自动用它。
- 多个出口 → 省略 `--port` 时**报错并列出可用端口**（不猜）。
- 兼容：显式给 `--port out` 也照常工作（同一个值，不是兼容层）。

创建表单提交的仍是现有 API：`{outputs:["out"], links:[{fromPort:"out",toRef:"script.echo",priority:0}]}`。

## 3. 控制台：只谈"下游能力"

创建/编辑表单：

```
下游能力（候选）
┌──────────────────────────────────────────────────────────┐
│ script.echo, notify.phone                                │   ← 一个输入框，逗号分隔
└──────────────────────────────────────────────────────────┘
跑完之后交给谁。多个 = 候选，运行期按优先级选一个；留空 = 终端能力（跑完就结束）。
```

- **删掉**「产出端口（ports）」输入框与「候选（按优先级选择）」的独立区块
- 优先级：单一输入框里不表达（全部 0）。需要调优先级时去能力详情的下游列表里改——
  那是"候选"的唯一归属地（`PATCH /v1/capabilities/{id}/links` 之类现有接口，C 组按现状接）
- 校验：逗号分隔的名字 trim + 去重；引用不存在的能力 → 400 并指出是哪个名字
- 提示文案里**不得出现"端口"二字**（四语言都一样）

能力详情：

```
下游（候选）
  回声（示例）    script.echo      ← 点进去是能力详情
  通知推送        notify.phone
  优先级 0 · 点「编辑」可调
（空）跑完就结束，不会触发任何下游。
```

- 不再单列"产出端口"
- 脚本样例区（已有）给的 emit 示例**不带 `--port`**

## 4. 图（源页 / trace 页 / 能力页的小图）

- 边标签**不再显示端口名**（`out` 这种名字对读者是噪音）。
- 候选 = 同一对（或同一源头）节点之间的多条边，已有的 1:N 连线足够表达。
- 例外：若某能力真有多个出口（`outputs` 长度 > 1，历史数据），才显示端口名 ——
  这条是给"以后真需要第二种产出"留的门，当前 UI 不产生这种数据。
- 灰点（未接下游）**保留**，但文案改成「没有下游」——它现在表达的是
  "这个能力不会再触发任何能力"，不是"某个端口没接线"。

## 5. 迁移

dev 库里现有数据（`touch@2` 的 `outputs=["echoed"]`、一条 `echoed` 边）**不迁移**：
协调者直接把它改成 `out`（或让用户重建）。生产库尚未存在。

多出口能力（`outputs` 长度 > 1）**不允许**被自动合并成 `out`：前端提交时若检测到
目标能力是多出口，按原样保留其端口结构（只读展示 + 提示"这是多出口能力"），
不要替用户做破坏性改写。
